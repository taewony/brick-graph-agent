Abstract

This study presents micro-vLLM, a Windows-native LLM inference engine artifact implemented with CUDA Python 1.0 and a cuTile-style kernel development workflow. Rather than claiming performance superiority over mature Linux serving stacks, micro-vLLM is designed as an educational systems artifact that exposes prefill, decode, paged KV cache, prefix caching, CUDA Green Contexts, and memory-allocation bottlenecks in a reproducible Windows GPU environment.

The artifact follows a staged migration path from tiled MatMul to fused multi-head attention, a minimal LLM-from-scratch loop, and finally a nano-vLLM-style serving engine. Prior measurements show that WSL2 FlashAttention achieves 2138.55 tok/s on average, approximately 4.62x faster than the current Windows-native cuTile backend at 463.35 tok/s. This result motivates a conservative framing: micro-vLLM is useful for migration, inspection, and education rather than immediate production replacement.

We further evaluate fixed-context agent workloads, where requests share long static prefixes such as system prompts, database schemas, SKILL.md files, or course contexts. On an RTX 5070 target PC, warm prefix KV-cache reuse reduces computed prefill tokens to 64 in all tested settings and reduces TTFT by 41.1%, 66.1%, and 79.7% for 1024-, 2048-, and 3072-token static prefixes, respectively. The negative-control condition with changed prefixes yields 0.0% cache hit and near no-cache TTFT. End-to-end throughput does not consistently improve in the 64-token generation benchmark because decode dominates total runtime.

1. Introduction

As generative AI systems become more widely deployed, there is growing demand for running LLMs on local PCs, laboratory machines, private networks, and offline educational environments. Applications such as RAG, natural-language database querying, CUDA kernel programming tutors, and local knowledge agents often reuse a fixed body of context while answering short user questions. In these settings, understanding local inference latency, memory behavior, and KV-cache reuse is as important as calling a remote cloud API.

Most high-performance LLM serving stacks, however, are tightly coupled to the Linux GPU software ecosystem. vLLM, TensorRT-LLM, FlashAttention, Triton, and NCCL-based distributed execution provide strong performance, but they are difficult to modify or teach step by step in a Windows-native environment. WSL2 is a practical workaround, but it still creates a boundary for Windows-native application development and GPU runtime education.

This paper therefore focuses on an educational systems artifact, not on absolute peak performance. micro-vLLM connects CUDA Python 1.0, a cuTile-style kernel workflow, tiled MatMul, FMHA, a minimal autoregressive loop, paged KV cache, prefix cache, continuous batching, and Green Contexts. The revised contribution centers on fixed-context agent workloads and a measured prefix KV-cache evaluation.

Contributions

  1. Windows-native educational systems artifact: micro-vLLM is organized as a staged migration path from MatMul and FMHA to LLM-from-scratch and nano-vLLM-style serving.
  2. Fixed-context agent benchmark: the paper defines agent workloads that repeatedly reuse system prompts, database schemas, SKILL.md files, and course contexts.
  3. Prefix KV-cache evidence: measured results show that warm cache reduces computed prefill to 64 tokens and reduces TTFT from 41.1% to 79.7% across 1024/2048/3072-token static prefixes.
  4. Serving-loop bottleneck analysis: the paper reports WSL2 FlashAttention baseline results, allocator thrashing, and mixed Green Contexts results to show that isolated kernel improvements do not automatically guarantee end-to-end serving gains.

2. Background

LLM Serving Loop

Autoregressive LLM serving consists of a prefill phase, which processes the prompt, and a decode phase, which generates one token at a time. Prefill is sensitive to prompt length and attention workload, while decode is sensitive to scheduler overhead, memory bandwidth, KV-cache access, and kernel-launch overhead at each token step. The same engine can therefore react very differently depending on whether a workload is prefill-dominated or decode-dominated.

Paged KV Cache and Prefix Cache

Paged KV cache manages Key/Value cache memory in blocks to reduce fragmentation and support dynamic batching. Prefix cache adds token-identical prefix reuse. If a new request shares the same token prefix as a previous request, the engine can reuse the corresponding KV blocks and prefill only the new suffix. Cache hits depend on exact token-level stability, so timestamps, run identifiers, and user-specific metadata placed early in the prompt can eliminate reuse.

CUDA Python 1.0, cuTile, and nano-vLLM

CUDA Python 1.0 provides access to CUDA runtime and driver APIs from Python. A cuTile-style DSL expresses tile-level GPU kernels within a Python workflow, lowering the entry barrier compared with C++ CUDA while exposing more hardware behavior than high-level PyTorch operators. nano-vLLM is a compact reference for understanding vLLM-style serving, and micro-vLLM migrates that style into a Windows-native CUDA Python experimentation path.

micro-vLLM Serving Architecture

micro-vLLM implements a lightweight serving loop for Qwen-family models. The scheduler manages waiting and running sequences. The BlockManager handles KV-cache block allocation and hash-based prefix reuse. Each Sequence tracks prompt tokens, generated tokens, a block table, and the number of cached tokens. ModelRunner separates prefill and decode while preparing input IDs, positions, sequence lengths, slot mappings, and block tables.

In the prefix-cache path, the scheduler checks complete-block hashes during sequence allocation. When an identical prefix block exists, seq.num_cached_tokens increases, and prepare_prefill sends only the suffix after the cached prefix to the model. The key sequence length still reflects the full context, while the query sequence length reflects only the newly computed suffix.

Text-to-SQL agents repeatedly include database schemas and SQL behavior rules. CUDA tutors repeatedly include course modules and grading rubrics. Educational knowledge agents repeatedly include selected OKF concept bundles. Once the first request loads the static prefix into the cache, later requests can prefill only the dynamic suffix.

4. Experimental Method

The experiments were conducted on a Windows 11 target PC with an NVIDIA GeForce RTX 5070 GPU. The recorded environment has 48 SMs, approximately 12GB VRAM, and 48MB L2 cache. micro-vLLM used a Qwen-family model.

The prefix-cache benchmark was executed with KernelAgent/3-micro-vllm/bench_prefix_cache.py. For each static-prefix length, three conditions were compared.

ConditionDescription
no_cacheClear the persistent hash table before each request and perform full prefill.
warm_cachePrime the cache once and then reuse the same static prefix.
prefix_changedChange the first prefix token as a negative control that prevents exact-prefix hits.

Each condition ran 8 requests. Static-prefix lengths were set to 1024, 2048, and 3072 tokens. The dynamic suffix was fixed at 64 tokens, and the generation length was fixed at 64 tokens. The benchmark recorded cache hit ratio, cached tokens, computed prefill tokens, TTFT, end-to-end latency, decode P50/P99 ITL, and throughput.

Warm prefix cache reduces computed prefill tokens to 64 in all static-prefix settings. The TTFT reduction grows as the static prefix becomes longer. With a 3072-token prefix, TTFT decreases from 381.76 ms to 77.47 ms, a 79.7% reduction.

The prefix_changed negative control produces 0.0% cache hit in all experiments and returns TTFT close to the no-cache condition. This confirms that the measured improvement comes from exact-prefix reuse rather than measurement noise. End-to-end throughput, however, does not improve consistently under warm cache. In this 64-token generation benchmark, decode dominates total runtime. The correct interpretation is therefore prefill-work and TTFT reduction for fixed-context workloads, not universal throughput speedup.

Allocator Thrashing Negative Result

Dynamic shape padding was intended to reduce JIT shape variation, but it caused padded tensor allocation and copy operations at every decode step, increasing PyTorch CUDA caching allocator and Python GC overhead. In the earlier benchmark, the no-padding eager path achieved 470.82 tok/s, while the dynamic-padding path achieved only 155.16 tok/s, a 67.04% throughput decrease.

Green Contexts split the 48 SMs of the RTX 5070 into 32 SMs for prefill and 16 SMs for decode. Initial single-run results showed some improvement, but repeated averages were nearly flat. This suggests that SM partitioning alone does not improve end-to-end latency when the current Python engine loop does not sufficiently overlap prefill and decode.

6. Discussion

Agent workloads differ from generic benchmarks because they repeatedly use long static contexts. Natural-language database agents repeatedly inject schemas and rules. Educational agents repeatedly inject course modules and rubrics. Placing the static prefix before the dynamic user query can therefore affect runtime efficiency, not only model quality.

micro-vLLM is not faster than production vLLM. Its practical value for a KTCP-style contribution is that it allows Windows-native execution and modification of the LLM serving loop, provides a staged learning path from MatMul to micro-vLLM, and makes both successful optimizations such as prefix caching and failed optimizations such as dynamic shape padding reproducible.

This paper deliberately excludes the ActiveGraph + Tau Coding Agent extension. That topic is better handled as a separate educational knowledge-agent or agent control-plane paper. Paper #1 mentions AI coding agents only as supporting tools for experiment design and analysis, while keeping the core contribution focused on the micro-vLLM artifact and measured systems behavior.

7. Limitations

  1. The measurements come from a single RTX 5070 target PC and should not be generalized directly to other GPUs or datacenter deployments.
  2. The Windows-native cuTile backend is substantially slower than WSL2 FlashAttention, so the work should not be interpreted as a production performance claim.
  3. The prefix-cache benchmark uses 64-token generation, which makes the workload decode-dominated and prevents consistent end-to-end throughput improvement.
  4. Prefix-cache effectiveness depends on exact token-prefix stability.
  5. Green Contexts produced mixed results in the current sequential Python engine loop.

8. Conclusion

This paper presents micro-vLLM, a Windows-native LLM inference engine artifact built with CUDA Python 1.0 and a cuTile-style workflow. Since WSL2 FlashAttention achieves 4.62x higher average throughput than the Windows cuTile backend, the paper frames micro-vLLM as a migration, inspection, education, and bottleneck-analysis artifact rather than a production serving replacement.

The fixed-context agent workload experiment demonstrates the value of prefix KV cache. Warm cache reduces computed prefill to 64 tokens for 1024/2048/3072-token static prefixes and reduces TTFT by 41.1%, 66.1%, and 79.7%, respectively. The changed-prefix negative control shows 0.0% cache hit and near no-cache TTFT, validating the exact-prefix reuse mechanism.
