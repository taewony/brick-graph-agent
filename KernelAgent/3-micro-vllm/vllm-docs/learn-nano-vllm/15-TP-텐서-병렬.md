# 강의 15: 텐서 병렬 (Tensor Parallelism)

본 강의는 nano-vllm에서의 **텐서 병렬(Tensor Parallelism, TP)** 구현을 심층 분석합니다. 이는 대형 모델 추론에서 가장 널리 사용되는 다중 GPU 병렬 처리 전략입니다. 수학적 원리를 바탕으로 `ColumnParallelLinear`, `RowParallelLinear`, `QKVParallelLinear`, `MergedColumnParallelLinear`, `VocabParallelEmbedding`의 설계 사상과 구현 세부 사항을 하나하나 설명하며, 면접 핵심 포인트와 함께 다룹니다.

---

## 1. 텐서 병렬이 필요한 이유

### 1.1 단일 GPU의 병목 현상

대형 모델의 파라미터 수가 증가하면서 단일 GPU에는 두 가지 병목 현상이 발생합니다.

**메모리 병목**:

| 모델 규모 | 파라미터 수 | FP16 가중치 크기 | KV Cache (2048 seq, batch=32) | 총 필요량 |
|---------|-----------|---------------|------------------------------|----------|
| 7B | 7×10⁹ | 14 GB | ~8 GB | ~22 GB |
| 13B | 13×10⁹ | 26 GB | ~16 GB | ~42 GB |
| 70B | 70×10⁹ | 140 GB | ~80 GB | ~220 GB |

A100-80GB 조차도 70B 모델의 가중치를 수용할 수 없으며, KV Cache는 말할 것도 없습니다.

**연산 병목**:

단일 GPU의 연산 능력은 제한적입니다. 메모리가 충분하더라도 7B 모델을 단일 A100에서 Decode 처리량은 약 2000 tokens/s인 반면, 4장의 A100으로 텐서 병렬을 사용하면 ~6000 tokens/s에 도달할 수 있습니다.

### 1.2 병렬 처리 전략 개요

| 전략 | 분할 차원 | 통신 패턴 | 적용 시나리오 |
|------|---------|----------|------------|
| **데이터 병렬(DP)** | 배치 기준 분할 | AllReduce 그래디언트 | 학습 |
| **텐서 병렬(TP)** | 가중치 행렬 기준 분할 | AllReduce 활성값 | 추론 (동일 노드) |
| **파이프라인 병렬(PP)** | 레이어 기준 분할 | 점대점 활성값 전송 | 학습 + 추론 (노드 간) |
| **시퀀스 병렬(SP)** | 시퀀스 길이 기준 분할 | AllGather/ReduceScatter | 긴 시퀀스 시나리오 |

### 1.3 추론에서 텐서 병렬을 선호하는 이유

추론 시나리오에서 TP는 다른 전략에 비해 독보적인 장점을 가집니다.

1. **낮은 지연 시간**: 모든 GPU가 동시에 계산하므로 한 레이어의 계산 시간은 거의 \( 1/N \) (N은 GPU 수)입니다. PP는 레이어를 순차적으로 처리해야 하므로 지연 시간을 줄일 수 없습니다.
2. **높은 활용도**: 각 GPU는 항상 할 일이 있습니다. PP는 추론 시 이전 레이어의 출력을 기다리는 "거품(bubble)"이 존재합니다.
3. **효율적인 AllReduce**: 동일 노드 내 GPU는 NVLink로 연결되어 AllReduce 대역폭이 최대 600 GB/s에 달합니다.
4. **비교적 간단한 구현**: Linear 레이어의 가중치 분할 방식만 수정하면 됩니다.

### 1.4 텐서 병렬의 핵심 아이디어

텐서 병렬의 핵심은 **행렬 블록 곱셈**입니다. 선형 레이어 \( Y = XW + b \)에 대해 가중치 행렬 \( W \)를 특정 차원을 기준으로 여러 GPU에 분할하고, 각 GPU는 부분 결과만 계산한 후 마지막에 통신으로 취합합니다.

```
단일 GPU:     Y = X × W           [M×K] × [K×N] = [M×N]

2-GPU TP:     Y₀ = X × W₀        [M×K] × [K×N/2] = [M×N/2]   ← GPU 0
              Y₁ = X × W₁        [M×K] × [K×N/2] = [M×N/2]   ← GPU 1
              Y = [Y₀, Y₁]       연결하여 [M×N]
```

핵심 문제는 **어느 차원을 분할할 것인지**, 그리고 **언제 통신이 필요한지**입니다.

## 2. 열 병렬 (ColumnParallelLinear)

### 2.1 수학적 원리

가중치 행렬 \( W \in \mathbb{R}^{K \times N} \)을 **열(출력 차원) 기준**으로 \( N_{\text{tp}} \)개로 분할합니다.

\[
W = [W_0, W_1, \ldots, W_{N_{\text{tp}}-1}], \quad W_i \in \mathbb{R}^{K \times (N/N_{\text{tp}})}
\]

각 GPU는 다음을 계산합니다.

\[
Y_i = X \cdot W_i, \quad Y_i \in \mathbb{R}^{M \times (N/N_{\text{tp}})}
\]

**결과는 완전한 출력의 일부 조각**입니다. 즉, 각 GPU는 \( N/N_{\text{tp}} \)개의 열 출력을 보유합니다.

```
입력 X:      모든 GPU 동일  [M × K]
가중치 W₀:   GPU 0         [K × N/2]
가중치 W₁:   GPU 1         [K × N/2]
출력 Y₀:     GPU 0         [M × N/2]  ← 앞쪽 N/2 열
출력 Y₁:     GPU 1         [M × N/2]  ← 뒤쪽 N/2 열
```

### 2.2 주요 특징

1. **입력 통신 불필요**: 각 GPU는 동일한 전체 입력 \( X \)를 받습니다.
2. **출력은 분할된 형태**: 각 GPU는 출력 열의 일부만 보유합니다.
3. **후속 레이어도 열 병렬일 경우**, 분할된 출력을 그대로 입력으로 사용할 수 있어 통신이 필요 없습니다.
4. **후속 레이어가 전체 입력을 필요로 하는 경우**(예: RowParallelLinear), 통신이 필요합니다.

### 2.3 nano-vllm 구현

```python
class ColumnParallelLinear(LinearBase):
    def __init__(self, input_size, output_size, bias=False):
        # output_size를 tp_size로 나눔: 각 GPU는 1/tp_size의 출력 열만 저장
        super().__init__(input_size, divide(output_size, tp_size), bias, tp_dim=0)

    def weight_loader(self, param, loaded_weight):
        # 전체 가중치에서 현재 GPU에 해당하는 열 분할을 추출
        shard_size = param_data.size(self.tp_dim)
        start_idx = self.tp_rank * shard_size
        loaded_weight = loaded_weight.narrow(self.tp_dim, start_idx, shard_size)
        param_data.copy_(loaded_weight)
```

#### 생성자 해석

```python
super().__init__(input_size, divide(output_size, tp_size), bias, tp_dim=0)
```

- `input_size`: 그대로 유지 (각 GPU가 전체 입력을 받음)
- `output_size / tp_size`: 각 GPU는 \( 1/N_{\text{tp}} \)의 열만 출력
- `tp_dim=0`: 가중치의 0번째 차원을 분할 (즉, 출력 차원. PyTorch Linear의 가중치 형태는 `[output, input]`이기 때문)

#### weight_loader 해석

`weight_loader`는 모델 로딩 시 호출되며, HuggingFace의 전체 가중치에서 현재 GPU에 해당하는 분할을 추출하는 역할을 합니다.

```python
shard_size = param_data.size(self.tp_dim)   # 현재 GPU의 분할 크기 = output_size / tp_size
start_idx = self.tp_rank * shard_size        # 시작 인덱스 = rank × 분할 크기
loaded_weight = loaded_weight.narrow(self.tp_dim, start_idx, shard_size)
```

`narrow`는 PyTorch의 슬라이싱 연산으로, 특정 차원을 따라 `loaded_weight[start_idx:start_idx+shard_size]`와 유사하게 동작합니다.

### 2.4 순전파

```python
def forward(self, x):
    return F.linear(x, self.weight, self.bias)
```

열 병렬의 순전파는 표준 행렬 곱셈입니다. **통신이 필요하지 않습니다.** 통신은 이후의 RowParallelLinear에서 발생합니다.

### 2.5 Transformer에서의 열 병렬 적용

Transformer에서 아래와 같은 레이어들이 열 병렬을 사용합니다.

- **Q/K/V 프로젝션** (`QKVParallelLinear`): 각 GPU가 일부 어텐션 헤드의 Q/K/V를 담당
- **FFN의 첫 번째 선형 레이어** (gate_proj, up_proj): 각 GPU가 일부 중간 차원을 담당
- **LM Head** (어휘 사전 매핑): 각 GPU가 어휘 사전의 일부를 담당

## 3. 행 병렬 (RowParallelLinear)

### 3.1 수학적 원리

가중치 행렬 \( W \in \mathbb{R}^{K \times N} \)을 **행(입력 차원) 기준**으로 분할합니다.

\[
W = \begin{bmatrix} W_0 \\ W_1 \\ \vdots \\ W_{N_{\text{tp}}-1} \end{bmatrix}, \quad W_i \in \mathbb{R}^{(K/N_{\text{tp}}) \times N}
\]

입력 \( X \)도 **이에 대응하여 분할**됩니다. (보통 이전 ColumnParallelLinear의 분할 출력)

\[
X = [X_0, X_1, \ldots, X_{N_{\text{tp}}-1}], \quad X_i \in \mathbb{R}^{M \times (K/N_{\text{tp}})}
\]

각 GPU는 국소 결과를 계산합니다.

\[
Y_i = X_i \cdot W_i, \quad Y_i \in \mathbb{R}^{M \times N}
\]

**핵심**: 각 \( Y_i \)의 형태는 \( [M \times N] \) (완전한 출력 형태)이지만, **부분 합**에 불과합니다. 완전한 출력을 얻으려면 다음이 필요합니다.

\[
Y = \sum_{i=0}^{N_{\text{tp}}-1} Y_i = X_0 W_0 + X_1 W_1 + \cdots
\]

이것이 바로 **AllReduce** 연산입니다. 모든 GPU의 부분 합을 하나로 모읍니다.

### 3.2 행 병렬에 AllReduce가 필요한 이유

행렬 곱셈의 블록 형태를 다시 살펴봅시다.

\[
Y = X \cdot W = [X_0, X_1] \cdot \begin{bmatrix} W_0 \\ W_1 \end{bmatrix} = X_0 W_0 + X_1 W_1
\]

각 GPU는 \( X_i W_i \)만 계산했으며, 이는 최종 결과의 일부입니다. 올바른 출력을 얻으려면 AllReduce(sum)를 통해 모든 GPU의 결과를 더해야 합니다.

### 3.3 nano-vllm 구현

```python
class RowParallelLinear(LinearBase):
    def __init__(self, input_size, output_size, bias=False):
        # input_size를 tp_size로 나눔: 각 GPU는 분할된 입력만 받음
        super().__init__(divide(input_size, tp_size), output_size, bias, tp_dim=1)

    def forward(self, x):
        # 1. 국소 행렬 곱셈
        y = F.linear(x, self.weight, self.bias if self.tp_rank == 0 else None)
        # 2. AllReduce 합계
        if self.tp_size > 1:
            dist.all_reduce(y)
        return y
```

#### 생성자 해석

```python
super().__init__(divide(input_size, tp_size), output_size, bias, tp_dim=1)
```

- `input_size / tp_size`: 각 GPU는 분할된 입력만 받음
- `output_size`: 완전한 형태를 유지 (각 GPU가 전체 형태의 부분 합을 출력)
- `tp_dim=1`: 가중치의 1번째 차원을 분할 (입력 차원)

#### 순전파 해석

```python
y = F.linear(x, self.weight, self.bias if self.tp_rank == 0 else None)
```

**Bias는 rank 0에서만 더합니다**: AllReduce가 모든 GPU의 결과를 합산하기 때문입니다. 만약 모든 GPU가 bias를 더하면 최종 결과에 bias가 \( N_{\text{tp}} \)번 더해지게 됩니다. 따라서 rank 0만 bias를 더하면 AllReduce 후 결과가 올바르게 됩니다.

```python
if self.tp_size > 1:
    dist.all_reduce(y)
```

`dist.all_reduce(y)`는 NCCL의 AllReduce 연산이며 기본적으로 합산입니다. 모든 GPU의 `y`가 다음과 같이 합산됩니다.

\[
y_{\text{final}} = y_0 + y_1 + \cdots + y_{N_{\text{tp}}-1}
\]

연산이 완료되면 **모든 GPU가 동일한 전체 출력**을 가지게 됩니다.

### 3.4 Transformer에서의 행 병렬 적용

- **Attention의 출력 프로젝션** (o_proj): 열 병렬로 나뉜 어텐션 출력 분할을 받아 행 병렬 + AllReduce로 전체 출력 복원
- **FFN의 두 번째 선형 레이어** (down_proj): 열 병렬로 나뉜 중간 결과 분할을 받아 행 병렬 + AllReduce로 전체 출력 복원

## 4. 열 병렬 + 행 병렬의 짝 패턴

### 4.1 짝을 이루는 원리

Transformer에서 열 병렬과 행 병렬은 항상 **쌍으로 나타납니다**.

```
Column Parallel(열 병렬)                Row Parallel(행 병렬)
(출력 차원 분할)                          (입력 차원 분할 + AllReduce)

    X [M×K]                              X₀ [M×K/2] (GPU 0)
    ↓                                    X₁ [M×K/2] (GPU 1)
    W₀ [K×N/2]  (GPU 0)                 ↓
    W₁ [K×N/2]  (GPU 1)                 W₀ [K/2×N]  (GPU 0)
    ↓                                    W₁ [K/2×N]  (GPU 1)
    Y₀ [M×N/2]  (GPU 0)                 ↓
    Y₁ [M×N/2]  (GPU 1)                 Y₀ [M×N]    (GPU 0)  ← 부분 합
                                         Y₁ [M×N]    (GPU 1)  ← 부분 합
    통신 불필요                            ↓ AllReduce
                                         Y [M×N]     (모든 GPU 동일)
```

### 4.2 Transformer에서의 적용

#### Attention 레이어

```
입력 X [M×D] (모든 GPU 동일)
    ↓
QKVParallelLinear (열 병렬)
    → Q₀, K₀, V₀ [M×D/TP]  (GPU 0)
    → Q₁, K₁, V₁ [M×D/TP]  (GPU 1)
    ↓
Attention 계산 (각 GPU가 자신의 헤드를 독립적으로 계산)
    → O₀ [M×D/TP]  (GPU 0)
    → O₁ [M×D/TP]  (GPU 1)
    ↓
o_proj (행 병렬 + AllReduce)
    → Y [M×D] (모든 GPU 동일)
```

#### FFN 레이어

```
입력 X [M×D] (모든 GPU 동일)
    ↓
gate_proj, up_proj (열 병렬 / MergedColumnParallelLinear)
    → gate₀, up₀ [M×D_ff/TP]  (GPU 0)
    → gate₁, up₁ [M×D_ff/TP]  (GPU 1)
    ↓
활성화 함수 + 요소별 곱셈 (각 GPU 독립)
    → H₀ [M×D_ff/TP]  (GPU 0)
    → H₁ [M×D_ff/TP]  (GPU 1)
    ↓
down_proj (행 병렬 + AllReduce)
    → Y [M×D] (모든 GPU 동일)
```

### 4.3 통신량 분석

Transformer 레이어 하나당 **2회의 AllReduce**가 필요합니다. (Attention의 o_proj에서 1회, FFN의 down_proj에서 1회)

단일 AllReduce의 통신량:
\[
\text{통신량} = 2 \times (N_{\text{tp}} - 1) / N_{\text{tp}} \times M \times D \times \text{sizeof(dtype)}
\]

M=1 (Decode 단일 토큰), D=4096, FP16, TP=4일 때:
\[
= 2 \times 3/4 \times 1 \times 4096 \times 2 = 12 \text{ KB}
\]

**매우 작습니다!** 이것이 TP를 동일 노드 내(NVLink)에서 사용할 때 효율이 극히 높은 이유입니다.

M=1000 (Prefill 긴 시퀀스)일 때:
\[
= 2 \times 3/4 \times 1000 \times 4096 \times 2 = 12 \text{ MB}
\]

여전히 수용 가능한 수준입니다. (NVLink 단방향 대역폭 300+ GB/s에서 12 MB 전송은 약 40 μs 소요)

## 5. QKVParallelLinear의 특수 처리

### 5.1 특수 처리가 필요한 이유

표준 Transformer에서 Q, K, V는 각각 세 개의 독립적인 선형 레이어로 생성됩니다. 하지만 실제 구현에서는 커널 런치 오버헤드를 줄이기 위해 Q, K, V의 가중치를 **하나의 큰 행렬로 병합**하여 한 번의 행렬 곱셈으로 Q, K, V를 동시에 얻습니다.

GQA(Grouped Query Attention)를 사용할 때 Q의 헤드 수(예: 32)와 KV의 헤드 수(예: 4)가 다르면, 가중치 행렬의 Q 부분과 KV 부분의 크기가 달라집니다. 텐서 병렬 분할까지 더해지면 가중치 로딩 시 특별한 분할 로직이 필요합니다.

### 5.2 병합된 가중치의 구조

```
QKV 병합 가중치 W_qkv: [hidden_size, (num_heads + 2×num_kv_heads) × head_dim]

다음과 같이 분해:
├── Q 부분: [hidden_size, num_heads × head_dim]
├── K 부분: [hidden_size, num_kv_heads × head_dim]
└── V 부분: [hidden_size, num_kv_heads × head_dim]
```

### 5.3 nano-vllm 구현

```python
class QKVParallelLinear(ColumnParallelLinear):
    def __init__(self, hidden_size, head_size, total_num_heads,
                 total_num_kv_heads=None):
        total_num_kv_heads = total_num_kv_heads or total_num_heads
        self.head_size = head_size
        self.num_heads = divide(total_num_heads, tp_size)
        self.num_kv_heads = divide(total_num_kv_heads, tp_size)

        # 총 출력 크기 = (Q 헤드 수 + 2×KV 헤드 수) × 헤드 차원
        output_size = (total_num_heads + 2 * total_num_kv_heads) * head_size
        super().__init__(hidden_size, output_size)
```

#### 생성자 해석

```python
self.num_heads = divide(total_num_heads, tp_size)      # GPU당 Q 헤드 수
self.num_kv_heads = divide(total_num_kv_heads, tp_size) # GPU당 KV 헤드 수
```

Qwen3-7B 예시 (total_num_heads=32, total_num_kv_heads=4, tp_size=2):
- GPU당 Q 헤드 수: 32 / 2 = 16
- GPU당 KV 헤드 수: 4 / 2 = 2

### 5.4 weight_loader의 특수 로직

QKVParallelLinear의 `weight_loader`는 Q와 KV의 가중치 분할을 구분하여 처리해야 합니다.

```python
def weight_loader(self, param, loaded_weight, weight_name):
    if "q_proj" in weight_name:
        # Q 가중치는 num_heads 기준으로 분할
        shard_size = self.num_heads * self.head_size
        start_idx = self.tp_rank * shard_size
        offset = 0
    elif "k_proj" in weight_name:
        # K 가중치는 num_kv_heads 기준으로 분할
        shard_size = self.num_kv_heads * self.head_size
        start_idx = self.tp_rank * shard_size
        offset = self.num_heads * self.head_size  # Q 뒤
    elif "v_proj" in weight_name:
        # V 가중치는 num_kv_heads 기준으로 분할
        shard_size = self.num_kv_heads * self.head_size
        start_idx = self.tp_rank * shard_size
        offset = (self.num_heads + self.num_kv_heads) * self.head_size  # Q+K 뒤

    loaded_weight = loaded_weight.narrow(0, start_idx, shard_size)
    param_data[offset:offset+shard_size].copy_(loaded_weight)
```

각 GPU의 가중치 배치:

```
GPU의 QKV 가중치: [Q_shard | K_shard | V_shard]
                  ↑         ↑         ↑
           num_heads×D  num_kv×D  num_kv×D
           (16×128)     (2×128)   (2×128)
```

### 5.5 순전파 후 분할

순전파로 얻은 QKV 연결 결과를 Q, K, V 세 개의 텐서로 분할해야 합니다.

```python
# attention.py
qkv = self.qkv_proj(x)  # [M, (num_heads + 2×num_kv_heads) × head_dim]
q, k, v = qkv.split([
    self.num_heads * self.head_dim,
    self.num_kv_heads * self.head_dim,
    self.num_kv_heads * self.head_dim
], dim=-1)
```

## 6. MergedColumnParallelLinear

### 6.1 설계 동기

Transformer FFN에는 보통 두 개의 열 병렬 선형 레이어를 동시에 계산해야 합니다. (예: Qwen3의 `gate_proj`와 `up_proj`). 커널 런치 오버헤드를 줄이기 위해 이들을 하나의 큰 행렬 곱셈으로 병합합니다.

```
개별 계산 (2회 커널 런치):
  gate = x @ W_gate    [M×D] × [D×D_ff/TP]
  up   = x @ W_up      [M×D] × [D×D_ff/TP]

병합 계산 (1회 커널 런치):
  gate_up = x @ [W_gate, W_up]   [M×D] × [D×2D_ff/TP]
```

### 6.2 구현

```python
class MergedColumnParallelLinear(ColumnParallelLinear):
    def __init__(self, input_size, output_sizes, bias=False):
        # output_sizes는 여러 열 병렬 레이어의 출력 크기 리스트
        # 예: [intermediate_size, intermediate_size]
        self.output_sizes = output_sizes
        total_output_size = sum(output_sizes)
        super().__init__(input_size, total_output_size, bias)
```

### 6.3 weight_loader의 특수 로직

로딩 시 각 하위 레이어의 가중치를 병합 행렬의 올바른 위치에 배치해야 합니다.

```python
def weight_loader(self, param, loaded_weight, weight_name):
    # gate_proj인지 up_proj인지 확인
    if "gate_proj" in weight_name:
        idx = 0
    elif "up_proj" in weight_name:
        idx = 1

    # 병합 가중치에서의 오프셋 계산
    shard_size = divide(self.output_sizes[idx], tp_size)
    offset = sum(divide(s, tp_size) for s in self.output_sizes[:idx])
    start_idx = self.tp_rank * shard_size

    loaded_weight = loaded_weight.narrow(0, start_idx, shard_size)
    param_data[offset:offset+shard_size].copy_(loaded_weight)
```

병합 후 각 GPU의 가중치 배치:

```
[gate_shard | up_shard]
 D_ff/TP      D_ff/TP
```

순전파 후 `split`으로 다시 나눕니다.

```python
gate, up = merged_output.split(
    [intermediate_size // tp_size, intermediate_size // tp_size], dim=-1
)
output = gate * F.silu(up)  # SwiGLU 활성화
```

## 7. 어휘 병렬 (VocabParallelEmbedding)

### 7.1 문제

Embedding 레이어는 토큰 ID를 임베딩 벡터로 매핑합니다. 어휘 크기는 보통 매우 크므로(예: 152,064) 임베딩 행렬이 많은 메모리를 차지합니다.

표준 Embedding:
```
W_embed: [vocab_size, hidden_size] = [152064, 4096]
크기 = 152064 × 4096 × 2 bytes ≈ 1.2 GB
```

### 7.2 병렬 전략

어휘 사전을 **행 기준으로 분할**하여 여러 GPU에 나눕니다.

```
GPU 0: W_embed[0:76032, :]           ← 토큰 ID 0~76031 담당
GPU 1: W_embed[76032:152064, :]      ← 토큰 ID 76032~152063 담당
```

각 GPU는 자신이 담당하는 범위의 토큰만 조회하고, 범위 밖의 토큰에 대해서는 0 벡터를 반환합니다.

```python
# tp_rank=0, vocab_start=0, vocab_end=76032 가정
mask = (input_ids >= vocab_start) & (input_ids < vocab_end)
local_ids = input_ids - vocab_start   # 로컬 인덱스로 변환
local_ids[~mask] = 0                   # 범위 밖은 0으로

embeddings = F.embedding(local_ids, self.weight)  # 로컬 조회
embeddings[~mask] = 0                              # 범위 밖은 0으로
```

그런 다음 **AllReduce(sum)**으로 취합합니다.

```python
if self.tp_size > 1:
    dist.all_reduce(embeddings)
```

각 토큰은 오직 하나의 GPU에서만 0이 아닌 임베딩을 가지므로, AllReduce 후에는 모든 GPU가 완전하고 정확한 임베딩을 갖게 됩니다.

### 7.3 LM Head의 어휘 병렬

LM Head는 Embedding의 역연산으로(보통 가중치 공유), 은닉 상태를 어휘 크기의 logits으로 매핑합니다.

```
logits = hidden_states @ W_embed.T    [M×D] × [D×vocab_size] = [M×vocab_size]
```

텐서 병렬에서 각 GPU는 어휘의 일부에 대한 logits을 계산합니다.

```python
local_logits = F.linear(hidden_states, self.weight)  # [M, vocab_size/tp_size]
```

그런 다음 **AllGather**로 연결합니다.

```python
if self.tp_size > 1:
    all_logits = [torch.empty_like(local_logits) for _ in range(tp_size)]
    dist.all_gather(all_logits, local_logits)
    logits = torch.cat(all_logits, dim=-1)  # [M, vocab_size]
```

AllGather 후에는 모든 GPU가 전체 logits을 가지게 되어 샘플링을 수행할 수 있습니다.

## 8. NCCL 통신 초기화

### 8.1 프로세스 그룹 초기화

```python
# model_runner.py
dist.init_process_group(
    backend="nccl",                  # NCCL 백엔드 사용
    init_method="tcp://localhost:2333",  # 랑데부 주소
    world_size=self.world_size,      # 전체 GPU 수
    rank=rank                        # 현재 프로세스 번호
)
```

**NCCL (NVIDIA Collective Communication Library)** 은 NVIDIA가 제공하는 GPU 간 고성능 집합 통신 라이브러리로, AllReduce, AllGather, ReduceScatter 등의 연산을 지원합니다.

**init_method**: 프로세스 간 랑데부(만남점)를 지정합니다. 모든 프로세스는 이 주소를 통해 서로를 발견합니다. `tcp://localhost:2333`은 TCP 방식을 사용하여 로컬 머신의 2333 포트에서 연결을 수립한다는 의미입니다.

### 8.2 다중 프로세스 시작

nano-vllm은 Python의 `multiprocessing`을 사용하여 여러 프로세스를 시작합니다.

```python
# llm_engine.py
if config.tensor_parallel_size > 1:
    processes = []
    event = Event()
    for rank in range(1, config.tensor_parallel_size):
        p = Process(target=ModelRunner, args=(config, rank, event))
        p.start()
        processes.append(p)
    # rank 0은 메인 프로세스에서 실행
    self.model_runner = ModelRunner(config, rank=0, event=event)
```

- Rank 0은 메인 프로세스에서 실행되며 스케줄링과 샘플링을 담당합니다.
- Rank 1~N은 서브 프로세스에서 실행되며, ModelRunner 생성 후 `loop()`에 진입하여 명령을 대기합니다.

### 8.3 NCCL 통신의 하드웨어 기반

| 연결 방식 | 대역폭 | 지연 시간 | 적용 시나리오 |
|---------|------|--------|------------|
| NVLink (A100) | 600 GB/s | ~1 μs | 동일 노드 GPU 간 |
| NVLink (H100) | 900 GB/s | ~1 μs | 동일 노드 GPU 간 |
| PCIe 4.0 x16 | 32 GB/s | ~2 μs | 동일 노드 CPU-GPU |
| InfiniBand HDR | 200 Gb/s (25 GB/s) | ~1-3 μs | 노드 간 |
| Ethernet 100G | 12.5 GB/s | ~5-10 μs | 노드 간 |

nano-vllm은 단일 노드 다중 GPU(NVLink 경유)만 지원하므로 AllReduce 통신 지연이 매우 낮습니다.

### 8.4 AllReduce 구현 원리

NCCL의 AllReduce는 **Ring AllReduce** 알고리즘을 사용합니다.

```
4개의 GPU, 각각 데이터 [A₀, A₁, A₂, A₃] 보유

1단계: Reduce-Scatter
  GPU 0 → GPU 1 → GPU 2 → GPU 3 → GPU 0 (링 전달)
  3단계 후, 각 GPU는 전체 합의 1/4씩 보유

2단계: All-Gather
  GPU 0 → GPU 1 → GPU 2 → GPU 3 → GPU 0 (링 전달)
  3단계 후, 각 GPU는 전체 합을 보유

총 통신량: 2 × (N-1)/N × 데이터량 ≈ 2 × 데이터량 (N이 클 때)
```

Ring AllReduce의 통신량은 GPU 수와 **거의 무관**합니다(N이 커질수록 상수에 수렴). 따라서 텐서 병렬의 통신 오버헤드는 잘 확장됩니다.

## 9. 완전한 텐서 병렬 데이터 흐름 예시

### 9.1 단일 Transformer 레이어의 데이터 흐름 (TP=2)

```
입력 X: [M×D] (두 GPU 동일)
│
├── GPU 0                              ├── GPU 1
│   QKV_proj (ColumnParallel)          │   QKV_proj (ColumnParallel)
│   W_q₀: [D, D/2]                    │   W_q₁: [D, D/2]
│   W_k₀: [D, D_kv/2]                 │   W_k₁: [D, D_kv/2]
│   W_v₀: [D, D_kv/2]                 │   W_v₁: [D, D_kv/2]
│   → Q₀, K₀, V₀                      │   → Q₁, K₁, V₁
│                                       │
│   Attention(Q₀, K₀, V₀)             │   Attention(Q₁, K₁, V₁)
│   → O₀: [M, D/2]                    │   → O₁: [M, D/2]
│                                       │
│   o_proj (RowParallel)               │   o_proj (RowParallel)
│   W_o₀: [D/2, D]                    │   W_o₁: [D/2, D]
│   → Y₀: [M, D] (부분 합)             │   → Y₁: [M, D] (부분 합)
│                                       │
│        ←──── AllReduce (sum) ────→
│   Y_attn: [M, D] (완전)              │   Y_attn: [M, D] (완전)
│                                       │
│   + Residual + LayerNorm              │   + Residual + LayerNorm
│   → X': [M, D]                       │   → X': [M, D]
│                                       │
│   gate_up_proj (MergedColumnParallel) │   gate_up_proj (MergedColumnParallel)
│   W_gate₀: [D, D_ff/2]              │   W_gate₁: [D, D_ff/2]
│   W_up₀: [D, D_ff/2]                │   W_up₁: [D, D_ff/2]
│   → gate₀, up₀                       │   → gate₁, up₁
│   → SiLU(gate₀) × up₀               │   → SiLU(gate₁) × up₁
│   → H₀: [M, D_ff/2]                │   → H₁: [M, D_ff/2]
│                                       │
│   down_proj (RowParallel)            │   down_proj (RowParallel)
│   W_down₀: [D_ff/2, D]              │   W_down₁: [D_ff/2, D]
│   → Z₀: [M, D] (부분 합)             │   → Z₁: [M, D] (부분 합)
│                                       │
│        ←──── AllReduce (sum) ────→
│   Y_ffn: [M, D] (완전)               │   Y_ffn: [M, D] (완전)
│                                       │
│   + Residual                          │   + Residual
│   → 다음 레이어의 입력                 │   → 다음 레이어의 입력
```

**핵심 관찰**: 레이어당 단 **2회의 AllReduce**만 필요하며, 다른 계산은 완전히 병렬로 수행되어 통신이 필요 없습니다.

## 10. 면접 빈출 핵심

### Q1: 텐서 병렬에서 ColumnParallelLinear와 RowParallelLinear의 차이를 설명하세요.

**참고 답안**:

| 차원 | ColumnParallelLinear | RowParallelLinear |
|------|---------------------|-------------------|
| 분할 방식 | 가중치를 열(출력) 기준으로 분할 | 가중치를 행(입력) 기준으로 분할 |
| 입력 요건 | 전체 입력 (모든 GPU 동일) | 분할 입력 (GPU마다 다름) |
| 출력 형태 | 분할 출력 (각 GPU가 일부 열만 보유) | 부분 합 (각 GPU가 완전한 형태지만 불완전한 값) |
| 통신 필요 여부 | 불필요 | AllReduce (sum) 필요 |
| 사용 위치 | Q/K/V 프로젝션, FFN gate/up | Attention o_proj, FFN down_proj |

둘은 항상 쌍으로 사용됩니다. ColumnParallel의 분할 출력이 직접 RowParallel의 분할 입력이 되며, RowParallel이 AllReduce를 통해 전체 출력을 복원합니다.

### Q2: RowParallelLinear에서 bias를 rank 0에서만 더하는 이유는 무엇인가요?

**참고 답안**:

AllReduce는 합산 연산이기 때문입니다. 각 GPU가 bias를 더하면 AllReduce 후 bias가 tp_size만큼 중복되어 더해집니다. 올바른 방법은 하나의 GPU(보통 rank 0)에서만 bias를 더하는 것입니다. AllReduce 합산 후 결과에는 자연스럽게 bias가 한 번만 포함됩니다.

수학적 표현:
- 오류: \( \sum_i (X_i W_i + b) = XW + N_{\text{tp}} \cdot b \)
- 정확: \( \sum_i X_i W_i + b = XW + b \) (rank 0만 b를 더함)

### Q3: 텐서 병렬은 레이어당 몇 번의 통신이 필요하며 통신량은 얼마인가요?

**참고 답안**:

Transformer 레이어 하나당 2회의 AllReduce가 필요합니다.
1. Attention의 o_proj 출력
2. FFN의 down_proj 출력

Ring AllReduce 통신량 = \( 2 \times (N_{\text{tp}} - 1) / N_{\text{tp}} \times \text{데이터량} \)

Decode 단계 (단일 토큰): 통신량 ≈ 2 × 2 × D × 2 bytes. D=4096일 때 약 32 KB/레이어. 총 32 레이어 ≈ 1 MB. NVLink(600 GB/s)에서는 약 2 μs로, 계산 시간보다 훨씬 짧습니다.

### Q4: TP, PP, DP 세 가지 병렬 전략의 장단점을 비교하세요.

**참고 답안**:

| | 텐서 병렬(TP) | 파이프라인 병렬(PP) | 데이터 병렬(DP) |
|--|------------|-----------------|--------------|
| 분할 차원 | 가중치 행렬 | 레이어 | 배치 |
| 통신 방식 | AllReduce | 점대점 | AllReduce 그래디언트 |
| 통신 빈도 | 레이어당 2회 | 마이크로 배치당 1회 | 스텝당 1회 |
| 지연 시간 | 낮음 (병렬 계산) | 중간 (직렬 파이프라인) | 감소하지 않음 |
| 처리량 | 선형에 가까운 확장 | 거품 현상 있음 | 선형 확장 |
| 적용 시나리오 | 동일 노드 추론 | 노드 간 추론 | 학습 |
| 구현 복잡도 | 중간 | 높음 | 낮음 |

추론 시나리오에서는 일반적으로 TP를 우선 선택합니다(지연 시간 최저). GPU 수가 단일 노드 한계를 초과하면 PP와 결합하여 노드 간 병렬 처리합니다. DP는 주로 학습에 사용됩니다.

### Q5: GQA가 텐서 병렬에 미치는 영향은 무엇인가요?

**참고 답안**:

GQA(Grouped Query Attention)에서는 Q의 헤드 수가 KV의 헤드 수보다 훨씬 많습니다(예: Q=32, KV=4). 텐서 병렬에서:
- Q는 `total_num_heads / tp_size`로 분할
- KV는 `total_num_kv_heads / tp_size`로 분할

따라서 `total_num_kv_heads`가 `tp_size`로 나누어 떨어져야 합니다. 예를 들어 KV=4일 때 tp_size는 1, 2, 4만 가능합니다. tp_size=8이면 4개의 KV 헤드를 나눌 수 없습니다.

`QKVParallelLinear`의 `weight_loader`는 Q와 KV의 분할 오프셋을 별도로 처리하여 가중치를 올바르게 로딩합니다.

### Q6: nano-vllm은 어떤 통신 백엔드를 사용하며, 왜 NCCL을 선택했나요?

**참고 답안**:

nano-vllm은 NCCL(NVIDIA Collective Communication Library)을 통신 백엔드로 사용합니다. 선택 이유:
1. **NVIDIA GPU에 최적화**: NVLink, NVSwitch 등 하드웨어 특성을 자동 활용
2. **모든 집합 통신 원어 지원**: AllReduce, AllGather, ReduceScatter 등
3. **GPU Direct**: CPU를 거치지 않고 GPU 간 직접 데이터 전송
4. **Ring 및 Tree 알고리즘 자동 적응**: 토폴로지와 데이터 양에 따라 최적 알고리즘 자동 선택
5. **PyTorch와 긴밀한 통합**: `torch.distributed`에서 NCCL 백엔드 기본 지원

### Q7: 모델 파라미터가 너무 커서 단일 노드에 수용할 수 없다면 어떻게 하나요?

**참고 답안**:

여러 병렬 전략을 결합해야 합니다.

1. **TP + PP**: 노드 내에서는 TP(NVLink 활용), 노드 간에는 PP(InfiniBand 활용)
2. **TP + PP + DP**: 학습 시나리오에서는 DP를 추가하여 처리량 향상
3. **모델 양자화**: 가중치를 FP16에서 INT8/INT4로 양자화하여 메모리 및 통신량 감소
4. **오프로딩**: 비활성 레이어 파라미터를 CPU 메모리로 임시 이동

nano-vllm은 단일 노드 TP만 지원하며 PP나 노드 간 병렬은 지원하지 않습니다. vLLM과 DeepSpeed Inference는 더 복잡한 병렬 조합을 지원합니다.

## 11. 요약

| 핵심 | 내용 |
|------|------|
| **TP가 필요한 이유** | 단일 GPU 메모리/연산 능력 부족, TP는 선형 확장 가능 |
| **열 병렬** | 출력 차원 기준 가중치 분할, 통신 불필요, 출력은 분할 형태 |
| **행 병렬** | 입력 차원 기준 가중치 분할, 출력은 부분 합, AllReduce 필요 |
| **짝 패턴** | Column → Row + AllReduce, 레이어당 2회 통신 |
| **QKVParallelLinear** | Q와 KV 헤드 수가 다르므로 특수 분할 및 로딩 로직 필요 |
| **MergedColumnParallel** | gate_proj + up_proj 병합으로 커널 런치 감소 |
| **어휘 병렬** | Embedding은 어휘 분할 + AllReduce, LM Head는 어휘 분할 + AllGather |
| **NCCL** | GPU 간 고성능 통신, Ring AllReduce 통신량은 GPU 수와 거의 무관 |

**핵심 암기구**:

> 열 병렬은 **출력을 나누고**, 행 병렬은 **입력을 나누며**;  
> Column은 **통신 없고**, Row는 **AllReduce**;  
> 짝지어 **하나는 입력, 하나는 출력**, 레이어당 단 **두 번 통신**;  
> QKV **헤드 수 달라 따로 나누고**, Merged는 **합쳐 런치를 절약**;  
> NCCL **NVLink로 빠르게**, TP 추론의 **첫 번째 선택**.

**다음 강의 예고**: 텐서 병렬을 마스터했으니, 이제 **CUDA Graph 최적화**로 들어가 Decode 단계의 커널 런치 오버헤드를 어떻게 제거하는지, 그리고 nano-vllm의 CUDAGraphRunner 구현을 이해해 보겠습니다.
