# 제20강: 전체 프로젝트 정리

초보자를 위한 설명: 본 강의는 nano-vllm 시리즈 강의의 **최종 정리**입니다. 모든 모듈을 연결하여 사용자 입력부터 모델 출력까지의 완전한 호출 체인을 정리하고, 아키텍처 설계 사상을 요약하며, vLLM과의 차이 및 확장 가능한 방향을 분석하고, 마지막으로 면접 필수 암기 포인트 목록을 제시합니다.

## 2. 완전한 호출 체인 정리

### 2.1 초기화 단계

```
LLMEngine.__init__(model_path)
    │
    ├── Config(model_path)
    │     └── config.json에서 모델 하이퍼파라미터 읽기
    │         (hidden_size, num_layers, num_heads, vocab_size, ...)
    │
    ├── 다중 프로세스 기동 (tensor_parallel_size > 1)
    │     └── for rank in 1..TP:
    │           Process(target=ModelRunner, args=(config, rank))
    │
    ├── ModelRunner(config, rank=0)
    │     ├── 모델 객체 생성 (Qwen2ForCausalLM / LlamaForCausalLM)
    │     │     └── 빈 파라미터 초기화 (nn.Parameter)
    │     │
    │     ├── load_model(model, path)
    │     │     ├── *.safetensors 파일 순회
    │     │     ├── packed_modules_mapping으로 QKV / gate_up 병합 처리
    │     │     └── weight_loader가 가중치를 해당 파라미터로 복사
    │     │
    │     ├── KV Cache 할당
    │     │     ├── 가용 GPU 메모리 계산
    │     │     ├── 수용 가능한 KV 블록 수 계산
    │     │     └── k_cache / v_cache 텐서 할당
    │     │
    │     └── capture_cudagraph() (enforce_eager=False 시)
    │           ├── graph_bs = [1,2,4,8,16,32,...] 정의
    │           ├── graph_vars 사전 할당 (최대 배치 버퍼)
    │           └── for bs in reversed(graph_bs):
    │                 warmup → capture → graph 저장
    │
    ├── AutoTokenizer.from_pretrained(model_path)
    │
    └── Scheduler(config)
          └── BlockManager(num_blocks, block_size)
```

### 2.2 추론 단계 (단일 요청 예시)

```
generate(["Hello world"], [SamplingParams()])
    │
    ├── add_request("Hello world", sp)
    │     ├── tokenizer.encode("Hello world") → [9707, 1879]
    │     ├── Sequence([9707, 1879], sp)
    │     └── scheduler.add(seq) → waiting 큐
    │
    └── while not is_finished():
          │
          ├── step() #1: Prefill
          │     ├── scheduler.schedule()
          │     │     ├── waiting에서 seq 꺼냄
          │     │     ├── block_manager.allocate(seq) → KV 블록 할당
          │     │     ├── slot_mapping 준비 (token → KV slot)
          │     │     └── 반환 (seqs=[seq], is_prefill=True)
          │     │
          │     ├── model_runner.call("run", seqs, is_prefill=True)
          │     │     ├── input_ids = [9707, 1879]    (2 tokens)
          │     │     ├── positions = [0, 1]
          │     │     │
          │     │     ├── run_model(input_ids, positions, is_prefill=True)
          │     │     │     │  → eager 경로 (CUDA Graph 미사용)
          │     │     │     │
          │     │     │     ├── model(input_ids, positions)
          │     │     │     │     ├── embedding(input_ids) → [2, hidden_size]
          │     │     │     │     ├── for layer in layers:
          │     │     │     │     │     ├── rmsnorm(x)
          │     │     │     │     │     ├── qkv_proj(x) → Q, K, V
          │     │     │     │     │     ├── rotary_emb(Q, K, positions)  # RoPE
          │     │     │     │     │     ├── store_kvcache(K, V, ...)      # Triton kernel
          │     │     │     │     │     ├── flash_attn_varlen_func(Q, K, V)  # Prefill attention
          │     │     │     │     │     ├── o_proj(attn_output)
          │     │     │     │     │     ├── rmsnorm(x)
          │     │     │     │     │     └── gate_up_proj → SiLU → down_proj  # FFN
          │     │     │     │     ├── final_rmsnorm(x)
          │     │     │     │     └── hidden_states 반환  # [2, hidden_size]
          │     │     │     │
          │     │     │     └── compute_logits(hidden_states[-1:])
          │     │     │           └── lm_head(hidden_states) → logits [1, vocab_size]
          │     │     │
          │     │     └── sampler(logits, temperature)
          │     │           ├── logits / temperature
          │     │           ├── softmax → probs
          │     │           ├── Gumbel-max → token_id = 2845
          │     │           └── [2845] 반환
          │     │
          │     └── scheduler.postprocess([seq], [2845])
          │           ├── seq.completion_token_ids.append(2845)
          │           ├── block_manager.append_slot(seq) → 새 슬롯 할당
          │           └── 정지 조건 확인 → 미완료, 계속
          │
          ├── step() #2: Decode (CUDA Graph)
          │     ├── scheduler.schedule()
          │     │     └── 반환 (seqs=[seq], is_prefill=False)
          │     │
          │     ├── model_runner.call("run", seqs, is_prefill=False)
          │     │     ├── input_ids = [2845]    (1 token)
          │     │     ├── positions = [2]
          │     │     │
          │     │     ├── run_model(input_ids, positions, is_prefill=False)
          │     │     │     │  → CUDA Graph 경로
          │     │     │     ├── graph = graphs[1]  (bs=1 그래프)
          │     │     │     ├── graph_vars["input_ids"][0] = 2845
          │     │     │     ├── graph_vars["positions"][0] = 2
          │     │     │     ├── graph_vars["slot_mapping"].fill_(-1)
          │     │     │     ├── graph_vars["slot_mapping"][0] = real_slot
          │     │     │     ├── graph.replay()  → GPU가 순전파 전체 실행
          │     │     │     └── compute_logits(graph_vars["outputs"][:1])
          │     │     │
          │     │     └── sampler(logits, temperature) → token_id = 5678
          │     │
          │     └── scheduler.postprocess([seq], [5678])
          │
          ├── step() #3, #4, ... : 계속 Decode
          │
          └── step() #N: seq.is_finished = True
                └── scheduler.free_blocks(seq)  # KV 블록 해제
```

## 3. 아키텍처 설계 요약

### 3.1 모듈 역할 일람

| 모듈 | 파일 | 핵심 역할 | 다른 모듈과의 관계 |
|------|------|---------|-----------------|
| **Config** | `config.py` | 모든 설정 파라미터 집약 | 모든 모듈이 읽음 |
| **LLMEngine** | `llm_engine.py` | 최상위 진입점, 모든 모듈 연결 | Scheduler, ModelRunner, Tokenizer 보유 |
| **Scheduler** | `scheduler.py` | 요청 스케줄링, 생애주기 관리 | BlockManager 보유 |
| **BlockManager** | `block_manager.py` | KV Cache 물리 블록 할당/해제 | Scheduler가 호출 |
| **ModelRunner** | `model_runner.py` | 모델 순전파 실행, CUDA Graph 관리 | Model, Sampler 보유 |
| **Model** | `model/qwen2.py` 등 | Transformer 순전파 계산 | Attention, FFN 호출 |
| **Attention** | `model/attention.py` | 어텐션 계산 + KV Cache 읽기/쓰기 | FlashAttention, Triton 커널 사용 |
| **Sampler** | `sampler.py` | logits → token ID | ModelRunner가 호출 |
| **Loader** | `loader.py` | 가중치 로딩 및 매핑 | ModelRunner가 호출 |

### 3.2 설계 원칙

nano-vllm의 설계는 다음 원칙을 따릅니다.

**1. 최소화하되 완결성 있게**
- 핵심 추론 경로만 구현하며, 학습, 미세 조정, API 서비스 등의 부가 기능은 포함하지 않음.
- 그러나 핵심 경로상의 주요 최적화(KV Cache 페이징, CUDA Graph, FlashAttention, 연속 배치)는 하나도 빠짐없이 포함.

**2. 계층 구조가 명확함**
```
사용자 인터페이스 계층:  LLMEngine (generate / add_request / step)
스케줄링 관리 계층:      Scheduler + BlockManager
계산 실행 계층:          ModelRunner + Model + Attention + Sampler
하위 최적화 계층:        CUDA Graph + Triton Kernel + FlashAttention
```
각 계층은 명확한 인터페이스를 통해 통신하며, 역할 경계가 분명합니다.

**3. 성능 우선**
- decode 경로는 기본적으로 CUDA Graph 사용 (단, `enforce_eager` 디버그 옵션 유지).
- Sampler는 Gumbel-max + `torch.compile` 사용.
- Attention은 FlashAttention 라이브러리 사용.
- QKV/gate_up을 packed modules로 병합하여 커널 수 감소.

**4. 가독성 우선**
- 총 코드량 약 3000줄로 제한.
- 핵심 데이터 구조(Sequence, Block)가 단순하고 직관적임.
- 과도한 추상화나 디자인 패턴을 사용하지 않음.

### 3.3 각 모듈 협력 관계도

```
                    LLMEngine
                   /    |    \
                  /     |     \
           Tokenizer  Scheduler  ModelRunner
                        |         /    |    \
                   BlockManager  Model Sampler Loader
                        |         |
                     KV Cache   Attention
                                  |
                       FlashAttention + Triton Kernel
```

**데이터 흐름**: 사용자 텍스트 → Tokenizer → Scheduler(요청 관리) → ModelRunner(순전파 실행) → Sampler(샘플링) → Scheduler(후처리) → Tokenizer → 사용자 텍스트

**제어 흐름**: LLMEngine.step() → Scheduler.schedule() → ModelRunner.run() → Scheduler.postprocess()

**자원 흐름**: BlockManager가 KV 블록 할당 → Attention이 KV Cache에 기록 → BlockManager가 KV 블록 해제

### 3.4 코드 라인 수와 모듈 복잡도 (`nano-vllm-main` 기준 대략적 통계)

교육용 저장소의 **Python 총 라인 수는 약 천여 줄 수준**입니다(버전에 따라 약간 변동 가능). 면접에서 "프로젝트 규모"를 질문받을 때 이 점을 들어 **작지만 완전하며 통독에 적합**하다고 답변할 수 있습니다. 아래 파일별 수량은 라인 수(공백 및 주석 포함)로, 복잡도 감을 위한 것입니다.

| 파일 (경로) | 약 라인 수 | 복잡도 감 |
|------------|----------|----------|
| `engine/model_runner.py` | ~250 | **높음**: 순전파 조합, CUDA Graph, `set_context`, 멀티프로세스 `call` |
| `models/qwen3.py` (또는 기타 모델) | ~200+ | **높음**: 전체 모델 구조, 레이어 적층 |
| `layers/linear.py` | ~150 | **중간-높음**: 텐서 병렬 분할, Packed Linear |
| `engine/block_manager.py` | ~110 | **중간**: 블록 할당, 프리픽스 캐싱 (활성화 시) |
| `engine/llm_engine.py` | ~90 | **중간**: 엔진 루프, `num_tokens` 처리량 부호화 |
| `engine/sequence.py` | ~80 | **중간**: 시퀀스 상태, 직렬화 |
| `layers/attention.py` | ~70 | **높음**: FlashAttention + Triton `store_kvcache` |
| `engine/scheduler.py` | ~70 | **중간**: prefill/decode 스케줄링 전략 |
| `utils/context.py` | ~30 | **낮음**: 전역 컨텍스트, 암시적 매개변수 전달 |
| `utils/loader.py` | ~30 | **중간**: safetensors + packed 가중치 매핑 |

**결론**: 복잡도는 **ModelRunner + Model + Attention + Linear**에 집중되어 있으며, 엔진 및 스케줄 코드는 분량이 적지만 **제어 흐름의 핵심**입니다. vLLM과 비교하면 nano-vllm은 **약 1%의 코드로 주요 경로상의 핵심 최적화 사상을 커버**하므로, 이력서 프로젝트로 원리를 명확히 설명한 후 산업용 프레임워크로의 확장성을 이야기하기에 적합합니다.

## 4. 핵심 기술 지식 포인트 회고

### 4.1 KV Cache와 PagedAttention

**문제**: 자기회귀 생성은 과거 Key/Value를 캐싱하여 중복 계산을 피해야 함. 그러나 시퀀스 길이가 서로 달라 연속 메모리 할당 시 단편화가 발생함.

**해결책**: 운영체제 가상 메모리 페이징에서 착안하여, KV Cache를 고정 크기의 **블록**(예: 16 토큰) 단위로 관리. 각 시퀀스는 필요할 때마다 블록을 할당받으며, 블록은 불연속적일 수 있음.

**핵심 구성 요소**:
- `BlockManager`: 유휴 블록 풀을 유지하며 블록을 할당/해제.
- `block_tables`: 시퀀스별 블록 번호 매핑 테이블.
- `slot_mapping`: 토큰 → 물리 슬롯 매핑.

### 4.2 연속 배치 (Continuous Batching)

**문제**: 전통적인 배치는 한 배치의 모든 요청이 완료될 때까지 기다려야 하므로, 먼저 끝난 시퀀스가 GPU 자원을 낭비함.

**해결책**: 매 스텝마다 새로운 요청을 추가하거나 완료된 요청을 제거할 수 있음. 서로 다른 시퀀스의 생애주기가 중첩될 수 있음.

**nano-vllm에서**:
- `Scheduler.schedule()`이 매 스텝 동적으로 계산에 참여할 시퀀스를 선택.
- 완료된 시퀀스는 즉시 KV 블록을 해제하여 새 요청에 자원 양보.

### 4.3 FlashAttention

**문제**: 표준 어텐션은 \(O(N^2)\) 중간 행렬을 저장해야 하여 메모리와 대역폭 오버헤드가 큼.

**해결책**: 타일링 계산을 통해 SRAM(온칩 메모리)에서 softmax와 행렬 곱을 완료하여, HBM 내 \(N^2\) 중간 결과를 회피.

**nano-vllm에서**:
- Prefill: `flash_attn_varlen_func` (가변 길이 배치 지원).
- Decode: `flash_attn_with_kvcache` (페이징된 KV Cache에서 읽기).

### 4.4 CUDA Graph

**문제**: decode 단계에서는 커널은 작지만 개수가 많아 CPU 런치 오버헤드가 병목이 됨.

**해결책**: 여러 배치 크기 단계의 완전한 순전파 패스를 사전 녹화해 두고, 실행 시 replay.

**nano-vllm에서**:
- `graph_bs = [1,2,4,8,16,32,...]` 단계로 구분.
- `graph_pool`로 메모리 풀 공유.
- `graph_vars`로 입출력 브릿지.

### 4.5 RoPE (회전 위치 인코딩)

**문제**: Transformer는 서로 다른 위치의 토큰을 구별하기 위해 위치 정보가 필요함.

**해결책**: 회전 행렬을 통해 Q와 K에 위치 정보를 인코딩하며, 우수한 외삽성과 상대 위치 인식 능력을 가짐.

**nano-vllm에서**: 각 Attention 레이어의 QKV 프로젝션 후, 어텐션 계산 전에 Q와 K에 회전을 적용.

### 4.6 텐서 병렬 (Tensor Parallelism)

**문제**: 대형 모델 가중치가 단일 GPU 메모리에 들어가지 않음.

**해결책**: 행렬 곱셈을 열 또는 행 기준으로 여러 GPU에 분할하고, All-Reduce로 결과를 집계.

**nano-vllm에서**:
- 열 병렬: QKV 프로젝션, gate_up 프로젝션.
- 행 병렬: Output 프로젝션, down 프로젝션.
- 다중 프로세스 + NCCL 통신.

## 6. vLLM과의 차이 및 확장 가능 방향

### 6.1 확장 가능 방향 (난이도 순)

**쉬움 (1~2일 작업량)**:

1. **더 많은 모델 아키텍처 지원**
   - 대부분의 Decoder-only 모델은 구조가 유사하므로, 약간의 세부 사항(어텐션 헤드 수 비율, 활성화 함수 등)만 수정하면 됨.
   - `model/mistral.py`, `model/gemma.py` 등 추가.

2. **스트리밍 출력 추가**
   - `step()` 반환 시 즉시 새로 생성된 토큰을 출력하고, `generate()` 종료까지 기다리지 않음.
   - `generate` 메서드를 제너레이터로 수정.

3. **Top-k / Top-p 샘플링**
   - Sampler에 Top-k 필터링 및 Top-p (nucleus) 샘플링 추가.
   - Gumbel-max 대비 정렬 연산이 필요하나 영향은 크지 않음.

**중간 (1~2주 작업량)**:

4. **Chunked Prefill**
   - 긴 프롬프트를 여러 개의 청크로 나누어, 매 스텝마다 하나의 청크를 처리하고 decode와 교차 실행.
   - Scheduler 및 Attention 로직 수정 필요.

5. **INT8 양자화**
   - W8A16(가중치 INT8, 활성화 FP16) 또는 W8A8 양자화 구현.
   - 가중치 로딩 및 선형 레이어 구현 수정 필요.

6. **OpenAI 호환 API 서비스**
   - FastAPI로 LLMEngine을 감싸서 `/v1/completions` 및 `/v1/chat/completions` 제공.
   - 비동기 호출 및 스트리밍 SSE 지원 필요.

**어려움 (1개월 이상 작업량)**:

7. **추측적 디코딩 (Speculative Decoding)**
   - draft model과 target model의 조정 관리.
   - 검증 및 롤백 로직 구현 필요.

8. **파이프라인 병렬 (Pipeline Parallelism)**
   - 모델을 레이어 단위로 여러 GPU에 분할.
   - 마이크로 배치 스케줄링 및 GPU 간 통신 구현 필요.

9. **멀티모달 지원**
   - 이미지/비디오 입력 지원, 비전 인코더 통합.
   - 멀티모달 토큰의 KV Cache 관리 필요.

### 6.2 아키텍처 진화 로드맵

```
nano-vllm (현재)
    │
    ├── + 더 많은 모델 아키텍처 → 범용 추론 프레임워크
    ├── + API 서비스 + 스트리밍 출력 → 배포 가능한 추론 서비스
    ├── + 양자화 → 더 낮은 비용 추론
    ├── + Chunked Prefill → 더 나은 지연-처리량 균형
    ├── + Speculative Decoding → 더 빠른 단일 시퀀스 속도
    └── + 멀티모달 → 멀티모달 추론 서비스
    │
    ▼
    vLLM 수준의 완전한 추론 프레임워크
```

## 7. 면접 필수 암기 포인트 목록

### 7.0 면접 필수 암기 20선 (속기 체크리스트)

1. **자기회귀**: 매 스텝 1개의 토큰만 생성하며, 이전 내용에 의존; 추론은 반복 과정.
2. **Prefill**: 프롬프트를 한 번에 처리, 계산량이 많고 shape 가변; **Decode**: 스텝당 시퀀스당 1 토큰, 메모리 접근 위주.
3. **KV Cache**: 과거 K/V를 캐싱하여 지난 토큰에 대한 Attention 재계산 회피.
4. **PagedAttention**: 고정 크기 **블록** 단위로 KV 관리, 물리 블록이 불연속 가능하며 단편화 감소, 프리픽스 공유 지원.
5. **Continuous Batching**: 매 스텝 동적으로 시퀀스 추가/제거, 동일 배치의 요청이 동시에 끝날 필요 없음.
6. **FlashAttention**: 타일링 + 온라인 softmax로 HBM 접근량 감소; 긴 시퀀스에서 큰 이득.
7. **CUDA Graph**: 안정적인 GPU 서브그래프를 녹화하여 `replay`로 **CPU launch** 감소; nano-vllm은 주로 **decode**에 사용.
8. **`graph_bs` 단계**: 작은 배치 조밀, 큰 배치 16 단위; `≥ bs`인 최소 단계 선택, 남는 자리는 `-1` / 0으로 초기화.
9. **`graph_pool`**: 여러 그래프가 메모리 풀을 공유하여 단편화 감소.
10. **Prefill은 Graph 미사용**: 가변 `cu_seqlens`, 그래프 구조 불고정; **bs>512**나 **`enforce_eager`** 시에도 미사용.
11. **전역 `Context`**: `set_context` / `get_context`로 slot_mapping, block_tables 등을 전달하여 레이어별 인자 전달 생략.
12. **Triton `store_kvcache`**: 프로그램 하나가 토큰 하나, `slot==-1` 시 패딩 건너뜀.
13. **`torch.compile` (Sampler 등)**: 연산자 융합, Inductor가 Triton 생성, 샘플링 오버헤드 감소.
14. **가중치 로딩**: `safetensors` + `packed_modules_mapping` + 선택적 `weight_loader` 조각 기록.
15. **텐서 병렬**: 멀티프로세스 + `spawn` + `Event`; 열 분할/행 분할 + AllReduce류 통신 (구현은 Linear/ModelRunner 참조).
16. **`LLMEngine.step`**: `schedule → run → postprocess`; `num_tokens`의 부호로 prefill/decode 통계 구분.
17. **처리량 측정법**: `bench.py`에서 `ignore_eos` + `sum(max_tokens)`으로 생성량 고정; **warmup** 필수.
18. **Gumbel-max 샘플링**: 병렬화에 유리, 대규모 어휘 `multinomial` 대체.
19. **vLLM과 비교**: nano-vllm은 chunked prefill, 추측적 디코딩, 양자화, 완전한 API 등이 부족하지만, **주요 경로 최적화는 정렬**.
20. **개선 방향**: 스트리밍 API, Chunked Prefill, INT4/FP8, Speculative, Prefix 적중률 모니터링 등 (아래 '확장 방향' 참조).

### 7.1 핵심 개념 (필수 10가지)

**첫 번째 단락: 프로젝트 개요**
> nano-vllm은 약 3000줄의 코드로 이루어진 경량 LLM 추론 엔진으로, vLLM의 핵심 최적화 기술인 PagedAttention, CUDA Graph, FlashAttention, Continuous Batching을 구현하였으며, Qwen2.5-7B 모델에서 vLLM 대비 약 90%의 추론 성능을 달성했습니다.

**두 번째 단락: 기술적 하이라이트**
> 몇 가지 핵심 기술을 깊이 연구했습니다. 첫째, KV Cache의 페이징 관리로, 운영체제 가상 메모리 사상에 착안하여 블록 단위로 캐시를 할당합니다. 둘째, CUDA Graph로 decode 단계를 최적화하여, 여러 배치 크기별로 계산 그래프를 단계적으로 녹화함으로써 CPU 런치 오버헤드를 줄입니다. 셋째, Triton을 사용하여 커스텀 GPU 커널을 작성해 KV Cache에 효율적으로 기록합니다.

**세 번째 단락: 개인적 이해/소감**
> 이 프로젝트를 통해 추론 엔진의 핵심 과제가 GPU 활용률(처리량)과 사용자 지연 시간 사이의 균형을 찾는 것임을 이해했으며, 시스템 수준의 최적화(스케줄링, 메모리 관리, 그래프 최적화)를 통해 하드웨어 병목을 보완하는 방법을 배웠습니다.

## 8. 프로젝트 총결산

### 8.1 우리가 배운 것

20회 강의를 통해 우리는 다음을 체계적으로 습득했습니다.

1. **LLM 추론의 기본 원리**: 자기회귀 생성, Prefill/Decode 두 단계, KV Cache의 필요성.

3. **메모리 관리 기술**: PagedAttention, 블록 할당/해제, 프리픽스 캐싱.
4. **스케줄링과 배치 처리**: Continuous Batching, 요청 생애주기 관리.
5. **GPU 최적화 기술**: CUDA Graph, FlashAttention, Triton Kernel, torch.compile.
6. **시스템 공학 실천**: 다중 프로세스 텐서 병렬, 가중치 로딩 매핑, 성능 테스트 방법.
