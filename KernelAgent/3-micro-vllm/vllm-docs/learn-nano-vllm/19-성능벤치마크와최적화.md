# 제19강: 성능 벤치마크와 최적화

초보자를 위한 설명: 본 강의는 nano-vllm의 **성능 벤치마크 테스트(bench.py)**를 상세히 해설하며, LLM 추론 성능을 과학적으로 측정하는 방법, 각 최적화 기술(CUDA Graph, torch.compile, FlashAttention, 프리픽스 캐싱)이 가져오는 가속 효과를 분석하고, 성능 튜닝 조언을 제공합니다.

---

## 1. 개념 설명: LLM 추론 성능 지표

### 1.1 성능 테스트가 중요한 이유

LLM 추론 성능은 다음에 직접적인 영향을 미칩니다.

- **사용자 경험**: 첫 토큰 지연 시간(TTFT)이 사용자 대기 시간을 결정합니다.
- **서비스 비용**: 처리량이 높을수록 토큰당 GPU 비용이 감소합니다.
- **확장성**: 제한된 GPU 자원으로 더 많은 사용자에게 서비스를 제공할 수 있는지 여부.

따라서 **과학적이고 재현 가능한 성능 테스트**는 추론 엔진의 품질을 평가하는 초석입니다.

### 1.2 핵심 성능 지표

| 지표 | 영문 | 정의 | 일반적인 단위 |
|------|------|------|--------------|
| 첫 토큰 지연 시간 | TTFT (Time To First Token) | 요청을 보낸 후 첫 생성 토큰을 받을 때까지의 시간 | ms |
| 토큰 간 지연 시간 | TPOT (Time Per Output Token) | decode 단계에서 토큰 하나를 생성할 때마다 걸리는 평균 시간 | ms |
| 종단 간 지연 시간 | E2E Latency | 요청 전송 후 완전한 응답을 받을 때까지의 시간 | ms / s |
| Prefill 처리량 | Prefill Throughput | 초당 처리하는 프롬프트 토큰 수 | tokens/s |
| Decode 처리량 | Decode Throughput | 초당 생성되는 새 토큰 수 | tokens/s |
| 총 처리량 | Total Throughput | 초당 처리되는 총 토큰 수 (prefill + decode) | tokens/s |

### 1.3 Prefill 처리량 vs Decode 처리량

이것은 면접에서 가장 자주 묻는 구분입니다.

**Prefill 처리량**:
- 엔진이 프롬프트를 처리하는 속도를 측정합니다.
- **연산 능력(FLOPS)**과 관련됩니다: prefill은 연산 중심(compute-bound)입니다.
- 프롬프트가 길 때 차이가 더 두드러집니다.

**Decode 처리량**:
- 엔진이 새 토큰을 생성하는 속도를 측정합니다.
- **메모리 대역폭** 및 **스케줄링 효율**과 관련됩니다: decode는 메모리 중심(memory-bound)입니다.
- 배치 크기(batch size)의 영향을 크게 받습니다: 배치가 클수록 GPU 활용률이 높아져 decode 처리량이 증가합니다.

양자의 관계:

\[
\text{총 처리량} = \frac{\text{prefill\_tokens} + \text{decode\_tokens}}{\text{total\_time}}
\]

## 2. 소스 코드 분석: bench.py 완전 해설

저장소 루트의 `bench.py`(예제에서는 로컬 경로 `~/huggingface/Qwen3-0.6B/`, `enforce_eager=False` 사용)는 아래 구조와 일치합니다. 이 스크립트는 **decode 측에서 `max_tokens`로 약정된 총 생성량** 하의 평균 처리량을 측정하며(아래 `total_tokens` 계산 참조), prefill/decode를 분리한 마이크로 벤치마크가 아닙니다.

### 2.1 전체 코드 분석

```python
def main():
    # ① 재현성을 위한 랜덤 시드 설정
    seed(0)

    # ② 테스트 데이터 생성
    num_seqs = 256
    prompt_token_ids = [
        [randint(0, 10000) for _ in range(randint(100, max_input_len))]
        for _ in range(num_seqs)
    ]
    sampling_params = [
        SamplingParams(temperature=0.6, ignore_eos=True, max_tokens=randint(100, max_ouput_len))
        for _ in range(num_seqs)
    ]

    # ③ 웜업: 엔진 예열
    llm.generate(["Benchmark: "], SamplingParams())

    # ④ 실제 테스트
    t = time.time()
    llm.generate(prompt_token_ids, sampling_params, use_tqdm=False)
    throughput = total_tokens / (time.time() - t)
```

### 2.2 구간별 해설

#### 랜덤 시드

```python
seed(0)
```

랜덤 시드를 설정하는 목적:

- **재현성**: 실행 간 동일한 프롬프트 길이 및 출력 길이 분포를 사용합니다.
- **공정 비교**: 다른 프레임워크나 다른 최적화 설정을 비교할 때 입력 데이터가 완전히 동일합니다.
- 영향 받는 무작위 요소: 프롬프트 내 토큰 ID, 프롬프트 길이, 출력 길이.

#### 테스트 데이터 생성

```python
num_seqs = 256
prompt_token_ids = [
    [randint(0, 10000) for _ in range(randint(100, max_input_len))]
    for _ in range(num_seqs)
]
```

| 파라미터 | 설명 |
|--------|------|
| `num_seqs = 256` | 동시 처리 시나리오를 모방하기 위해 256개의 요청 테스트 |
| `randint(100, max_input_len)` | 프롬프트 길이는 100에서 max_input_len 사이에서 무작위 |
| `randint(0, 10000)` | 토큰 ID 무작위, 단어 사전의 일부를 커버 |

실제 텍스트 대신 **무작위 토큰 ID**를 사용하는 이유?

- **토크나이즈 오버헤드 제거**: 토큰 ID 리스트를 직접 전달하여 토크나이저 생략.
- **변수 통제**: 서로 다른 프롬프트 텍스트의 토크나이즈 결과 길이가 달라지는 것을 방지하고, 무작위 ID로 정밀하게 제어 가능.
- **실제 성능은 텍스트 내용과 무관**: 추론 엔진의 계산 속도는 토큰의 구체적인 값이 아닌 형태(shape)에 의존함.

#### 샘플링 파라미터

```python
sampling_params = [
    SamplingParams(temperature=0.6, ignore_eos=True, max_tokens=randint(100, max_ouput_len))
    for _ in range(num_seqs)
]
```

주요 설정:

- `temperature=0.6`: 확률 샘플링 사용 (greedy 아님), 실제 서비스 환경에 더 가까움.
- `ignore_eos=True`: **EOS 토큰 무시**, `max_tokens`까지 강제 생성. 이는 벤치마크의 표준 방식으로, 실행 간 샘플링 무작위성으로 인해 EOS 위치가 달라져 생성 길이가 일관되지 않는 것을 방지합니다.
- `max_tokens=randint(100, max_ouput_len)`: 출력 길이 무작위, 실제 시나리오에서 요청별 출력 길이 차이를 시뮬레이션.

#### 웜업(Warmup)

```python
llm.generate(["Benchmark: "], SamplingParams())
```

웜업이 필요한 이유?

1. **CUDA 컨텍스트 초기화**: GPU 최초 사용 시 드라이버 초기화, 디바이스 메모리 할당.
2. **torch.compile JIT 컴파일**: `@torch.compile`이 적용된 함수는 첫 호출 시 컴파일, 이후 호출부터 캐시 사용.
3. **CUDA Graph 캡처**: ModelRunner 초기화 시 이미 완료되었지만, 첫 replay 시 추가 오버헤드 가능성.
4. **cuBLAS 핸들 초기화**: 첫 행렬 곱셈 시 cuBLAS 핸들 생성 및 설정.
5. **메모리 할당자 예열**: PyTorch CUDA 메모리 할당자는 첫 할당 후 메모리 블록을 캐싱함.

웜업이 충분하지 않으면 첫 테스트 데이터에 이러한 일회성 오버헤드가 포함되어 **실제 성능을 과소평가**하게 됩니다.

#### 실제 테스트 및 처리량 계산

```python
t = time.time()
llm.generate(prompt_token_ids, sampling_params, use_tqdm=False)
t = (time.time() - t)
total_tokens = sum(sp.max_tokens for sp in sampling_params)
throughput = total_tokens / t
print(f"Total: {total_tokens}tok, Time: {t:.2f}s, Throughput: {throughput:.2f}tok/s")
```

- `use_tqdm=False`: 진행 막대를 비활성화하여 tqdm의 I/O 작업이 타이밍에 영향을 주지 않도록 합니다.
- **`total_tokens = sum(sp.max_tokens for sp in sampling_params)`**: `ignore_eos=True` 하에서 각 시퀀스 생성 길이는 `max_tokens`로 고정되므로, 총 **생성 토큰 작업량**을 사전에 합산할 수 있습니다. 이 지표는 **prefill 입력 토큰 총량**과 무관하므로, 이 스크립트가 출력하는 **tok/s**는 **decode 총 출력/총 시간**에 치우친 거시적 지표입니다(여전히 각 요청의 prefill 시간을 포함하므로 종단 간 혼합 처리량).
- `time.time()`은 **벽시계 시간(wall-clock time)**을 측정하며 모든 오버헤드를 포함합니다.

### 2.3 테스트 방법론

엄밀한 벤치마크는 다음을 고려해야 합니다.

| 요소 | bench.py의 방식 | 이상적인 방식 |
|------|----------------|-------------|
| 재현성 | `seed(0)`로 랜덤 시드 고정 | ✅ |
| 웜업 | 짧은 요청 한 번 실행 | ✅ |
| 데이터 규모 | 256개 요청 | 충분함 |
| 입력 다양성 | 무작위 길이 프롬프트 | ✅ |
| 출력 다양성 | 무작위 길이 출력 | ✅ |
| EOS 비활성화 | `ignore_eos=True` | ✅ |
| 여러 번 반복 | 수행 안 함 | 이상적으로는 3-5회 실행 후 평균 |
| GPU 독점 | 명시적 확인 없음 | 다른 프로세스가 GPU를 점유하지 않도록 확인 필요 |
| 온도 측정 | 모니터링 안 함 | 실제 서비스 환경에서는 GPU 온도 모니터링 필요 (열 쓰로틀링이 성능에 영향) |

## 3. 각 최적화 기술의 가속 효과

### 3.1 CUDA Graph 가속 (16강 복습)

**원리**: decode 단계의 여러 번의 커널 런치를 한 번의 그래프 런치로 병합하여 CPU 오버헤드를 줄입니다.

**가속 효과** (A100에서 Qwen2.5-7B 기준):

| 시나리오 | Graph 없음 | Graph 있음 | 가속비 |
|---------|-----------|----------|--------|
| Decode 처리량 (bs=1) | ~800 tok/s | ~1500 tok/s | ~1.9x |
| Decode 처리량 (bs=32) | ~2500 tok/s | ~3800 tok/s | ~1.5x |
| Decode 처리량 (bs=128) | ~4000 tok/s | ~5500 tok/s | ~1.4x |

**규칙**: 배치 크기가 작을수록 CUDA Graph의 가속비가 커집니다. 이는 작은 배치에서 전체 소요 시간 대비 커널 런치 오버헤드 비중이 높기 때문입니다.

**사용하지 말아야 할 경우**:
- 디버깅 단계 (`enforce_eager=True`).
- 배치가 512를 초과할 때 (캡처 상한 초과).
- 커널별 프로파일링이 필요할 때.

### 3.2 `torch.compile` 가속

**원리**: PyTorch 2.0에서 도입된 컴파일러로, Python + PyTorch 코드를 최적화된 GPU 커널로 컴파일합니다.

**주요 최적화**:
1. **연산자 융합**: 여러 작은 연산자를 하나의 큰 커널로 병합하여 런치 및 메모리 접근 감소.
2. **메모리 최적화**: 중간 텐서 할당 감소.
3. **자동 벡터화**: GPU의 벡터 명령어 활용.
4. **백엔드 코드 생성**: Inductor 백엔드를 통해 Triton 커널 생성.

**nano-vllm에서 `torch.compile`이 사용되는 대표적 위치** (`nanovllm/layers/sampler.py` 예):

```python
class Sampler(nn.Module):
    @torch.compile
    def forward(self, logits, temperatures):
        logits = logits.float().div_(temperatures.unsqueeze(dim=1))
        probs = torch.softmax(logits, dim=-1)
        sample_tokens = probs.div_(torch.empty_like(probs).exponential_(1).clamp_min_(1e-10)).argmax(dim=-1)
        return sample_tokens
```

| 위치 | 기능 | 최적화 효과 |
|------|------|-----------|
| `Sampler.forward` | 온도 스케일링 + softmax + Gumbel-max 샘플링 | 2-3배 가속 (미컴파일 대비) |
| 모델 내 기타 `@torch.compile` 적용 소연산자 (구현에 있을 경우) | RMSNorm, RoPE, SiLU 등 | 융합 후 런치 감소 |

**가속 효과 (전체)**:

| 지표 | compile 없음 | compile 있음 | 가속비 |
|------|-------------|-------------|--------|
| 총 처리량 | ~3000 tok/s | ~3800 tok/s | ~1.27x |

**주의**: `torch.compile`의 첫 컴파일은 수십 초가 걸릴 수 있지만, 컴파일 결과는 캐시됩니다.

### 3.3 FlashAttention 가속

**원리**: **타일링(Tiling)**과 **온라인 소프트맥스(Online Softmax)**를 통해 HBM(고대역폭 메모리) 접근을 줄여 어텐션 계산의 I/O 복잡도를 \(O(N^2)\)에서 \(O(N)\)으로 낮춥니다.

**핵심 기술**:

```
기존 Attention:
  S = Q @ K^T       →   HBM에 기록 (N×N 행렬)
  P = softmax(S)    →   HBM에서 S 읽고, P 기록
  O = P @ V         →   HBM에서 P 읽음

FlashAttention:
  Q, K, V를 타일로 분할 → SRAM에서 S, P 계산 완료 → O에 직접 누적
  전체 N×N 어텐션 행렬을 HBM에 저장할 필요 없음
```

**가속 효과 (Prefill 단계에서 가장 두드러짐)**:

| 프롬프트 길이 | 표준 Attention | FlashAttention | 가속비 |
|-------------|--------------|---------------|--------|
| 512 | 5 ms | 2 ms | 2.5x |
| 2048 | 80 ms | 15 ms | 5.3x |
| 8192 | 1280 ms | 120 ms | 10.7x |

**규칙**: 시퀀스가 길수록 FlashAttention의 이점이 커지며, 이는 \(O(N^2)\) 중간 행렬 저장을 완전히 회피하기 때문입니다.

**nano-vllm에서의 사용**:
- Prefill: `flash_attn_varlen_func` 사용, 가변 길이 시퀀스 일괄 처리 지원.
- Decode: `flash_attn_with_kvcache` 사용, KV Cache에서 바로 과거 K/V 읽기.

### 3.4 프리픽스 캐싱(Prefix Caching) 가속

**원리**: 여러 요청이 동일한 프리픽스(예: 시스템 프롬프트)를 공유할 때, 이미 계산된 KV Cache를 **재사용**하여 중복 계산을 방지합니다.

**대표 시나리오**:

```
요청 1: [시스템 안내문] + "오늘 날씨 어때?"
요청 2: [시스템 안내문] + "번역 좀 해줘."
요청 3: [시스템 안내문] + "시 한 편 써줘."
```

세 요청이 동일한 [시스템 안내문]을 공유하므로, 프리픽스 캐싱을 켜면 시스템 안내문의 KV는 한 번만 계산하면 됩니다.

**가속 효과**:

| 시나리오 | 프리픽스 캐싱 없음 | 프리픽스 캐싱 있음 | 가속비 |
|--------|----------------|----------------|--------|
| 2048 토큰 프리픽스 공유 | Prefill 35ms | Prefill 5ms | 7x |
| 512 토큰 프리픽스 공유 | Prefill 12ms | Prefill 5ms | 2.4x |
| 공유 프리픽스 없음 | 변화 없음 | 변화 없음 | 1x |

**nano-vllm의 프리픽스 캐싱 구현** (이전 강의 복습):
- **해시 테이블**을 사용하여 계산된 KV 블록 캐싱.
- **블록 단위**로 프리픽스를 매칭 (`block_size` 토큰이 한 그룹).
- 캐시에 적중하면 해당 토큰의 prefill 계산을 건너뜀.

## 4. nano-vllm vs vLLM 성능 비교

### 4.1 비교 차원

| 차원 | nano-vllm | vLLM |
|------|-----------|------|
| 코드 라인 수 | ~3000줄 | ~100K+ 줄 |
| 지원 모델 | Qwen2/Llama 등 소수 | 수십 가지 모델 아키텍처 |
| 양자화 | 미지원 | AWQ/GPTQ/FP8 등 |
| 추측적 디코딩(Speculative Decoding) | 미지원 | 지원 |
| 청크 Prefill(Chunked Prefill) | 미지원 | 지원 |
| 텐서 병렬 | 기본 지원 | 완전 지원 |
| 파이프라인 병렬 | 미지원 | 지원 |

### 4.2 성능 비교 (Qwen2.5-7B, 단일 A100 기준)

| 지표 | nano-vllm | vLLM | 비율 |
|------|-----------|------|------|
| Decode 처리량 | ~5000 tok/s | ~5500 tok/s | ~91% |
| Prefill 처리량 | ~8000 tok/s | ~9000 tok/s | ~89% |
| TTFT (bs=1) | ~50 ms | ~45 ms | ~111% |
| 메모리 사용량 | 약간 높음 | 최적화가 더 정교함 | — |

nano-vllm은 핵심 추론 성능에서 vLLM의 **85-95%**에 도달했으며, 3000줄의 코드만을 감안하면 매우 우수한 성과입니다.

### 4.3 성능 차이 원인 분석

nano-vllm과 vLLM의 차이는 주로 다음에서 기인합니다.

1. **Chunked Prefill 부재**: vLLM은 긴 프롬프트를 분할 처리하여 decode와 교차 실행함으로써 GPU 활용률을 높입니다.
2. **스케줄링 전략 단순화**: nano-vllm의 스케줄러는 vLLM만큼 정교하지 않습니다(우선순위 스케줄링, 선점 메커니즘 부재 등).
3. **Paged Attention V2 부재**: vLLM은 더 최적화된 페이징 어텐션 구현을 사용합니다.
4. **양자화 지원 부재**: AWQ/GPTQ 등의 양자화는 메모리 대역폭 요구를 줄여 decode 속도를 높입니다.
5. **더 정교한 메모리 관리**: vLLM의 BlockManager는 더 세밀한 swap/recompute 전략을 가지고 있습니다.

### 5.2 배치 크기 튜닝

배치 크기는 처리량에 영향을 미치는 가장 중요한 매개변수 중 하나입니다.

```
처리량
  ↑
  │         ┌────────── 메모리 대역폭 병목선
  │        ╱
  │      ╱
  │    ╱
  │  ╱
  │╱
  └──────────────→ 배치 크기
  1   4   16  64  256
```

- **작은 배치**(1-8): GPU 활용률 낮음, 메모리 대역폭 불포화, 처리량 낮음.
- **중간 배치**(16-128): 점차 메모리 대역폭 상한에 접근, 처리량 빠르게 증가.
- **큰 배치**(128+): 메모리 상한에 근접, KV Cache가 많은 메모리 점유.

**제안**: `max_num_seqs`를 GPU 메모리에 수용할 수 있는 최대값으로 설정하세요.

### 5.3 주요 파라미터 튜닝 체크리스트

| 파라미터 | 권장 값 | 설명 |
|--------|--------|------|
| `max_num_seqs` | 메모리 따라 계산 | 클수록 처리량 증가, 메모리 제약 받음 |
| `gpu_memory_utilization` | 0.85-0.95 | OOM 방지를 위해 여유분 남기되 너무 낮으면 안 됨 |
| `enforce_eager` | False | 디버깅이 아니라면 CUDA Graph 활성화 필요 |
| `enable_prefix_caching` | True (적용 가능 시) | 공유 프리픽스 시나리오에서 현저한 가속 |
| `block_size` | 16 | 일반적으로 수정 불필요 |

## 6. 고급 최적화 방향

### 6.1 양자화 (Quantization)

모델 가중치를 FP16(16-bit)에서 INT8/INT4로 양자화하면 다음과 같은 이점이 있습니다.

- **메모리 사용량 감소**: 7B 모델 기준 ~14GB → ~7GB (INT8) 또는 ~3.5GB (INT4).
- **메모리 대역폭 활용률 증가**: 같은 계산에 더 적은 바이트 읽기.
- **decode 가속**: decode 단계는 메모리 중심이므로 데이터 양 감소가 곧 속도 향상.

비용: 정밀도가 약간 떨어질 수 있으므로 적절한 양자화 보정이 필요합니다.

### 6.2 추측적 디코딩 (Speculative Decoding)

작은 모델(draft model)로 여러 후보 토큰을 빠르게 생성한 후, 큰 모델(target model)로 병렬 검증합니다.

```
Draft model: k개의 후보 토큰 생성 (매우 빠름)
Target model: 한 번의 순전파로 k개의 토큰 검증 (prefill의 병렬성 활용)
n ≤ k개의 토큰 수락
```

이론적으로 decode 속도를 2-3배 높일 수 있으며, 대가는 추가적인 작은 모델의 메모리와 계산입니다.

### 6.3 Continuous Batching 최적화

스케줄링 전략을 더욱 개선합니다.

- **Iteration-level 스케줄링**: 매 step마다 새로운 요청을 추가하거나 완료된 요청을 제거할 수 있습니다.
- **Preemption**: 메모리 부족 시 낮은 우선순위의 요청을 일시 중단하고 높은 우선순위 요청에 KV Cache를 양보합니다.
- **Chunked Prefill**: 긴 프롬프트를 분할하여 decode와 교차 실행함으로써 긴 프롬프트가 decode를 막는 현상을 방지합니다.

## 8. 면접 예상 문제 (모범 답안 포함)

**1. 공정한 LLM 추론 벤치마크를 어떻게 설계해야 하나요?**  
**답변**: 핵심 요소로는 ① 재현성을 위한 랜덤 시드 고정; ② 초기화 오버헤드 배제를 위한 웜업 수행; ③ `ignore_eos=True`로 출력 길이 제어; ④ 실제 분포를 모방하기 위해 입출력 길이가 다양한 범위를 커버해야 함; ⑤ 배칭 효과를 충분히 활용하기 위한 충분한 요청 수(예: 256건); ⑥ 지터 감소를 위한 여러 번 반복 후 평균; ⑦ GPU에 다른 부하가 없도록 보장이 포함됩니다.

**2. Prefill 처리량과 Decode 처리량의 차이는 무엇이며, 각각 어떤 요인의 영향을 받나요?**  
**답변**: Prefill 처리량은 프롬프트 처리 속도를 측정하며, prefill이 연산 중심(compute-bound)이므로 **GPU 연산 능력(FLOPS)**의 영향을 받습니다. Decode 처리량은 새 토큰 생성 속도를 측정하며, decode가 메모리 중심(memory-bound)이므로 **메모리 대역폭 및 스케줄링 효율**의 영향을 받습니다. 최적화 방향도 달라서, prefill은 FlashAttention으로, decode는 CUDA Graph + 큰 배치 + 양자화로 속도를 높입니다.

**3. bench.py에서 `ignore_eos=True`를 사용하는 이유는 무엇인가요?**  
**답변**: EOS를 무시하지 않으면 샘플링의 무작위성 때문에 실행 간 각 시퀀스가 서로 다른 위치에서 EOS를 생성하여 출력 길이가 달라집니다. 이는 총 토큰 수와 시간에 영향을 주어 성능 데이터를 비교할 수 없게 만듭니다. `ignore_eos=True`는 모든 시퀀스가 `max_tokens`까지 강제로 생성되도록 하여 작업량을 일정하게 만듭니다.

**4. CUDA Graph는 어떤 시나리오에서 가속 효과가 가장 뚜렷한가요?**  
**답변**: **작은 배치 decode** 시나리오에서 가장 뚜렷합니다(1.5-2배 가속). 이는 GPU 계산량은 적지만 커널 런치 횟수가 많아, 전체 소요 시간 대비 CPU 런치 오버헤드의 비중이 높기 때문입니다. 배치가 커지면 계산 자체가 주를 이루어 Graph의 이점은 줄어듭니다(그래도 1.3-1.5배는 유지). Prefill 단계는 가변 shape 때문에 Graph를 적용할 수 없습니다.

**5. FlashAttention의 가속 원리는 무엇이며, 왜 긴 시퀀스에서 더 효과적인가요?**  
**답변**: FlashAttention은 타일링(Tiling)을 통해 전체 \(N \times N\) 어텐션 행렬을 HBM에 저장하지 않아 I/O 복잡도를 \(O(N^2)\)에서 \(O(N)\)으로 낮춥니다. 긴 시퀀스일 때 표준 Attention은 저장하고 읽어야 할 \(N^2\) 행렬이 매우 커져 심각한 메모리 대역폭 병목이 됩니다. FlashAttention은 이 오버헤드를 완전히 회피하므로 시퀀스가 길수록 가속비가 커집니다.

**6. torch.compile은 어떻게 추론을 가속하나요?**  
**답변**: `torch.compile`은 세 가지 수준에서 최적화합니다. ① **연산자 융합**: 여러 작은 연산자(예: cast + div + softmax + argmax)를 하나의 큰 커널로 병합하여 런치 오버헤드와 중간 메모리 할당 감소; ② **메모리 최적화**: 임시 텐서의 생성과 회수 감소; ③ **백엔드 코드 생성**: Inductor 백엔드가 기본 PyTorch eager 실행보다 효율적인 최적화 Triton 코드를 생성합니다.

**7. nano-vllm과 vLLM의 성능 차이는 주로 어떤 부분에서 발생하나요?**  
**답변**: 주로 ① Chunked Prefill 부재 (긴 프롬프트를 decode와 교차 실행 불가); ② 단순화된 스케줄링 전략 (선점, 우선순위 메커니즘 부재); ③ 양자화 미지원 (AWQ/GPTQ/FP8은 메모리 대역폭 요구 감소); ④ 추측적 디코딩 미지원; ⑤ Paged Attention 구현이 vLLM만큼 정교하지 않음 등에서 비롯됩니다. 하지만 핵심 추론 경로(모델 순전파, FlashAttention, CUDA Graph)는 기본적으로 일치합니다.

**8. 성능 테스트에서 웜업이 충분하지 않으면 어떤 문제가 발생하나요?**  
**답변**: **실제 성능을 과소평가**하게 됩니다. 불충분한 웜업으로 인해 테스트 데이터에 CUDA 컨텍스트 초기화(~100ms), torch.compile JIT 컴파일(수십 초), cuBLAS auto-tuning, 메모리 할당자 첫 할당 등 일회성 오버헤드가 포함됩니다. 이들은 실제 운영 환경에서는 한 번만 발생하므로, 정상 상태 성능 데이터에 포함되어서는 안 됩니다.

**9. 주어진 GPU에서 모델의 이론적 최대 decode 처리량을 어떻게 계산하나요?**  
**답변**: decode 단계는 메모리 중심이므로, 이론적 최대 처리량 ≈ **메모리 대역폭 / 토큰당 읽어야 할 가중치 바이트 수**. 예를 들어 A100-80G(2TB/s 대역폭)에서 7B FP16 모델의 경우: 토큰당 약 14GB의 가중치를 읽어야 하므로, 이론적 상한 ≈ 2000GB/s ÷ 14GB ≈ 143 tok/s (단일 시퀀스). 배칭을 통해 여러 시퀀스가 가중치 읽기를 공유하면 수천 tok/s까지 향상 가능합니다.

**10. 실제 서비스 환경에서 처리량 외에 주목해야 할 성능 지표는 무엇인가요?**  
**답변**: ① **TTFT(첫 토큰 지연 시간)**: 사용자가 체감하는 응답 속도에 영향; ② **P99 지연 시간**: 꼬리 지연 시간이 SLA 달성률에 영향; ③ **GPU 메모리 사용률**: 서비스 가능한 최대 동시 접속 수에 영향; ④ **요청 대기 시간**: 스케줄링 효율을 반영; ⑤ **GPU 사용률**: 유휴(idle) 낭비 여부; ⑥ **서비스 가용성**: OOM으로 인한 재시작 빈도 등이 있습니다. 실제 서비스 환경에서는 보통 처리량과 지연 시간 사이에서 균형을 잡아야 합니다(파레토 최적).
