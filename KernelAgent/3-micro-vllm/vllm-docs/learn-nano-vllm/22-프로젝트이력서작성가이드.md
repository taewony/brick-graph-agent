# 프로젝트 이력서 작성 가이드: nano-vllm을 이력서에 기재하는 방법

> **읽기 대상**: 인턴/신입/경력 지원을 준비하며, 'nano-vllm 학습/실습'을 이력서의 강점으로 만들고 싶은 초보자.  
> **읽기 목표**: 템플릿을 활용하여 프로젝트 경험을 작성할 수 있고, 키워드, 정량적 표현, ATS 및 면접 질문 대응 방안을 알게 됩니다.

---

## 1. 이력서 프로젝트 경험 템플릿 (여러 버전)

아래 템플릿의 **기간, 하드웨어, 데이터**는 본인의 실제 상황에 맞게 수정하세요; **처리량 1434 tok/s** 등의 지표는 프로젝트 내 `bench.py`와 튜토리얼의 일반적인 벤치마크(RTX 4070 등 환경)에서 가져온 것이므로, 직접 재현하지 않았다면 숫자를 그대로 복사하지 마세요.

### 버전 1: 신입 이력서 (간결 버전)

적합 대상: 한 페이지 이력서, 프로젝트가 많고, 항목당 길이가 너무 길면 안 되는 경우.

```
프로젝트명: nano-vllm 기반 대규모 모델 추론 엔진 심층 학습 및 최적화
프로젝트 기간: 2026.xx - 2026.xx
기술 스택: Python, PyTorch, CUDA, Triton, FlashAttention, NCCL
프로젝트 설명: nano-vllm 경량 대규모 모델 추론 엔진(약 1200줄 파이썬, 커뮤니티에서 높은 스타를 받은 교육용 구현)을 심층 학습하고 최적화하여, 프로덕션급 추론 프레임워크의 핵심 기술을 숙달했습니다.
핵심 작업:
- PagedAttention 메모리 관리 메커니즘을 심층 이해하고 분석했으며, xxhash 기반의 프리픽스 캐시 구현을 파악했습니다.
- 연속 배치 처리 스케줄링 전략을 학습하고, Prefill 우선 및 Decode 단계에서 running 큐에 대한 스케줄링 방식을 이해했습니다.
- 텐서 병렬 처리(TP) 구현을 분석했으며, 열/행 병렬 Linear와 QKVParallelLinear를 포함합니다.
- CUDA Graph 최적화의 녹화-재생 메커니즘을 이해하고, Triton Kernel 작성을 숙달했습니다.
- bench.py를 통해 성능 테스트를 재현하고, 동일한 하드웨어와 모델에서 vLLM과 유사한 수준의 성능을 확인했습니다(본인의 실측 결과 기준).
```

**작성 팁**: '학습했다'를 '재현/구현/디버깅했다'로 바꾸면 더 능동적인 표현이 됩니다; 만약 **소스 코드 리딩이 주**라면, '소스 코드 수준에서 정리하고 부분적인 실험을 구현했다'고 작성할 수 있으며, '엔진 전체를 처음부터 개발했다'고 허위로 쓰지 마세요.

### 버전 2: 경력 이력서 (상세 버전)

적합 대상: 경력 1~3년, 추론/Infra 직무, **모듈 경계와 공학적 의사 결정**을 부각해야 하는 경우.

> **프로젝트명**: 경량 LLM 추론 엔진 (nano-vllm 아키텍처 실습 및 성능 분석)  
> **프로젝트 기간**: 2026.xx – 2026.xx  
> **기술 스택**: Python, PyTorch, CUDA, FlashAttention-2, Triton, NCCL, torch.compile, SharedMemory  
> **프로젝트 설명** (예시 bullet point, 필요에 따라 삭제 가능):  
> - nano-vllm(~1200줄)을 기반으로 **vLLM 계열 아키텍처**를 정리하고 실습했습니다: 스케줄링(`Scheduler`), 페이징 KV(`BlockManager`), 실행(`ModelRunner`), 어텐션 및 KV 쓰기(`Attention` + Triton), 멀티 카드 TP(`linear.py` / NCCL).  
> - **메모리와 페이징**: `BlockManager`의 블록 할당, `allocate`/`may_append`/`deallocate`, xxhash 체인 해시 및 프리픽스 적중을 구현/디버깅했습니다; `block_table`과 물리 블록 풀 `free_block_ids`의 매핑 관계를 이해했습니다.  
> - **연속 배치 처리**: `schedule()`에서 **Prefill과 Decode가 두 단계로 나뉘는 것**, 메모리 부족 시 `preempt`와 `can_append`의 상호작용을 구현하거나 검증했습니다; 산업계의 FCFS/LIFO 선점 설명과의 대응 관계를 설명할 수 있습니다.  
> - **연산 및 그래프 최적화**: Prefill 시 `flash_attn_varlen_func`, Decode 시 `flash_attn_with_kvcache`를 사용합니다; Decode 경로는 `capture_cudagraph`의 다중 batch size 녹화 및 `graph.replay()`와 연계됩니다; 핫스팟에는 `torch.compile`을 적용했습니다(샘플링, 활성화 함수 등, 코드 기준).  
> - **결과**: 재현 가능한 벤치마크 보고서를 출력했습니다(모델, 시퀀스 길이, batch, 하드웨어). eager / CUDA Graph, 동일 설정의 vLLM과의 차이를 비교할 수 있습니다; 문제 해결 노트를 정리했습니다(예: slot_mapping, prefix cache 분기).

**경력직 가산점 문장**: 별도의 줄로 **당신만의 기여**를 작성하세요: 예를 들어 '메모리 프로파일링 스크립트 추가', '특정 경계 케이스 수정', '설정 항목 확장' 등 — 순수한 오픈소스 사용자와의 동질화를 피하세요.

### 버전 3: 인턴 이력서

적합 대상: 2학년~석사 1년차, **학습 속도, 탄탄한 기초, 성장 가능성**을 강조합니다.

> **프로젝트명**: nano-vllm 대규모 모델 추론 엔진 소스 코드 학습 및 실험  
> **역할**: 개인 학습 프로젝트 / 과목 과제 (사실대로 기재)  
> **기술 스택**: Python, PyTorch, FlashAttention, (선택) Triton 입문  
> **설명 요점**:  
> - X주 내에 핵심 모듈(스케줄링, KV 페이징, 어텐션, 샘플링)을 통독하고, 「`add_request` → `step` → `schedule` → `run`」 호출 체인을 그렸습니다.  
> - 문서를 따라가며 디버깅하면서, **PagedAttention**과 **FlashAttention 두 API**의 prefill/decode에서의 역할 분담을 이해했습니다.  
> - `bench.py` 또는 자체 작성 스크립트를 사용하여 최소 한 세트의 처리량/지연 시간 실험을 완료하고, 환경 의존성과 재현 단계를 기록했습니다.  
> - (선택 사항) 노트, 주석이 추가된 fork, 또는 1~2개의 작은 개선점(로깅, 설정, 단위 테스트)을 제출했습니다.

**인턴쉽 버전 원칙**: '학습/재현'이라고 정직하게 쓰는 것은 부끄러운 일이 아닙니다; **검증 가능한 산출물**(노트 링크, 커밋, 실험 표)로 공허한 형용사를 대체하세요.

## 2. 이력서 작성 원칙

### 2.1 STAR 법칙 적용

- **S (상황)**: 한 문장 — 대규모 모델 추론은 메모리, 처리량, 지연을 동시에 해결해야 합니다; 산업계에서는 흔히 vLLM 계열 아키텍처를 사용합니다.  
- **T (과제)**: 당신의 목표는 '숙달/구현/평가'하고자 하는 것(구체적으로 모듈까지)입니다.  
- **A (행동)**: 동사로 시작: **분석/디버깅/구현/비교/프로파일링**, `block_manager.py`, `scheduler.py` 등 실제 파일명에 대응시킵니다.  
- **R (결과)**: 정량화 또는 **검증 가능한** 결과: 처리량, TTFT, 코드 줄 수, 문서 페이지 수, 이슈 링크; 숫자가 없다면 '화이트보드에 데이터 흐름을 명확히 설명할 수 있음'이라고 씁니다.

이력서 본문은 '행동 + 결과'로 압축할 수 있으며, 면접에서는 완전한 STAR로 전개합니다(`23-STAR면접스크립트.md` 참조).

### 2.2 정량적 성과

우선 사용: **코드 규모, 실험 환경, 지표명, 비교 대상**.

- 코드: 「약 1200줄의 핵심 코드를 통독」「4대 모듈을 정리」가 「코드에 익숙함」보다 강합니다.  
- 성능: 「RTX 4070, Qwen3-0.6B, 고정 프롬프트 길이」가 tok/s 숫자 하나만 있는 것보다 강합니다.  
- 비교: 「eager 모드 대비」「vLLM 동일 설정 대비」가 「효과가 매우 좋음」보다 강합니다.

피할 것: **자신이 증명할 수 없는 규모**(예: '메모리가 40% 향상') — 측정 방법이 있고 면접에서 설명할 수 있는 경우가 아니라면.

### 2.3 기술 키워드 최적화 (ATS 친화적)

- bullet **앞부분**에 자연스럽게 JD 고빈도 단어를 삽입합니다: `PagedAttention`, `KV Cache`, `Continuous Batching`, `Tensor Parallel`, `FlashAttention`, `CUDA Graph`.  
- 동일 단락에서 10번 반복해서 쌓는 것을 피합니다; 「KV Cache 페이징(PagedAttention) 담당」으로 한 번에 합쳐서 표현할 수 있습니다.  
- 파일명, 논문명, 라이브러리명을 정확하게 표기합니다: `FlashAttention-2`, `NCCL`, `Triton`.

### 2.4 피해야 할 실수

| 피할 것 | 이유 | 제안 |
|------|------|------|
| 「vLLM을 베꼈다 / 데모만 돌렸다」 | 부정적 암시 | 「vLLM 아키텍처에 대응하는 교육용 구현」「소스 코드 수준 학습」이라고 작성 |
| 키워드만 쌓고 구현은 없음 | ATS는 통과해도 면접은 반드시 실패 | 각 키워드를 2분 동안 설명할 수 있는 내용과 대응시킴 |
| 스타 수, 순위를 허위 작성 | 검증 가능 | 「커뮤니티에서 유행하는 교육용 프로젝트」라고 쓰거나 정확히 인용 |
| 전부 '이해/숙지' | 수동적으로 보임 | '디버깅했다', '데이터 흐름을 그렸다', '스크립트를 작성했다'로 변경 |
| JD와 무관한 기술들 길게 나열 | 노이즈 | 직무에 맞게 삭제, 추론 직무는 CUDA/스케줄링/KV 유지 |

## 3. 기술 키워드 목록

### 3.1 필수 키워드 (프로젝트 또는 기술 칸에 포함시키는 것을 강력히 권장)

| 키워드 | nano-vllm과의 대응 관계 (면접에서 설명할 수 있어야 함) |
|--------|----------------------------------------|
| **vLLM** | 아키텍처 사상이 대응됨; nano-vllm은 간소화된 교육용 구현임을 설명 |
| **PagedAttention** | `BlockManager` + `block_table` + 물리 블록 풀 |
| **KV Cache** | `ModelRunner.allocate_kv_cache` 대형 텐서 + 레이어별 마운트 |
| **Continuous Batching** | `Scheduler.schedule` 동적 입대기·출대기 |
| **Tensor Parallel** | `layers/linear.py` 등 병렬 레이어 + NCCL |
| **FlashAttention** | `attention.py` 내 varlen / kvcache 두 경로 |
| **CUDA Graph** | `ModelRunner.capture_cudagraph` + `replay` |
| **Triton** | `store_kvcache_kernel` KV 쓰기 |
| **NCCL** | `dist.init_process_group("nccl", ...)` |

### 3.2 가산점 키워드

| 키워드 | 설명 |
|--------|------|
| **torch.compile** | 샘플링, 활성화, RoPE 등 핫스팟 (각 레이어 구현 참조) |
| **Speculative Decoding** | nano-vllm에는 보통 미구현, '원리를 이해함 + 스케줄링에 어떻게 접목할지' 답변 가능 |
| **Prefix Caching** | `BlockManager.compute_hash` + `hash_to_block_id` |
| **RoPE** | `rotary_embedding.py` |
| **GQA** | `num_key_value_heads`가 Q 헤드 수와 다름; KV 메모리 |

## 4. 이력서 QA

### Q1: 「이 프로젝트를 그냥 공부만 했을 뿐, 직접 코드를 작성하지 않았다면 어떻게 하나요?」

**제안**: 학습 자체도 이력서에 쓸 수 있지만, **정직 + 증분**이어야 합니다.  
- 이력서에는 '소스 코드 리딩, 디버깅, 실험 재현'이라고 쓰고, '전체 엔진을 독자 개발'이라고 쓰지 마세요.  
- 오픈소스 또는 로컬 fork에서 **작은 개선**을 완료하세요: 단위 테스트, 로깅, 설정 항목, 성능 스크립트, 주석 PR.  
- 면접에서 STAR를 사용하세요: 당신이 **해결한 구체적인 버그/의문**(예: slot_mapping과 block_table의 대응 관계)이 막연한 '열심히 했다'보다 훨씬 설득력 있습니다.

### Q2: 「면접관이 무엇을 물어볼까요?」

- **기초**: prefill vs decode, KV Cache가 필요한 이유, PagedAttention이 해결하는 문제.  
- **소스 코드**: `schedule`의 두 단계, `can_append`와 `len(seq) % block_size`, `deallocate`가 역순으로 참조 카운트를 감소시키는 이유.  
- **확장**: 양자화, 추측적 디코딩, PD 분리, Chunked Prefill — 튜토리얼 `21-면접빈출문제대전.md` 및 `24-면접질문전집-STAR답변.md` 참고.

### Q3: 「당신이 정말로 이해했음을 어떻게 증명할 수 있나요?」

- **STAR 스토리 준비**: 각 핵심 모듈마다 「문제에 봉착—코드 확인—검증」의 스토리 1개씩.  
- **화이트보드 데이터 흐름**: 요청부터 `Sequence`, `block_table`, FlashAttention 인터페이스 파라미터까지.  
- **시연 가능**: 로컬에서 `example.py` / `bench.py`를 실행하고, 각 단계의 로그와 메모리 변화를 설명할 수 있습니다.
