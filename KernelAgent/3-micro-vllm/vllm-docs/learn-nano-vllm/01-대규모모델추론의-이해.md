# 강의 01: 대규모 모델 추론의 이해

> 먼저 "추론이 무엇을 하는지"를 명확히 이해합시다: 자기회귀, Prefill과 Decode 두 단계, GPU 메모리와 연산 병목, 그리고 처리량과 지연 시간까지—이는 nano-vllm 엔진 코드를 읽기 전에 반드시 알아야 할 상식입니다.

## 본 강의 목표

이 강의를 마치면 다음을 할 수 있어야 합니다:

1. **자신의 말로** **자기회귀 생성**과 **Prefill / Decode** 두 단계의 차이를 설명할 수 있다.
2. **GPU 메모리, 연산, 지연 시간** 세 가지 관점에서 **추론이 왜 종종 시스템 병목이 되는지** 설명할 수 있다.
3. 면접에서 **처리량(throughput)과 지연 시간(latency)** 의 트레이드오프에 대해 논의하고, 각각에 대한 최적화 전략을 한 가지씩 예로 들 수 있다(개념 수준).
4. 후속 학습(`scheduler.py`, `attention.py` 등)을 위해 **용어 정렬표**(prefill batch, decode step, KV 등)를 만들 수 있다.

## 핵심 개념

### LLM 추론이 하는 일

**학습**은 파라미터를 업데이트하지만, **추론**은 파라미터가 고정된 상태에서 입력 토큰 시퀀스에 기반해 다음 토큰의 분포를 계산하고 샘플링하여, 종료 조건까지 이를 반복하는 것입니다. 추론은 그래디언트를 신경 쓰지 않고, **지연 시간, 처리량, GPU 메모리 사용량**에 집중합니다.

Decoder-only Transformer(예: GPT, Qwen, LLaMA)의 경우:

- 입력: **프롬프트**(토큰 시퀀스 \(x_1,\dots,x_T\)로 간주)
- 출력: 프롬프트 이후 **하나씩** 토큰 \(y_1, y_2, \dots\)을 생성하며, EOS에 도달하거나 최대 길이에 도달할 때까지 진행

### Prefill 단계 (프리필 단계)

**정의**: 처음(또는 특정 추가 라운드)으로 **프롬프트 전체**(혹은 새로운 토큰 배치)에 대해 순전파를 수행하여, 각 레이어의 **Q, K, V**를 계산하고 **KV Cache**를 기록해 이후 단계에서 재사용할 수 있도록 합니다.

**특징**:

- **연산 집약적(Compute-bound)**: 행렬 곱셈 차원이 커서 GPU 연산 능력을 쉽게 포화시킵니다.
- **병렬화 가능성 높음**: 인과 마스크(causal mask) 하에서도 프롬프트 내 토큰 간에 효율적인 어텐션(FlashAttention 등)이 가능합니다.
- nano-vllm에서는 일반적으로 `context.is_prefill == True`인 경로에 해당합니다.

### Decode 단계 (디코딩 단계)

**정의**: **이미 생성된 마지막 위치**부터 시작하여, 각 단계마다 **1개의 새로운 토큰**(또는 시퀀스당 한 토큰)만 입력하고, **기록된 KV Cache**를 읽어 현재 단계의 어텐션을 계산한 후, 다음 토큰을 샘플링합니다.

**특징**:

- **메모리/대역폭 집약적(Memory-bound)**: 단계별 연산은 상대적으로 작고, 병목은 주로 **KV 읽기/쓰기**와 **커널 런칭**에 있습니다.
- **단계 수가 많음**: 생성 길이가 \(N\)이라면, decode는 약 \(N\)번의 단계를 실행해야 합니다(여러 시퀀스를 스케줄링으로 합칠 수도 있음).
- nano-vllm에서는 일반적으로 `context.is_prefill == False`이며, `flash_attn_with_kvcache` 등의 API를 사용합니다.

### 자기회귀 생성 원리

**자기회귀**: \(t\)번째 출력 토큰의 분포는 **앞선 모든 토큰**(프롬프트와 이미 생성된 부분)에 조건부로 결정됩니다.

\[
P(y_1,\dots,y_{L}) = \prod_{t=1}^{L} P(y_t \mid x, y_{<t})
\]

구현은 사실상 **for 루프**입니다: 각 단계마다 **순전파** → **소프트맥스로 logits 획득** → **샘플링 혹은 탐욕적 선택** → 시퀀스 끝에 추가 → EOS까지 반복.

**KV Cache가 필요한 이유**: 매 단계마다 **전체 이력**의 K, V를 다시 계산하면 복잡도가 폭발합니다. **과거 위치의 K, V**를 캐시하고, 새 단계에서는 **현재 토큰의 Q**만 계산하여 캐시된 K, V와 어텐션하는 방식이 산업계 추론의 표준입니다.

### 추론이 병목이 되는 이유

1. **GPU 메모리(VRAM)**  
   - KV Cache는 **시퀀스 길이 × 레이어 수 × 헤드 수 × head_dim**에 따라 증가하며, 여러 사용자가 동시에 요청하면 **선형적으로 커집니다**.  
   - 활성값, 임시 버퍼, 가중치(충분히 공유되지 않을 경우)도 메모리를 차지합니다.

2. **연산(Compute)**  
   - **긴 프롬프트**의 Prefill은 한 번의 순전파 비용이 큽니다. 모델이 클수록 FLOPs도 높아집니다.  
   - Decode의 단계별 FLOPs는 작을 수 있지만, **총 단계 수 × 동시 요청 수**를 고려하면 무시할 수 없습니다.

3. **지연 시간(Latency)**  
   - **첫 토큰 시간(TTFT, Time To First Token)**은 주로 Prefill에 의해 결정됩니다.  
   - **토큰당 시간**은 Decode 단계에서 누적되며, 출력이 길어질수록 총 지연 시간이 늘어납니다.

### 처리량 vs 지연 시간의 트레이드오프

| 지표 | 의미 | 주요 관심사 |
|------|------|------------|
| **처리량** | 단위 시간당 처리한 토큰 수 또는 요청 수 | 배치 크기, 연속 배치 처리, GPU 활용률 향상 |
| **지연 시간** | 단일 요청이 입력부터 첫 토큰까지 / 토큰당 소요되는 시간 | 작은 배치, 짧은 대기열, 불필요한 동기화 회피 |

**모순**: 배치 크기를 늘리면 보통 처리량이 증가하지만, 단일 요청의 대기 시간이 길어질 수 있습니다(**큐잉**). **연속 배치 처리(continuous batching)**는 이 둘 사이의 균형을 찾으려는 시도이며, 이것이 바로 nano-vllm / vLLM 스케줄러의 핵심 설계 중 하나입니다.

### nano-vllm 설정 항목과의 직관적 연결 (예고)

앞으로 `config.py`를 읽을 때, 본 강의의 개념을 **숫자에 대응**시킬 수 있습니다:

- **`max_model_len`**: 단일 시퀀스의 **컨텍스트 길이 상한**, KV 논리적 규모와 스케줄링 가능성에 직접적 영향.
- **`max_num_batched_tokens`**: 한 번의 순전파에서 허용하는 **총 토큰 수 상한**, **Prefill에서 긴 프롬프트를 배치로 합칠 때**의 엄격한 제약.
- **`max_num_seqs`**: 동시 **시퀀스 개수** 상한, **Decode에서 여러 요청을 함께 실행**하는 것과 밀접한 관련.
- **`gpu_memory_utilization`**: **KV 블록 풀** 등을 위해 예약할 GPU 메모리 비율의 '다이얼'. 너무 크면 OOM 발생 위험, 너무 작으면 메모리 낭비.

이 내용들은 본 강의의 핵심 도출 내용은 아니지만, "왜 추론이 느리거나 OOM이 발생하는가"에 답할 때 **개념**과 **설정 이름**을 연결 지으면 **알고리즘과 시스템을 모두 이해하고 있다**는 인상을 줄 수 있습니다.

## 소스 코드 분석 (전체 소스 코드 및 줄별 주석 포함)

본 강의는 개념 위주이므로 **특정 파이썬 파일에 구속되지 않습니다**. 아래는 앞으로 `llm_engine`에서 보게 될 "바깥 루프"의 멘탈 모델을 보여주는 **의사 코드**입니다. 실제 소스 코드와 대조하기 위한 용도입니다:

```python
# 의사 코드: 자기회귀 + prefill/decode 두 단계 (nano-vllm 직접 소스 아님)

def generate_one(prompt_token_ids, max_new_tokens):
    # 1) Prefill: 프롬프트 전체를 한 번에 순전파하여 KV cache 채움
    logits = model.forward_prefill(prompt_token_ids)  # 연산 집약적
    next_token = sample(logits[-1])

    out = [next_token]
    # 2) Decode: 각 단계마다 새 토큰 하나만 입력하고 KV cache 사용
    for _ in range(max_new_tokens - 1):
        logits = model.forward_decode([next_token])   # 메모리 대역폭 민감
        next_token = sample(logits[0])
        if next_token == EOS:
            break
        out.append(next_token)
    return out
```

줄별 설명:

1. **`forward_prefill`**: 긴 시퀀스를 입력받아 각 토큰의 표현을 병렬로 계산하고, **KV cache를 기록**합니다.
2. **`logits[-1]`**: 일반적으로 **마지막 위치**의 예측만 첫 번째 생성 토큰으로 사용합니다(prefill에서 `ParallelLMHead`가 마지막 hidden만 취하는 것과 일관됨).
3. **`forward_decode`**: 단계마다 **1개의 토큰**, **캐시된 K, V**에 의존하므로 메모리 접근이 두드러집니다.
4. **루프와 EOS**: **자기회귀**를 보여줍니다. 실제 엔진에서는 **배치 내 여러 시퀀스, 다양한 길이**를 `Scheduler`가 관리합니다.

## 그림 설명 (텍스트/ASCII 설명)

**시간 축에서의 두 단계**:

```
프롬프트 토큰:  [t1][t2][t3]...[tT]
                      | Prefill 한 번의 순전파 (연산 중심)
                      v
KV cache가 앞부분 위치를 채움
                      |
              샘플링으로 y1 얻음
                      | Decode 단계 1 (메모리 접근 중심)
                      v
              샘플링으로 y2 얻음
                      ...
```

**단일 요청 자원 개요**:

```
Prefill:  ████████████  (행렬 크기가 커서 GPU 연산 장치가 바쁨)
Decode:   ▁▁▁▁▁▁▁▁▁▁  (각 단계가 작아 메모리·커널 대기)
```

## 면접 출제 포인트

- **Prefill vs Decode** 차이: **연산 중심 vs 메모리 접근 중심**, **입력 길이**, **시퀀스 점진적 증가 여부**.
- **KV Cache의 역할**과 **캐시 없을 때 발생하는 복잡도 문제**.
- **TTFT**와 **토큰당 지연 시간**이 각각 무엇에 의해 좌우되는가.
- **처리량 vs 지연 시간**의 모순 및 **continuous batching**의 동기(개념 수준, 자세한 내용은 스케줄러 강의에서).

## 자주 나오는 면접 질문

1. **추론과 학습(역전파)의 주요 차이는?**  
   답변: 추론은 학습을 위한 중간 활성값을 저장하지 않습니다. 최적화 목표가 '수렴'에서 **지연 시간, 처리량, GPU 메모리**로 바뀝니다. **KV cache, 양자화, 연산자 융합** 등이 자주 사용됩니다.

2. **Decode 단계가 더 memory-bound라고 하는 이유는?**  
   답변: 단계별 배치 내 유효 계산량이 상대적으로 작고, **KV 읽기와 쓰기**가 차지하는 비중이 높습니다. 또한 **커널 런칭 횟수**가 많아 연산 능력을 충분히 활용하기 어렵습니다.

3. **첫 토큰 지연 시간(TTFT)은 주로 무엇의 영향을 받나요?**  
   답변: 주로 **Prefill 길이와 모델 크기**의 영향을 받습니다. 다중 사용자 큐잉 시에는 **스케줄링 대기 시간**도 추가됩니다.

4. **자기회귀에서 여러 토큰을 병렬로 생성할 수 없나요?**  
   답변: 표준 자기회귀는 **미래의 여러 토큰을 병렬로 예측할 수 없습니다**(인과성). 병렬 처리는 **배치 내 여러 요청**이나 **추측적 디코딩(speculative decoding)** 등의 확장 기법에서 비롯됩니다. 본 강의에서는 다루지 않습니다.

5. **Prefill과 Decode에서 배치 크기의 의미가 어떻게 다른가요?**  
   답변: **Prefill**의 배치는 보통 "몇 개의 시퀀스, 몇 개의 토큰을 함께 계산할 것인가"를 의미합니다. **Decode**는 보통 "몇 개의 시퀀스가 동시에 진행되는가"를 의미하며, 각 시퀀스는 단계마다 보통 1개의 새 토큰을 생성합니다. 스케줄러는 `max_num_batched_tokens` 등으로 **총 토큰 예산**을 제한하여 OOM을 방지합니다.

6. **GPU 메모리를 주로 차지하는 것은 무엇인가요?**  
   답변: 대규모 모델 추론에서는 **가중치**(멀티 GPU 분할이 안 된 경우), **KV Cache**(동시 요청 수와 길이에 따라 증가), **활성값과 임시 버퍼**가 세 가지 주요 원인입니다. 서빙 환경에서는 **KV**가 가장 민감한 요소인 경우가 많습니다.

## 요약

- **추론 = 고정 가중치 하에서 순전파 + 샘플링 루프**; 핵심은 **Prefill(연산)**과 **Decode(메모리 접근)**의 두 단계입니다.
- **KV Cache**는 두 단계를 연결하는 다리이자 **GPU 메모리 압박**의 주된 원천입니다.
- **처리량과 지연 시간**은 스케줄링 및 배치 전략을 통해 균형을 맞춰야 하며, 이것이 바로 이후 **nano-vllm 엔진 계층**이 해결하려는 과제입니다.

**용어와 nano-vllm 대응표 (예습)**:

| 개념 | 저장소 내 위치 (후속 강의에서 전개) |
|------|------------------------------|
| Prefill / Decode | `utils/context.py`의 `is_prefill`; `scheduler`에서 단계 구분 |
| KV Cache 배치 | `attention.py`의 `k_cache`/`v_cache` + `store_kvcache` |
| 가변 길이 배치 | `cu_seqlens_q` / `cu_seqlens_k`(FlashAttention varlen) |
| 샘플링 | `layers/sampler.py` + `SamplingParams` |

**흔히 하는 실수 주의사항**:

- Prefill은 **임베딩만 하는 것이 아닙니다**. **프롬프트 전체에 대한 완전한 Transformer 순전파**이며, **KV를 기록**합니다.
- Decode는 **KV가 필요 없는 것이 아닙니다**. 오히려 **과거 KV에 강하게 의존**하며, 매 단계 현재 토큰의 K, V를 **추가**할 뿐입니다.
- **TTFT**와 **총 생성 시간**은 분리해서 봐야 합니다. 전자는 주로 **Prefill과 큐잉**을 통해 최적화하고, 후자는 **Decode 단계 수와 단계별 소요 시간**을 고려합니다.

**본 강의 자가 점검 (구두로 답변 가능해야 함)**:

1. Prefill과 Decode의 병목 유형을 두 문장으로 비교해 보세요.  
2. KV Cache의 역할을 최소 두 가지 말해 보세요.  
3. 배치를 늘린다고 해서 항상 단일 사용자의 지연 시간이 줄어들지는 않는 이유를 설명해 보세요.

**부록 - inference pipeline:**

- tokenizer는 CPU-side preprocessing이고,
vLLM은 token id 이후의 처리만을 담당한다.
```
Text
 ↓
Tokenizer (CPU)
 ↓
Token IDs
 ↓
vLLM Engine (GPU-heavy)
 ↓
Next Token IDs
 ↓
Detokenizer
 ↓
Text
```

- Hugging Face Transformers의 ecosystem:

  - tokenizer.json
  - merges.txt
  - vocab.json
  - sentencepiece.model

- vLLM은 그냥 이미 검증된 tokenizer를 사용한다. Tokenizer는 “모델 정의의 일부”이기 때문이다.
- 성능 관점에서도 tokenizer는 병목이 아니다. Tokenizer는 상대적으로, CPU-side 짧은 처리라서 GPU engine 안에 tightly integrate할 이유가 적다.
- LLM inference 시간 대부분은 다음 GPU 처리에서 발생한다.
  - attention
  - GEMM
  - KV cache memory access

### 이 구조의 장점

#### (1) 멀티모달 확장 쉬움

이미지가 들어와도:

```text
Image → Vision Encoder → image token ids
```

결국 token ids만 생성하면 됨.

vLLM은 tokenizer를 몰라도 된다.

---

#### (2) Agent system integration 쉬움

외부 시스템이:

* custom tokenizer
* compression token
* structured token

을 생성 가능.

---

#### (3) Serving scalability

Tokenizer는:

* CPU pool
* 별도 서버
* 비동기 처리

로 분리 가능.

GPU engine과 decouple 가능.

---

### 아주 중요한 내부 철학

vLLM은:

> “문자열 처리 시스템”이 아니라
> “Token sequence execution engine”

이다.

이 관점이:

* tokenizer externalization
* paged KV cache
* token scheduling

모두 연결된다.

---

### Transformer 본질 관점에서 보면

Transformer는 원래:

[
f: \mathbb{Z}^n \rightarrow \mathbb{Z}^m
]

즉:

* integer token sequence
* → integer token sequence

를 학습한 모델이다.

인간은 text를 보지만,
모델은 token id world만 본다.

그래서:

> tokenizer는 “human language ↔ token universe” 변환기

이고,
vLLM은 그 이후 계산만 담당한다.

---

# 14) 핵심 정리

| 구성          | 역할                         |
| ----------- | -------------------------- |
| Tokenizer   | text → token ids           |
| vLLM        | token ids → next token ids |
| Detokenizer | token ids → text           |

그리고:

> vLLM이 tokenizer를 외부화한 이유:
>
> * tokenizer 다양성
> * 모델 coupling 문제
> * HF ecosystem 재사용
> * GPU engine 단순화
> * architecture decoupling
