## 1. KV Cache (8문제)

### 1. KV Cache란 무엇인가요? 왜 필요한가요?

**문제:** KV Cache란 무엇인가요? 왜 필요한가요?

**상세 답변:**  
셀프 어텐션은 디코딩 단계에서 매 단계마다 하나의 query 토큰만 새로 추가하지만, key/value는 **이미 생성된 모든 프리픽스 위치**에 의존합니다. 만약 매 단계마다 시퀀스 전체에 대해 K, V를 다시 계산한다면, 계산량은 길이의 제곱에 비례하여 증가하고 대량의 중복이 발생합니다. KV Cache는 과거 위치의 **K, V 텐서를 GPU 메모리에 지속적으로 유지**하여, 새 단계에서는 현재 단계의 Q만 계산하고 캐시된 K, V와 어텐션을 수행함으로써, 단계별 복잡도를 '전체 길이와 관련된 고차'에서 '현재 단계 및 캐시 읽기와 관련된 수준'으로 낮춥니다.  
nano-vllm에서는 각 레이어의 `Attention`이 `k_cache`/`v_cache` 뷰를 보유하고 있으며, 순전파 시 먼저 이번 단계에서 계산된 k, v를 해당 slot에 **기록**한 후, FlashAttention 인터페이스를 호출하여 캐시를 읽어 어텐션을 수행합니다.

**nano-vllm 소스 코드와 결합:**  
`Attention.forward`는 캐시가 존재할 때 먼저 `store_kvcache(k, v, k_cache, v_cache, context.slot_mapping)`를 수행한 후, `context.is_prefill`에 따라 varlen 또는 `flash_attn_with_kvcache`를 사용합니다(`layers/attention.py` 참조).

**면접 가산점 기법:**  
먼저 '디코딩 시 과거 K/V 재사용, 중복 투영 및 어텐션 재계산 방지'라고 답하고, 이어서 'PagedAttention/블록 관리와 결합해야만 다중 시퀀스의 효율적인 카드 공유가 가능하다'고 보충하며, 마지막으로 nano-vllm의 **slot 매핑 쓰기**라는 구현 디테일을 짚습니다.

### 2. KV Cache의 GPU 메모리 계산 공식은 무엇인가요?

**문제:** KV Cache의 GPU 메모리 계산 공식은 무엇인가요?

**상세 답변:**  
단일 레이어, 단일 시퀀스의 단순 추정: 레이어마다 **K와 V** 두 개를 저장하며, 형상은 `(seq_len, num_kv_heads, head_dim)`과 관련되며, 총 바이트 수는 약 `2 × num_layers × seq_len × num_kv_heads × head_dim × sizeof(dtype)`입니다. 실제 시스템에서 seq_len은 **블록**으로 분할되며, 총 점유량은 '블록 수 × 블록당 바이트 수'로 계산됩니다. 만약 텐서 병렬을 사용한다면, **카드당 KV 헤드 수**는 `num_kv_heads // tp_size`입니다.  
nano-vllm은 할당 시 단일 시퀀스 기준이 아닌 **전역 블록 풀** 기준으로 합니다: 먼저 블록당 바이트 `block_bytes`를 계산한 후, 남은 사용 가능한 GPU 메모리를 `block_bytes`로 나누어 `num_kvcache_blocks`를 구합니다.

**nano-vllm 소스 코드와 결합:**  

```109:111:nano-vllm-main/nanovllm/engine/model_runner.py
        block_bytes = 2 * hf_config.num_hidden_layers * self.block_size * num_kv_heads * head_dim * hf_config.torch_dtype.itemsize
        config.num_kvcache_blocks = int(total * config.gpu_memory_utilization - used - peak + current) // block_bytes
```

여기서 `num_kv_heads`는 이미 `world_size`(TP)로 나누어져 있습니다.

**면접 가산점 기법:**  
**2×L×…**(K+V)를 쓰고, **TP가 헤드별로 분할**됨을 설명하며, **블록화 후 block_bytes에 블록 수를 곱하는 방식**으로 전환하여, 교과서 공식에서 공학적 구현으로의 도약을 보여줍니다.

### 3. Prefill과 Decode 단계에서 KV Cache 사용의 차이점은 무엇인가요?

**문제:** Prefill과 Decode 단계에서 KV Cache 사용의 차이점은 무엇인가요?

**상세 답변:**  
Prefill 단계는 보통 프롬프트의 대량 토큰(또는 프리픽스 미적중 부분)을 한 번에 처리하며, **여러 query 위치**에 대해 병렬로 K/V를 기록해야 하고, 어텐션은 '긴 시퀀스 대 긴 시퀀스'의 인과 모드입니다. Decode 단계는 시퀀스당 보통 **1개의 토큰**만 추가하며, 어텐션은 배치 내 다중 시퀀스, 시퀀스당 길이가 context+1인 **점진적 디코딩**으로 축소됩니다.  
데이터 준비 면에서 전자는 `cu_seqlens_q/k`를 구성하고, prefix cache의 `block_tables`를 포함할 수 있습니다. 후자는 `context_lens`, `slot_mapping`을 구성하여 **현재 쓰기 슬롯**을 가리킵니다. nano-vllm은 전역 `Context`로 두 모드를 구분합니다.

**nano-vllm 소스 코드와 결합:**  
`ModelRunner.prepare_prefill`은 `set_context(True, cu_seqlens_q, ...)`를 설정합니다; `prepare_decode`는 `set_context(False, slot_mapping=..., context_lens=..., block_tables=...)`를 설정합니다(`model_runner.py`).

**면접 가산점 기법:**  
"prefill은 계산이 많고, decode는 계산이 적지만 단계 수가 많다"라고 한 문장으로 비교하고, **FlashAttention API가 다르다**(varlen vs with_kvcache)는 점과 **스케줄링 상에서 prefill이 우선되는** 공학적 이유를 강조합니다.

### 4. Prefix Cache(프리픽스 캐시)란 무엇인가요? nano-vllm은 어떻게 구현하나요?

**문제:** Prefix Cache(프리픽스 캐시)란 무엇인가요? nano-vllm은 어떻게 구현하나요?

**상세 답변:**  
Prefix Cache는 여러 요청 또는 여러 호출이 **동일한 토큰 프리픽스**를 공유할 때, 프리픽스의 KV를 반복 계산할 필요 없이 물리 블록 내 캐시를 직접 재사용하여, 첫 패킷 지연과 연산 능력을 낮추는 것을 말합니다. 구현의 핵심은 **프리픽스와 물리 블록의 해시 매핑**과 **참조 카운팅**입니다.  
nano-vllm은 `xxhash`를 사용하여 블록 내 토큰에 대해 해시를 수행하고, **체인 방식**으로 이전 블록의 해시를 프리픽스로 전달하여, 동일한 프리픽스 체인이 적중될 수 있도록 합니다. 적중 시 `ref_count`를 증가시키고 `num_cached_tokens`를 진행시킵니다.

**nano-vllm 소스 코드와 결합:**  
`BlockManager.compute_hash`는 `prefix.to_bytes` + 토큰 바이트를 사용합니다. `allocate`에서 `hash_to_block_id`가 적중하고 `token_ids`가 일치하면 재사용하고 `num_cached_tokens += block_size`를 수행합니다(`block_manager.py`). Prefill 시 프리픽스 캐시가 존재하면, `prepare_prefill`이 `block_tables`를 준비합니다(`model_runner.py`의 `cu_seqlens_k[-1] > cu_seqlens_q[-1]` 분기).

**면접 가산점 기법:**  
**블록 수준의 세분성**, **해시 충돌 시 토큰 비교**, 그리고 **PagedAttention 블록 테이블과의 협업** 세 가지를 설명합니다.

### 5. nano-vllm의 KV Cache 텐서 형상은 무엇인가요? 왜 이렇게 설계했나요?

**문제:** nano-vllm의 KV Cache 텐서 형상은 무엇인가요? 왜 이렇게 설계했나요?

**상세 답변:**  
전체 형상은 **`[2, num_layers, num_blocks, block_size, num_kv_heads, head_dim]`**입니다: 차원 0은 K/V; 차원 1은 레이어; 차원 2는 전역 물리 블록; 블록 내에서는 `block_size`로 펼쳐 토큰을 배치합니다; 마지막 두 차원은 GQA/MHA의 KV 헤드와 헤드 차원입니다. 이렇게 하면 **동일한 물리 블록이 GPU 메모리 내에서 연속**되며, **slot = block_id * block_size + offset**이라는 1차원 인덱스로 사용하기 쉽고, FlashAttention의 `block_table` 의미론과 일관됩니다.  
텐서 병렬 하에서 `num_kv_heads`는 **이 카드의 헤드 수**입니다.

**nano-vllm 소스 코드와 결합:**  

```112:118:nano-vllm-main/nanovllm/engine/model_runner.py
        self.kv_cache = torch.empty(2, hf_config.num_hidden_layers, config.num_kvcache_blocks, self.block_size, num_kv_heads, head_dim)
        layer_id = 0
        for module in self.model.modules():
            if hasattr(module, "k_cache") and hasattr(module, "v_cache"):
                module.k_cache = self.kv_cache[0, layer_id]
                module.v_cache = self.kv_cache[1, layer_id]
```

**면접 가산점 기법:**  
먼저 형상을 외우고, **「물리 블록 풀 + 각 어텐션 레이어 슬라이스」**가 vLLM 논문의 PagedAttention 저장 방식과 일치함을 설명하여 소스 코드를 읽었음을 보여줍니다.

### 6. KV Cache의 블록 수를 어떻게 동적으로 계산하나요?

**문제:** KV Cache의 블록 수를 어떻게 동적으로 계산하나요?

**상세 답변:**  
동적 블록 수의 본질은: 모델 가중치와 기타 런타임 오버헤드가 이미 일부 GPU 메모리를 점유한 후, **`gpu_memory_utilization × 총 GPU 메모리`**를 목표 상한으로 사용하고, 현재 할당량과 피크 할당량을 차감하여, **KV 풀에 할당할 수 있는 바이트 수**를 구한 다음, 블록당 `block_bytes`로 나누어 내림 정수 블록 수를 얻는 것입니다.  
이렇게 하면 수동으로 블록 수를 조정할 필요가 없어지고, **워밍업 후 피크 GPU 메모리**와 정렬되어 OOM을 줄입니다.

**nano-vllm 소스 코드와 결합:**  
`allocate_kv_cache` 참조: `mem_get_info`로 `total/free` 획득, `peak`는 `memory_stats`에서 가져옴, `block_bytes`는 레이어 수, 블록 길이, 헤드 수, dtype에 의해 결정됨, 마지막으로 정수 나누기를 통해 `num_kvcache_blocks`를 얻습니다(`model_runner.py`).

**면접 가산점 기법:**  
**워밍업의 목적**(피크 통계)과 **`gpu_memory_utilization`은 사용자가 조정 가능한 안전 여유분**임을 강조합니다.

### 7. KV Cache의 Block 관리 전략에는 어떤 것들이 있나요?

**문제:** KV Cache의 Block 관리 전략에는 어떤 것들이 있나요?

**상세 답변:**  
일반적인 전략으로는: **빈 연결 리스트/스택**으로 할당 가능한 물리 블록 관리, **참조 카운팅**으로 여러 시퀀스의 블록 공유 지원, **LRU**(일부 시스템에서 축출에 사용), 그리고 **프리픽스 해시 테이블**로 블록 수준 재사용 등이 있습니다. nano-vllm 구현에서는: **빈 큐 `free_block_ids`, 사용 중 집합 `used_block_ids`, 해시 테이블 `hash_to_block_id`**를 사용하며, `ref_count`와 함께 deallocate 시 회수합니다.  
append 시 블록이 가득 차면 새 블록을 신청하고, 가득 차지 않았으면 마지막 블록의 해시를 업데이트합니다.

**nano-vllm 소스 코드와 결합:**  
`BlockManager.allocate` / `deallocate` / `may_append`(`block_manager.py`); `Sequence`는 `num_blocks`, `last_block_num_tokens` 등을 제공합니다(`sequence.py`).

**면접 가산점 기법:**  
'순수 할당 해제'와 '공유가 포함된 참조 카운팅'을 대비시키며, **선점 시 반드시 deallocate로 물리 블록을 해제해야 함**을 설명합니다(스케줄러 절 참조).

### 8. KV를 Cache에 어떻게 기록하나요? nano-vllm은 어떤 기술을 사용했나요?

**문제:** KV를 Cache에 어떻게 기록하나요? nano-vllm은 어떤 기술을 사용했나요?

**상세 답변:**  
기록 시 이번 단계에서 계산된 `(N, num_heads, head_dim)`의 K/V를 **slot_mapping**에 따라 대형 블록 캐시의 해당 위치로 scatter해야 합니다. 만약 단순 인덱싱을 사용하면 여러 번의 작은 쓰기가 발생하지만, nano-vllm은 **Triton JIT 커널**을 사용하여 토큰별로 병렬화하고, 각 program이 하나의 토큰에 대한 전체 head_dim×heads 펼침 차원을 처리합니다.  
`slot == -1`이면 바로 반환하여 자리 채우기와 호환됩니다.

**nano-vllm 소스 코드와 결합:**  
`store_kvcache_kernel` 및 `store_kvcache`(`layers/attention.py`).

**면접 가산점 기법:**  
**FlashAttention과의 분리**를 언급합니다: 먼저 명시적으로 cache에 쓰고, 그 다음 `flash_attn_*`를 호출하여 cache에서 읽음으로써, 역할이 명확합니다.

## 2. PagedAttention (6문제)

### 1. PagedAttention이란 무엇인가요? 전통적인 Attention과 어떤 차이가 있나요?

**문제:** PagedAttention이란 무엇인가요? 전통적인 Attention과 어떤 차이가 있나요?

**상세 답변:**  
전통적인 구현은 시퀀스당 **연속된** 길이 `max_len`의 KV를 예약하기 쉬워, GPU 메모리 낭비와 파편화 정리가 어렵습니다. PagedAttention은 KV를 **고정 크기의 물리 블록**으로 나누고, **Block Table**을 통해 논리 위치를 비연속적인 물리 블록으로 매핑하는데, 이는 OS 페이징과 유사합니다.  
어텐션 커널은 **block_table에 따른 간접 주소 지정**을 지원해야 합니다(FlashAttention-2의 varlen/with_kvcache 인터페이스). nano-vllm은 decode 경로에서 `block_table=context.block_tables`를 전달합니다.

**nano-vllm 소스 코드와 결합:**  
`prepare_decode`가 `block_tables`를 구성합니다; `flash_attn_with_kvcache(..., block_table=...)`(`attention.py`).

**면접 가산점 기법:**  
한 문장으로: **논리적으로 연속, 물리적으로 이산**이라고 표현하고, vLLM 논문의 동기를 보충하면 됩니다.

---

### 2. Block Table이란 무엇인가요? 논리 블록에서 물리 블록으로의 매핑을 어떻게 유지 관리하나요?

**문제:** Block Table이란 무엇인가요? 논리 블록에서 물리 블록으로의 매핑을 어떻게 유지 관리하나요?

**상세 답변:**  
Block Table은 **각 시퀀스**가 유지 관리하는 배열입니다: i번째 논리 블록이 어느 **물리 block_id**에 대응하는지를 나타냅니다. 추론 시 현재 토큰이 블록 내에서의 오프셋에 따라 **slot**을 계산하여, 쓰기 및 어텐션 주소 지정에 사용합니다.  
유지 관리는 스케줄러가 GPU 메모리를 할당할 때 발생합니다: `allocate`가 `seq.block_table`을 채웁니다; 매 단계 `may_append`가 블록 경계에서 새로운 물리 블록을 확장합니다.

**nano-vllm 소스 코드와 결합:**  
`Sequence.block_table`; `prepare_block_tables`가 텐서로 채우고 -1로 패딩합니다(`model_runner.py`).

**면접 가산점 기법:**  
**논리 토큰 인덱스 → 블록 인덱스 + 블록 내 오프셋 → 물리 slot**을 손으로 그립니다.

---

### 3. nano-vllm의 Block 크기를 왜 256으로 설정했나요?

**문제:** nano-vllm의 Block 크기를 왜 256으로 설정했나요?

**상세 답변:**  
블록 크기는 **세분성과 오버헤드의 절충**입니다: 너무 작으면 block table이 길어지고 관리 오버헤드가 커집니다; 너무 크면 단일 시퀀스의 짧은 요청에서 내부 파편화가 많아집니다. 256은 FlashAttention / GPU warp 친화적인 형상의 일반적인 설정과 일치하며, `Config`에서 `kvcache_block_size % 256 == 0`을 요구하여 커널 정렬을 용이하게 합니다.  
교육용 프로젝트는 보통 vLLM의 기본 경험값을 그대로 따릅니다.

**nano-vllm 소스 코드와 결합:**  
`Sequence.block_size = 256`; `Config.kvcache_block_size: int = 256` 및 assertion(`config.py`, `sequence.py`).

**면접 가산점 기법:**  
'경험적 기본값 + 정렬 + 파편화 트레이드오프'라고 답하고, '유일한 최적값'이라고 단정하지 않습니다.

---

### 4. xxhash 프리픽스 캐시는 어떻게 구현하나요? 체인 해시의 설계 사상은?

**문제:** xxhash 프리픽스 캐시는 어떻게 구현하나요? 체인 해시의 설계 사상은?

**상세 답변:**  
단일 블록 내에서는 토큰 시퀀스에 대해 `xxhash`를 수행하여 지문을 얻습니다. **다중 블록 프리픽스**에 대해서는, **이전 블록의 해시 값을 seed/prefix**로 다음 블록 계산에 전달하여, '동일한 프리픽스 체인'이 자연스럽게 비교 가능한 체인 지문을 얻을 수 있도록 하며, 매번 전체 프리픽스에 대해 재해시할 필요가 없습니다.  
적중 조건: `hash_to_block_id[h]`가 존재하고 **저장된 토큰 리스트가 현재 블록과 완전히 일치**해야 합니다(해시 충돌 방지).

**nano-vllm 소스 코드와 결합:**  
`compute_hash(token_ids, prefix)`; `allocate` 루프 내 `h = self.compute_hash(token_ids, h) if len(token_ids)==block_size else -1`(`block_manager.py`).

**면접 가산점 기법:**  
**체인 해시가 긴 프리픽스의 중복 계산을 낮추는 것**을 강조하고, **충돌 시 토큰 비교로 보완**함을 언급합니다.

---

### 5. Block의 참조 카운트(ref_count)는 어떤 역할을 하나요?

**문제:** Block의 참조 카운트(ref_count)는 어떤 역할을 하나요?

**상세 답변:**  
여러 시퀀스가 동일한 물리 블록을 **공유**할 때(프리픽스 캐시 적중), 한 시퀀스가 종료되었다고 해서 블록을 회수할 수 없습니다. `ref_count`는 몇 개의 논리적 사용자가 보유하고 있는지를 기록하며, 0으로 감소해야 `free_block_ids`에 반환됩니다.  
할당 시 `reset`이 ref를 1로 설정하고, 공유 시 증가합니다.

**nano-vllm 소스 코드와 결합:**  
`allocate`가 사용 중인 블록에 적중 시 `block.ref_count += 1`; `deallocate`는 블록별로 `--`하며, 0이면 `_deallocate_block`(`block_manager.py`).

**면접 가산점 기법:**  
**공유 포인터 / inode 참조**에 비유하면, 면접관이 쉽게 공감합니다.

---

### 6. allocate와 deallocate의 완전한 흐름은 무엇인가요?

**문제:** allocate와 deallocate의 완전한 흐름은 무엇인가요?

**상세 답변:**  
**allocate**: 시퀀스 논리 블록 수만큼 순회하며, 블록별로 토큰을 가져와 해시 적중 시도; 미적중이거나 충돌 시 `free_block_ids`에서 물리 블록을 가져와 `_allocate_block` 초기화, 해시 테이블과 `block_table` 업데이트.  
**deallocate**: `block_table`을 역순으로 순회하며, 참조를 감소시키고, 0이면 `used`에서 제거하고 빈 큐에 추가, 시퀀스 측 캐시 카운트와 테이블을 비웁니다.

**nano-vllm 소스 코드와 결합:**  
`BlockManager.allocate` / `deallocate`(`block_manager.py`).

**면접 가산점 기법:**  
본 구현에서 deallocate가 `reversed`를 사용하는 것은 다른 로직과의 일관성을 위한 것이며, 핵심은 **참조 카운팅과 빈 큐 일관성**에 있다고 설명합니다.

---

## 3. 연속 배치 처리 (5문제)

### 1. 연속 배치 처리란 무엇인가요? 정적 배치 처리와의 차이점은?

**문제:** 연속 배치 처리란 무엇인가요? 정적 배치 처리와의 차이점은?

**상세 답변:**  
연속 배치 처리(continuous batching / iteration-level scheduling)는 **각 디코딩 단계**마다 동적으로 한 무리의 요청을 선택하여 실행하며, 요청은 언제든지 진입/퇴장할 수 있고, 동일한 batch 크기로 끝까지 고정할 필요가 없습니다. 정적 배치 처리는 보통 batch 내 시퀀스 길이가 같거나 동일한 길이로 패딩할 것을 요구하며, GPU 연산 능력이 패딩에 낭비됩니다.  
nano-vllm의 `Scheduler.schedule`은 매 라운드 자원 제약에 따라 배치를 재구성합니다.

**nano-vllm 소스 코드와 결합:**  
`schedule`이 `scheduled_seqs, is_prefill`을 반환합니다(`scheduler.py`).

**면접 가산점 기법:**  
**「반복 레벨」**이지 요청 레벨이 아니라고 요약하고, **KV 블록 동적 할당**과 연결시킵니다.

---

### 2. nano-vllm의 스케줄링 전략은 무엇인가요? (Prefill 우선)

**문제:** nano-vllm의 스케줄링 전략은 무엇인가요?

**상세 답변:**  
구현은 **먼저 가능한 한 waiting 큐에서 요청을 가져와 prefill을 수행**하며, `max_num_seqs` 또는 `max_num_batched_tokens`에 도달하거나 블록 할당이 실패할 때까지 진행합니다. 이번 라운드 prefill이 비어 있을 때만, **decode** 분기로 진입하여 running 큐에서 시퀀스를 가져와 단일 단계 디코딩을 수행합니다.  
이렇게 하면 새 요청의 순전파를 우선 처리하여(프롬프트 처리량 향상), decode가 새 요청을 굶주리게 하는 것을 방지합니다(비즈니스에 따라 조정 가능하며, 일부 시스템에서는 혼합 전략을 사용하기도 합니다).

**nano-vllm 소스 코드와 결합:**  
`schedule`이 먼저 `while self.waiting ...`으로 `True`를 반환; 그렇지 않으면 decode 분기(`scheduler.py`).

**면접 가산점 기법:**  
**공정성 vs 지연**을 논의할 수 있습니다: prefill 우선은 긴 decode 큐를 대기시킬 수 있으며, '산업계에서는 가중치/할당량을 부여한다'고 언급할 수 있습니다.

---

### 3. 선점(preempt) 메커니즘이란 무엇인가요? 언제 발동하나요?

**문제:** 선점(preempt) 메커니즘이란 무엇인가요? 언제 발동하나요?

**상세 답변:**  
decode 단계에서 새 토큰을 위해 **블록을 append**해야 하지만 빈 물리 블록이 부족할 때, 해당 단계를 계속 실행할 수 없습니다. 스케줄러는 **선점**을 선택하여 실행 중인 어떤 시퀀스의 상태를 대기로 되돌리고 **KV 블록을 해제**하여 자원을 확보합니다. 선점된 시퀀스는 이후 다시 prefill을 수행해야 합니다(구현 상으로는 nano-vllm 의미론에서 간소화되어 있습니다).  
발동 조건: `can_append`가 거짓이고 다른 실행 시퀀스로부터 블록을 양보받을 수 없을 때, 어떤 시퀀스에 대해 `preempt`를 수행합니다.

**nano-vllm 소스 코드와 결합:**  
`decode` 분기에서 `while not self.block_manager.can_append(seq)`가 `preempt`를 호출합니다(`scheduler.py`).

**면접 가산점 기법:**  
**GPU 메모리는 하드 제약**이며, 선점은 **배압** 수단임을 설명하고, 운영체제 메모리 페이지 스왑 아웃과 비유합니다.

---

### 4. max_num_seqs와 max_num_batched_tokens의 역할은 무엇인가요?

**문제:** max_num_seqs와 max_num_batched_tokens의 역할은 무엇인가요?

**상세 답변:**  
`max_num_seqs`는 **동일 step 내 동시 시퀀스 수 상한**을 제한하여, decode batch 너비와 스케줄링 상태 규모를 제어합니다. `max_num_batched_tokens`는 **prefill 단계에서 처리하는 토큰 총 수 상한**을 제한하여, 단일 prefill이 너무 긴 시퀀스로 연산 능력이나 GPU 메모리를 가득 채우는 것을 방지합니다. 둘은 공동으로 scheduler 첫 번째 while 루프를 제약합니다.  
설정 요구사항: `max_num_batched_tokens >= max_model_len`이어야 단일 시퀀스가 긴 컨텍스트를 모두 처리할 수 있습니다.

**nano-vllm 소스 코드와 결합:**  
`schedule` 내 조건; `Config` 기본값과 assertion(`config.py`).

**면접 가산점 기법:**  
**OOM과 지연**에 연결시킵니다: 동시성을 늘리면 처리량이 향상되지만 단일 요청 지연이 악화됩니다.

---

### 5. 연속 배치 처리가 GPU 활용률을 어떻게 향상시키나요?

**문제:** 연속 배치 처리가 GPU 활용률을 어떻게 향상시키나요?

**상세 답변:**  
패딩을 줄여, 단계별 **유효 행렬 곱셈 크기**를 하드웨어 포화에 더 가깝게 만들고, 새 요청의 삽입과 완료 요청의 퇴장을 허용하여, '가장 긴 시퀀스를 기다리는' 공회전을 방지합니다. **PagedAttention**과 결합하면, GPU 메모리가 max_len에 따라 선형적으로 폭발하지 않아야 대규모 배치 너비를 지원할 수 있습니다.  
nano-vllm은 `run_model`에서 비교적 큰 decode batch에 대해 CUDA Graph를 사용하여 launch 오버헤드를 낮추고, 유효 처리량을 더욱 향상시킵니다.

**nano-vllm 소스 코드와 결합:**  
`warmup_model`이 가득 찬 설정으로 시퀀스를 구성합니다; `capture_cudagraph`(`model_runner.py`).

**면접 가산점 기법:**  
'공회전 감소 + 유효 batch 토큰 향상 + kernel launch 감소', 세 층위로 점진적으로 답변합니다.

---

## 4. FlashAttention (6문제)

### 1. FlashAttention의 핵심 사상은 무엇인가요?

**문제:** FlashAttention의 핵심 사상은 무엇인가요?

**상세 답변:**  
표준 어텐션은 HBM 읽기/쓰기에 병목이 뚜렷합니다. FlashAttention은 **타일링(tiling)**을 통해 SRAM 상에서 블록별로 softmax 통계량을 누적하여, HBM 왕복을 줄이고, 여러 연산을 **융합**합니다. FlashAttention-2는 병렬화와 work partitioning을 더욱 최적화합니다.  
nano-vllm은 CUDA attention을 직접 작성하지 않고, **flash-attn** 공식 연산자를 호출하며, KV cache 레이아웃과 정렬됩니다.

**nano-vllm 소스 코드와 결합:**  
`flash_attn_varlen_func` / `flash_attn_with_kvcache`(`attention.py`).

**면접 가산점 기법:**  
한 문장: **빠르게 계산하는 것보다 적게 옮기는 것이 낫다**(IO 복잡도는 후술).

---

### 2. flash_attn_varlen_func와 flash_attn_with_kvcache의 차이점은?

**문제:** flash_attn_varlen_func와 flash_attn_with_kvcache의 차이점은?

**상세 답변:**  
`varlen_func`는 **한 무리의 불균등한 길이의 시퀀스가 이어붙여진 긴 텐서**를 대상으로 하며, `cu_seqlens`로 경계를 기술합니다. **prefill** 시 여러 시퀀스를 병렬 처리하고 명시적인 KV cache 텐서가 없는 경우(또는 K/V가 이번에 계산된 텐서인 경우)에 적합합니다.  
`with_kvcache`는 **decode**를 대상으로 합니다: Q는 새 토큰, K/V는 **지속적 cache**에서 오며, `cache_seqlens`, `block_table`과 함께 페이징 주소 지정을 수행합니다.  
nano-vllm은 `is_prefill`에 따라 엄격하게 분기하여 선택합니다.

**nano-vllm 소스 코드와 결합:**  
`Attention.forward` 분기(`attention.py`).

**면접 가산점 기법:**  
**데이터 레이아웃과 API 계약이 다르다**는 점을 강조하며, 혼용할 수 없음을 밝힙니다.

---

### 3. cu_seqlens_q와 cu_seqlens_k의 의미는 무엇인가요?

**문제:** cu_seqlens_q와 cu_seqlens_k의 의미는 무엇인가요?

**상세 답변:**  
둘 모두 **프리픽스 합 배열**(길이 N+1)이며, `cu_seqlens[i+1]-cu_seqlens[i]`는 i번째 시퀀스의 이어붙임 차원 상의 길이입니다. Q와 K는 다를 수 있습니다: 예를 들어 **프리픽스 캐시** 적중 시, 이번 라운드에서는 새 토큰의 Q(짧음)만 계산하지만, K 측은 완전한 컨텍스트(김)를 포함하므로 `cu_seqlens_k[-1] > cu_seqlens_q[-1]`입니다.  
nano-vllm은 `prepare_prefill`에서 `seqlen_q`와 `seqlen_k`를 각각 누적합니다.

**nano-vllm 소스 코드와 결합:**  
`prepare_prefill` 루프 내 업데이트; prefix 시 `block_tables` 준비(`model_runner.py`).

**면접 가산점 기법:**  
**두 개의 프리픽스 합 곡선**을 손으로 그리고, prefix cache 시나리오를 설명합니다.

---

### 4. 왜 Prefill은 varlen_func를 사용하고 Decode는 with_kvcache를 사용하나요?

**문제:** 왜 Prefill은 varlen_func를 사용하고 Decode는 with_kvcache를 사용하나요?

**상세 답변:**  
Prefill은 주로 **대량의 새 토큰**에 대한 어텐션을 계산하므로, varlen 배치 처리에 적합합니다. 또한 이때 K/V는 계산에서 직접 유입되거나 유연한 레이아웃이 필요합니다. Decode는 단계마다 **시퀀스당 1개의 query**만 있으며, HBM에서 전체 K/V를 반복적으로 읽는 것은 이미 **cache + 단일 단계 인터페이스**로 최적화되어 있으며, `with_kvcache`가 **쓰기와 읽기**를 페이징 정보와 함께 캡슐화합니다.  
nano-vllm은 또한 prefill 쓰기 단계에서 Triton으로 명시적으로 `store_kvcache`를 수행한 후, cache를 읽어 어텐션을 수행하므로 경로가 명확합니다.

**nano-vllm 소스 코드와 결합:**  
`store_kvcache` + 두 분기(`attention.py`).

**면접 가산점 기법:**

### 5. FlashAttention v1 / v2 / v3의 진화는?

## 5. 텐서 병렬 (6문제)

### 1. 텐서 병렬이란 무엇인가요? 데이터 병렬, 파이프라인 병렬과의 차이점은?

**문제:** 텐서 병렬이란 무엇인가요? 데이터 병렬, 파이프라인 병렬과의 차이점은?

**상세 답변:**  
**텐서 병렬(TP)**은 단일 레이어 내 대형 행렬 곱셈을 열/행 기준으로 여러 GPU로 분할하고, 각 카드는 일부 가중치를 저장하며, 순전파 시 통신을 통해 완전한 결과를 조합합니다. **데이터 병렬(DP)**은 카드마다 완전한 모델을 가지고 다른 batch를 처리하며, 그래디언트를 동기화합니다. **파이프라인 병렬(PP)**은 레이어별로 다른 디바이스로 분할하고, 마이크로배치 파이프라인을 구성합니다.  
nano-vllm은 **단일 머신 멀티 카드 TP**를 구현하며(`dist.init_process_group`), PP는 없습니다.

**nano-vllm 소스 코드와 결합:**  
`ModelRunner`가 NCCL을 초기화합니다; `linear.py` 내 `dist.get_world_size()`.

**면접 가산점 기법:**  
한 마디로: **TP는 레이어 내 텐서 분할, PP는 레이어 간 분할, DP는 batch 분할**.

---

### 2. 열 병렬(ColumnParallel)과 행 병렬(RowParallel)의 원리는?

**문제:** 열 병렬과 행 병렬의 원리는?

**상세 답변:**  
선형 레이어 `Y = XA^T`: 열 병렬은 **출력 차원**을 분할하며, 각 카드는 출력의 일부를 계산합니다. 만약 완전한 출력이 필요하면 concat하거나 후속 레이어가 샤드 입력을 받아들여야 합니다. 행 병렬은 **입력 차원**을 분할하며, 각 카드는 부분 내적을 계산하고, **결과는 all-reduce 합산**이 필요하여 완전한 출력을 얻습니다.  
Transformer에서 흔한 패턴: **Attention QKV 열 병렬**, **출력 투영 행 병렬**, 통신 횟수를 줄입니다.

**nano-vllm 소스 코드와 결합:**  
`ColumnParallelLinear`는 `output_size`를 분할합니다; `RowParallelLinear`는 `input_size`를 분할하고 forward 내에서 `all_reduce`합니다(`linear.py`).

**면접 가산점 기법:**  
**작은 행렬 블록 곱셈**을 손으로 써서 보여줍니다.

---

### 3. QKVParallelLinear의 샤딩 전략은?

**문제:** QKVParallelLinear의 샤딩 전략은?

**상세 답변:**  
Q, K, V 세 부분을 **하나의 큰 출력 차원으로 이어붙이고**, 다시 열 병렬 규칙에 따라 각 TP rank로 분할합니다. 가중치 로딩 시 **shard_id**(q/k/v)에 따라 해당 구간을 이 카드의 파라미터 서브 블록에 기록합니다.  
헤드 수와 KV 헤드 수는 TP로 나누어 떨어져야 합니다.

**nano-vllm 소스 코드와 결합:**  
`QKVParallelLinear`의 `output_size`와 `weight_loader`(`linear.py`).

**면접 가산점 기법:**  
**선형 레이어 병합으로 커널 횟수를 줄이는** 공학적 이득을 강조합니다.

### 4. AllReduce 통신의 오버헤드 분석은?

**문제:** AllReduce 통신의 오버헤드 분석은?

**상세 답변:**  
RowParallel 후 각 카드는 부분 합을 얻으며, 완전한 벡터를 얻으려면 all-reduce가 필요합니다. 복잡도는 **벡터 길이, 카드 수, 네트워크 토폴로지**에 따라 변합니다. NCCL은 ring/tree 등의 알고리즘을 선택합니다. TP는 **작은 batch decode** 시 통신 비중이 올라갈 수 있으며, 이는 혼합 병렬 전략에서 트레이드오프해야 할 지점입니다.  
nano-vllm은 `RowParallelLinear`와 `VocabParallelEmbedding`에서 all_reduce를 사용합니다.

**nano-vllm 소스 코드와 결합:**  
`dist.all_reduce(y)`(`linear.py`); Embedding forward(`embed_head.py`).

**면접 가산점 기법:**  
**batch 크기 및 hidden 크기와 비례**한다고 언급하고, **멀티 카드 확장성의 비선형성**과 연결시킵니다.

### 5. VocabParallelEmbedding은 어떻게 어휘 병렬을 구현하나요?

**문제:** VocabParallelEmbedding은 어떻게 어휘 병렬을 구현하나요?

**상세 답변:**  
어휘 차원을 여러 구간으로 나누어, 각 카드는 **일부 embedding**만 저장합니다. 순전파 시: 만약 토큰 id가 이 카드의 구간에 속하면 테이블을 조회하여 벡터를 얻고, 그렇지 않으면 0으로 합니다. 다시 **all_reduce**로 각 카드의 기여도를 집계하여, 완전한 embedding을 얻습니다(마스크로 잘못된 누적 방지).  
nano-vllm은 `mask`와 `vocab_start_idx`/`vocab_end_idx`로 판단합니다.

**nano-vllm 소스 코드와 결합:**  
`VocabParallelEmbedding.forward`(`embed_head.py`).

**면접 가산점 기법:**  
**테이블 조회는 희소하다**는 점을 대비시킵니다: 토큰당 하나의 파티션에만 적중하므로, mask+reduce를 사용합니다.

### 6. ParallelLMHead는 어떻게 gather로 logits를 수집하나요?

**문제:** ParallelLMHead는 어떻게 gather로 logits를 수집하나요?

**상세 답변:**  
LM Head의 본질은 `hidden @ W^T`이며, 열 병렬 하에서 각 카드는 일부 어휘 열만 보유하므로, **부분 logits**를 얻습니다. **rank0**에서 `gather`로 각 카드의 logits를 모은 후 `cat`하여 완전한 어휘 차원으로 만들어야 합니다. Prefill 시에는 `cu_seqlens_q`에 따라 **시퀀스당 마지막 query** 위치를 취하여, 중간 위치에 대해 샘플링하는 것을 방지합니다.  
nano-vllm은 `dist.gather`를 사용하며(all_gather 변형이 아님), rank0이 수집합니다.

**nano-vllm 소스 코드와 결합:**  

```56:66:nano-vllm-main/nanovllm/layers/embed_head.py
    def forward(self, x: torch.Tensor):
        context = get_context()
        if context.is_prefill:
            last_indices = context.cu_seqlens_q[1:] - 1
            x = x[last_indices].contiguous()
        logits = F.linear(x, self.weight)
        if self.tp_size > 1:
            all_logits = [torch.empty_like(logits) for _ in range(self.tp_size)] if self.tp_rank == 0 else None
            dist.gather(logits, all_logits, 0)
            logits = torch.cat(all_logits, -1) if self.tp_rank == 0 else None
```

**면접 가산점 기법:**  
**prefill 시 마지막 토큰 취함**과 **decode 시 시퀀스당 단일 토큰**의 차이를 설명합니다.

## 6. CUDA Graph (4문제)

### 1. CUDA Graph란 무엇인가요? 왜 추론을 가속화하나요?

**문제:** CUDA Graph란 무엇인가요? 왜 추론을 가속화하나요?

**상세 답변:**  
CUDA Graph는 일련의 커널과 그 의존성을 하나의 그래프로 **녹화(recording)**하고, 이후 **재생(replay)** 시 CPU 측 제출 오버헤드와 일부 스케줄링 지연을 줄여, **형상이 안정적이고 제어 흐름이 고정된** 반복 실행에 적합합니다.  
decode 단계의 형상은 보통 'batch × 단일 토큰'으로, 그래프 녹화에 비교적 적합합니다.

**nano-vllm 소스 코드와 결합:**  
`capture_cudagraph`와 `graph.replay()`(`model_runner.py`).

**면접 가산점 기법:**  
**동적 shape의 빈번한 재녹화** 비용과 대비시킵니다.

---

### 2. 왜 Decode 단계에만 CUDA Graph를 사용하나요?

**문제:** 왜 Decode 단계에만 CUDA Graph를 사용하나요?

**상세 답변:**  
Prefill의 **시퀀스 길이와 이어붙임 길이**는 변화가 크며, 또한 `input_ids.size(0) > 512` 등의 분기를 자주 발동시킵니다. decode 단계는 **batch 내 토큰 수가 시퀀스 수와 같아**, 형상이 비교적 안정적입니다. nano-vllm은 `run_model`에서: `is_prefill` 또는 `enforce_eager` 또는 batch 토큰 수>512 시 eager 경로를 사용합니다.

**nano-vllm 소스 코드와 결합:**  
`run_model` 조건(`model_runner.py`).

**면접 가산점 기법:**  
**그래프 녹화에는 워밍업과 GPU 메모리 점유**(그래프 풀)가 필요함을 언급합니다.

---

### 3. graph_bs의 이산 batch size 설계는 어떤 고려 사항이 있나요?

**문제:** graph_bs의 이산 batch size 설계는 어떤 고려 사항이 있나요?

**상세 답변:**  
실제 동시 시퀀스 수는 임의의 정수에 분포합니다. 만약 각 bs마다 하나의 그래프를 녹화하면, **컴파일과 저장 오버헤드**가 과도하게 커집니다. 이산화는 **현재 bs 이상인 최소 사전 녹화 bs**(`next(x for x in graph_bs if x >= bs)`)를 사용하여, `graph_vars`에서 앞쪽 bs개의 슬롯만 채우고 나머지는 유효 계산에 참여하지 않습니다.  
시퀀스: `[1,2,4,8]` 그 후 16씩 증가하여 max까지.

**nano-vllm 소스 코드와 결합:**  
`self.graph_bs = [1, 2, 4, 8] + list(range(16, max_bs + 1, 16))` 및 `run_model`에서 그래프 선택(`model_runner.py`).

**면접 가산점 기법:**  
**패딩으로 소량의 연산 능력을 낭비**하는 대신 **범용성과 녹화 그래프 수를 통제 가능하게** 한다는 점을 인정합니다.

### 4. CUDA Graph의 제한 사항은 무엇인가요?

**문제:** CUDA Graph의 제한 사항은 무엇인가요?

**상세 답변:**  
제한 사항으로는: **동적 제어 흐름**, 빈번한 shape 변화, **메모리 주소 고정**에 대한 세심한 처리 필요, 디버깅 어려움, 일부 **비동기 복사/멀티 스트림**과의 복잡한 상호작용 등이 있습니다. nano-vllm은 `enforce_eager`로 그래프를 비활성화하여 디버깅을 용이하게 합니다.  
rank>0 프로세스는 SharedMemory를 통해 호출되는 경로와 주 프로세스의 그래프 녹화가 일관되어야 합니다(프로젝트에서는 rank0이 주 실행).

**nano-vllm 소스 코드와 결합:**  
`if not self.enforce_eager: self.capture_cudagraph()`(`ModelRunner.__init__`).

**면접 가산점 기법:**  
**「그래프 녹화 조건이 까다롭다」**라고 나열하는 것으로 충분하며, 문제 해결 경험을 보여줍니다.

## 7. RoPE (4문제)

### 2. inv_freq는 어떻게 계산되나요?

**문제:** inv_freq는 어떻게 계산되나요?

**상세 답변:**  
차원 인덱스를 짝수 단계로 샘플링하여, `inv_freq = 1 / (base ** (i/rotary_dim))`로 하면, 서로 다른 차원이 서로 다른 주파수에 대응하여, 다중 주파수 사인 코사인 기저를 형성합니다. 위치 t와 inv_freq의 외적으로 `freqs`를 얻고, 다시 cos/sin을 구합니다.  
`base`는 보통 하이퍼파라미터입니다(예: rope_theta).

**nano-vllm 소스 코드와 결합:**  

```29:34:nano-vllm-main/nanovllm/layers/rotary_embedding.py
        inv_freq = 1.0 / (base**(torch.arange(0, rotary_dim, 2, dtype=torch.float) / rotary_dim))
        t = torch.arange(max_position_embeddings, dtype=torch.float)
        freqs = torch.einsum("i,j -> ij", t, inv_freq)
        cos = freqs.cos()
        sin = freqs.sin()
```

**면접 가산점 기법:**  
**Transformer 사인 위치 인코딩의 주파수 형식과 유사함**을 지적합니다.

### 3. apply_rotary_emb의 구현 원리는?

**문제:** apply_rotary_emb의 구현 원리는?

**상세 답변:**  
마지막 차원을 두 부분으로 나누어 `(x1, x2)`로 하고, 회전 공식 `y1 = x1*cos - x2*sin`, `y2 = x2*cos + x1*sin`에 따라 계산한 후 다시 이어붙입니다. 캐시된 cos/sin(positions 인덱스에서 가져옴)과 곱합니다.  
float 중간 정밀도를 사용한 후 원래 dtype으로 캐스트하여 수치 문제를 줄입니다.

**nano-vllm 소스 코드와 결합:**  
`apply_rotary_emb`(`rotary_embedding.py`).

**면접 가산점 기법:**  
**q, k에만 적용하고 v에는 적용하지 않는다**는 점을 언급합니다(표준 관행).

### 4. RoPE의 길이 외삽 방법에는 어떤 것들이 있나요? (NTK-aware, YaRN 등)

**문제:** RoPE의 길이 외삽 방법에는 어떤 것들이 있나요?

**상세 답변:**  
일반적인 방법으로는: **NTK-aware**(base 또는 주파수를 스케일링하여 고주파 감쇠를 늦춤), **YaRN**(구간별 혼합 스케일링과 어텐션 온도 보정), **위치 보간 PI** 등이 있습니다. nano-vllm의 `get_rope`에서는 **`rope_scaling`을 직접 assert None**으로 하여, 교육용 코드에서는 이러한 변형을 구현하지 않았으나, 모델 설정에서 자리 표시자를 전달할 수 있습니다.

**nano-vllm 소스 코드와 결합:**  
`get_rope` 내 `assert rope_scaling is None`(`rotary_embedding.py`).

**면접 가산점 기법:**  
**프로젝트가 간소화를 위해 생략**했으며, 실제 운영 시 HF 동일 구현을 연결해야 한다고 설명합니다.

## 8. GQA / MQA / MHA (4문제)

### 1. MHA, MQA, GQA의 차이점은?

**문제:** MHA, MQA, GQA의 차이점은?

**상세 답변:**  
**MHA**: Q/K/V 헤드 수가 같습니다. **MQA**: 여러 Q가 단일 K/V를 공유합니다. **GQA**: K/V 헤드 수가 Q 헤드 수의 약수로, 그룹 내에서 공유합니다.  
목적: KV 메모리와 대역폭을 줄이고, 구현 복잡도가 약간 증가합니다.

**nano-vllm 소스 코드와 결합:**  
`num_key_value_heads`는 HF config에서 옵니다; `Attention` 내 `num_kv_heads`(`qwen3.py`).

**면접 가산점 기법:**  
**KV 대역폭** 관점에서 추론 친화적임을 설명합니다.

---

### 2. nano-vllm에서 GQA는 어떻게 구현되나요?

**문제:** nano-vllm에서 GQA는 어떻게 구현되나요?

**상세 답변:**  
모델 측 `QKVParallelLinear` 출력은 여전히 Q와 K/V 구간으로 나뉩니다; `k`, `v`는 `num_kv_heads`로 reshape되며, FlashAttention 내부에서 **Q 헤드와 KV 헤드의 브로드캐스트/그룹화**를 담당합니다(flash-attn 구현). KV cache 형상은 **실제 kv 헤드 수**에 따라 할당되어, 현저히 메모리를 절약합니다.  
TP 하에서 헤드 수는 나누어 떨어져야 합니다.

**nano-vllm 소스 코드와 결합:**  
`Qwen3Attention` 내 `total_num_kv_heads`와 `view(-1, self.num_kv_heads, head_dim)`(`qwen3.py`).

**면접 가산점 기법:**  
**절약하는 것은 cache와 대역폭이지, Q 계산이 아니다**라고 강조합니다.

---

### 3. GQA의 KV 헤드 수와 Q 헤드 수의 비례 관계는?

**문제:** GQA의 KV 헤드 수와 Q 헤드 수의 비례 관계는?

**상세 답변:**  
Q 헤드 수를 `H`, KV 헤드 수를 `H_kv`라 하면, 보통 `H % H_kv == 0`이며, 각 그룹 `H/H_kv`개의 Q 헤드가 한 쌍의 KV를 공유합니다. nano-vllm은 설정이 나누어 떨어지고 TP 분할을 만족한다고 가정합니다.

**nano-vllm 소스 코드와 결합:**  
`divide(total_num_kv_heads, tp_size)`(`linear.py`).

**면접 가산점 기법:**  
**8:2** 예시를 들어 빠르게 설명합니다.

---

### 4. GQA가 GPU 메모리와 계산에 미치는 영향은?

**문제:** GQA가 GPU 메모리와 계산에 미치는 영향은?

**상세 답변:**  
GPU 메모리: KV cache가 `num_kv_heads`에 따라 선형적으로 감소합니다. 계산: Q는 여전히 멀티헤드이며, 어텐션 중 **K/V와 관련된 메모리 대역폭**이 감소합니다. 전체적으로 **긴 컨텍스트 decode**에 더 유리합니다.  
nano-vllm의 `block_bytes`는 `num_kv_heads`(이미 TP)를 사용하여 계산에 포함합니다.

**nano-vllm 소스 코드와 결합:**  
`allocate_kv_cache`(`model_runner.py`).

**면접 가산점 기법:**  
**Attention IO 병목**과 연결시킵니다.

## 9. Sampler / Decoding 전략 (5문제)

### 1. 온도 샘플링의 원리는?

**문제:** 온도 샘플링의 원리는?

**상세 답변:**  
logits를 온도 T로 나눕니다: T>1 분포가 더 평평해짐(탐험 증가); T<1 더 뾰족해짐(더 확정적). 그 후 분포에서 샘플링합니다. 수학적으로는 softmax의 엔트로피를 조정하는 것과 동등합니다.  
nano-vllm은 sampler에서 logits를 온도로 스케일링한 후 softmax합니다.

**nano-vllm 소스 코드와 결합:**  
`logits.float().div_(temperatures.unsqueeze(dim=1))` 후 `softmax`(`sampler.py`).

**면접 가산점 기법:**  
**수치 안정성**을 언급합니다: 먼저 max를 뺀 후 softmax(만약 직접 작성한다면); 본 프로젝트는 PyTorch softmax에 의존합니다.

---

### 2. nano-vllm의 Gumbel-max 샘플링 기법은?

**문제:** nano-vllm의 Gumbel-max 샘플링 기법은?

**상세 답변:**  
Gumbel-max 기법: 카테고리 k에 대해 독립적으로 Gumbel 노이즈 `g_k`를 샘플링하고, `argmax(log p_k + g_k)`를 취하는 것은 softmax(p)에서 샘플링하는 것과 동등합니다. 구현 상의 동등 변형: **지수 분포** 노이즈와 확률을 나눈 후 argmax(지수 분포와 Gumbel은 변환 가능한 관계).  
nano-vllm은 `probs.div_(exponential(1)).argmax`를 사용합니다.

**nano-vllm 소스 코드와 결합:**  

```10:15:nano-vllm-main/nanovllm/layers/sampler.py
    @torch.compile
    def forward(self, logits: torch.Tensor, temperatures: torch.Tensor):
        logits = logits.float().div_(temperatures.unsqueeze(dim=1))
        probs = torch.softmax(logits, dim=-1)
        sample_tokens = probs.div_(torch.empty_like(probs).exponential_(1).clamp_min_(1e-10)).argmax(dim=-1)
```

**면접 가산점 기법:**  
**명시적 multinomial 없음**, **GPU 벡터화에 적합**함을 설명합니다.

---

### 3. Top-k / Top-p 샘플링 원리는?

**문제:** Top-k / Top-p 샘플링 원리는?

**상세 답변:**  
**Top-k**: 확률이 가장 높은 k개의 토큰에 대해서만 재정규화하고 샘플링합니다. **Top-p(nucleus)**: 확률을 큰 것부터 작은 것까지 누적하여 임계값 p를 초과할 때까지 더한 프리픽스를 잘라내고, 그 후 재정규화하여 샘플링합니다.  
nano-vllm은 **top-k/top-p를 구현하지 않았으며**, 기본 온도+Gumbel-max식 샘플링만 있습니다. 면접에서 확장 포인트를 설명할 수 있습니다.

**nano-vllm 소스 코드와 결합:**  
`sampler.py`에는 top-k/p가 없습니다.

**면접 가산점 기법:**  
정직하게 + **만약 내가 한다면 softmax 후 플러그 가능한 전략으로 추가할 것입니다**.

---

### 4. 추측적 디코딩(Speculative Decoding)이란 무엇인가요?

**문제:** 추측적 디코딩(Speculative Decoding)이란 무엇인가요?

**상세 답변:**  
작은 모델 또는 초안 모델로 **다단계 예측** 후보 토큰을 생성하고, 대형 모델이 병렬로 검증하여, 수락되면 생성을 가속하고, 거부되면 롤백합니다. 지연을 낮출 수 있지만 시스템 복잡도를 증가시킵니다. nano-vllm은 **구현하지 않았습니다**.

**면접 가산점 기법:**  
**검증 병렬화**와 **수락률**이 핵심임을 언급합니다.

---

### 5. 왜 nano-vllm은 탐욕적 디코딩을 지원하지 않나요?

**문제:** 왜 nano-vllm은 탐욕적 디코딩을 지원하지 않나요?

**상세 답변:**  
탐욕적 디코딩은 **온도→0** 또는 argmax로 직접 최대값을 취하는 것과 동등합니다. 프로젝트는 `SamplingParams`를 통해 **극도로 낮은 온도를 금지**하며, `temperature > 1e-10`을 assert하여, '탐욕적 디코딩을 지원한다고 주장'하지만 샘플링 구현과 불일치하는 것을 원천적으로 방지합니다. 또한 sampler 경로는 **무작위 샘플링** 구현입니다. 탐욕적 디코딩을 하려면 코드를 변경하여 `argmax` 분기를 추가해야 합니다.

**nano-vllm 소스 코드와 결합:**  

```10:12:nano-vllm-main/nanovllm/sampling_params.py
    def __post_init__(self):
        assert self.temperature > 1e-10, "greedy sampling is not permitted"
```

**면접 가산점 기법:**  
**교육용 프로젝트의 간소화와 API 일관성**으로 표현하여, 면접관의 수치적 코너 케이스 추궁을 피합니다.

### 2. 양자화(INT8 / INT4)의 기본 원리는?

**문제:** 양자화(INT8 / INT4)의 기본 원리는?

nano-vllm 예제는 bf16/fp16 경로이며, **GPTQ/AWQ 로딩이 내장되어 있지 않습니다**. vLLM과 비교할 수 있습니다.

### 3. AWQ와 GPTQ의 차이점은?

**문제:** AWQ와 GPTQ의 차이점은?

**상세 답변:**

### 5. pin_memory와 non_blocking 전송의 역할은?

**문제:** pin_memory와 non_blocking 전송의 역할은?

## 11. Triton 프로그래밍 (4문제)

### 2. @triton.jit의 작동 원리는?

**문제:** @triton.jit의 작동 원리는?

**상세 답변:**  
데코레이터가 파이썬 함수를 **JIT 컴파일**하여 GPU 커널로 만듭니다. 첫 호출 시 **템플릿 파라미터(constexpr)**와 그리드 설정에 따라 컴파일 캐시됩니다. 함수 내에서는 `tl` 네임스페이스를 사용하여 SIMD 연산을 표현합니다.

**nano-vllm 소스 코드와 결합:**

**면접 가산점 기법:**  
**컴파일 캐시와 첫 호출이 느리다**는 점을 언급합니다.

---

### 3. tl.program_id, tl.arange의 의미는?

**문제:** tl.program_id, tl.arange의 의미는?

**상세 답변:**  
`tl.program_id(axis)`는 현재 **program(블록과 유사)**의 지정 축 상의 인덱스를 반환합니다; `tl.arange`는 0..N-1의 1차원 벡터를 생성하여, load/store 포인터 오프셋을 구성하는 데 사용합니다.  
`store_kvcache_kernel`에서 `idx = tl.program_id(0)`는 몇 번째 토큰에 대응합니다.

**nano-vllm 소스 코드와 결합:**  
`store_kvcache_kernel` 내(`attention.py`).

**면접 가산점 기법:**  
CUDA의 `blockIdx`와 `threadIdx`의 분업에 비유합니다(Triton은 레벨이 다름).

---

### 4. store_kvcache_kernel의 설계 사상은?

**문제:** store_kvcache_kernel의 설계 사상은?

**상세 답변:**  
각 program이 하나의 토큰을 담당합니다: `slot_mapping`을 읽어 전역 slot을 얻고, 유효하지 않으면 반환합니다. K/V 포인터를 stride에 따라 길이 D=`num_heads*head_dim`의 벡터로 펼쳐 load한 후, cache의 `slot*D` 오프셋에 기록합니다.  
**헤드 차원을 병합**하여 하나의 벡터로 만들면, 주소 지정이 단순화됩니다. `D`는 `constexpr`로 하여 컴파일러 최적화를 용이하게 합니다.

**nano-vllm 소스 코드와 결합:**  
완전한 kernel(`attention.py`).

**면접 가산점 기법:**  
**FlashAttention과 분리된 명시적 쓰기**를 강조하며, KV 레이아웃 디버깅에 용이함을 밝힙니다.

## 12. 모델 아키텍처 (5문제)

### 1. Qwen3의 전체 아키텍처는?

**문제:** Qwen3의 전체 아키텍처는?

**상세 답변:**  
Decoder-only Transformer: **Embedding → N × DecoderLayer(Pre-Norm: RMSNorm + 셀프 어텐션 + RMSNorm + SwiGLU MLP) → 최종 RMSNorm → LMHead**.  
nano-vllm은 `Qwen3Model` + `Qwen3ForCausalLM`으로 포장합니다.

**nano-vllm 소스 코드와 결합:**  
`qwen3.py` 내 `Qwen3Model`, `Qwen3DecoderLayer`.

**면접 가산점 기법:**  
한 마디: **디코더 전용, 인과 마스크, 교차 어텐션 없음**.

---

### 2. SwiGLU 활성화 함수의 원리는? (SiLU 게이팅)

**문제:** SwiGLU 활성화 함수의 원리는?

**상세 답변:**  
SwiGLU는 은닉층을 gate와 up 두 경로로 나눕니다: `SiLU(gate) * up`, 그 후 down 투영을 거칩니다. `SiLU`는 시그모이드 가중 x입니다. 단일 ReLU/GELU보다 표현력이 강하고, 파라미터가 약간 증가합니다.  
nano-vllm은 `MergedColumnParallelLinear`로 두 배의 중간 차원을 출력하고, 다시 `SiluAndMul`을 사용합니다.

**nano-vllm 소스 코드와 결합:**  
`Qwen3MLP` + `SiluAndMul`(`qwen3.py`, `activation.py`).

**면접 가산점 기법:**  
**게이트 곱셈 문**을 그립니다.

---

### 3. RMSNorm vs LayerNorm?

**문제:** RMSNorm vs LayerNorm?

**상세 답변:**  
RMSNorm은 평균을 빼지 않고, **제곱 평균 제곱근**으로만 스케일링하며, 파라미터가 더 적고 계산 비용이 더 낮습니다. LLM에서 Pre-Norm과 함께 사용하면 학습이 안정적입니다. LayerNorm은 평균을 빼고 분산으로 정규화합니다.  
nano-vllm은 전부 `RMSNorm`을 사용합니다.

**nano-vllm 소스 코드와 결합:**  
`layernorm.py`(존재하는 경우); `Qwen3DecoderLayer`가 참조합니다.

**면접 가산점 기법:**  
**Pre-Norm이 그래디언트를 완화한다**는 점을 언급합니다. 추론과는 무관하지만 자주 추궁받습니다.

---

### 4. Pre-Norm vs Post-Norm?

**문제:** Pre-Norm vs Post-Norm?

**상세 답변:**  
Pre-Norm은 LN을 서브레이어의 **입력**에 배치하여, 학습이 더 안정적이고 깊게 쌓기 쉽습니다. Post-Norm은 LN을 **출력**에 배치하며, 고전적인 Transformer의 원래 설계입니다. 현대 LLM은 대부분 Pre-Norm입니다.  
nano-vllm `Qwen3DecoderLayer`: `input_layernorm`이 어텐션 앞에, `post_attention_layernorm`이 MLP 앞에 있어, Pre-Norm 구조에 속합니다.

**nano-vllm 소스 코드와 결합:**  
`forward` 파라미터 `residual`(`qwen3.py`).

**면접 가산점 기법:**  
**잔차 분기**와 결합하여 설명합니다.

---

### 5. packed_modules_mapping 가중치 매핑의 설계는?

**문제:** packed_modules_mapping 가중치 매핑의 설계는?

**상세 답변:**  
HF 가중치는 보통 `q_proj/k_proj/v_proj`로 나뉘어 있지만, 공학적으로 `qkv_proj`로 병합하여 커널을 줄입니다. `packed_modules_mapping`은 **이전 이름→새 모듈 이름 + 샤드 식별자**를 기술하며, 로딩 시 이름을 대체하고 해당 `weight_loader`를 호출합니다.  
`gate_proj/up_proj`가 `gate_up_proj`로 병합되는 것도 같은 이치입니다.

**nano-vllm 소스 코드와 결합:**  

```186:192:nano-vllm-main/nanovllm/models/qwen3.py
    packed_modules_mapping = {
        "q_proj": ("qkv_proj", "q"),
        "k_proj": ("qkv_proj", "k"),
        "v_proj": ("qkv_proj", "v"),
        "gate_proj": ("gate_up_proj", 0),
        "up_proj": ("gate_up_proj", 1),
    }
```

`load_model`에서 루프 매칭(`loader.py`).

**면접 가산점 기법:**  
**safetensors 키 이름과 일대일 대응**하는 유지보수성을 강조합니다.

## 13. 시스템 설계 (5문제)

### 1. nano-vllm의 전체 아키텍처 설계는?

**문제:** nano-vllm의 전체 아키텍처 설계는?

**상세 답변:**  
**LLMEngine**이 **Scheduler**(CPU 측 스케줄링)와 **ModelRunner**(GPU 실행 + 가중치)를 보유합니다. `step`이 동기적으로 `run`을 호출하여 한 번의 prefill 또는 decode를 완료합니다. 멀티 카드 TP 시 rank0이 주 프로세스이고, 다른 rank는 **SharedMemory + Event**로 명령을 받아 동일 구조의 `ModelRunner` 메서드를 실행합니다.  
전역 `Context`가 어텐션 메타데이터를 전달합니다.

**nano-vllm 소스 코드와 결합:**  
`llm_engine.py`, `model_runner.py`, `context.py`.

**면접 가산점 기법:**  
**한 장의 그림**을 그립니다: 요청 → 스케줄링 → runner → kernel.

---

### 2. SharedMemory 다중 프로세스 통신의 구현은?

**문제:** SharedMemory 다중 프로세스 통신의 구현은?

**상세 답변:**  
rank0 `write_shm`: pickle로 직렬화한 `[method_name, args]`를 공유 메모리에 4바이트 길이 프리픽스로 기록합니다; 자식 프로세스에 대해 `event.set()`. 자식 프로세스 `read_shm`: `event.wait()` 후 길이와 payload를 읽고, `pickle.loads`, `clear` 이벤트.  
메서드 이름 `"exit"`으로 루프를 종료합니다.

**nano-vllm 소스 코드와 결합:**  
`read_shm`/`write_shm`/`loop`(`model_runner.py`).

**면접 가산점 기법:**  
**pickle 오버헤드**와 프로덕션에서 **더 긴밀한 프로토콜**을 사용하는 것의 대비를 언급합니다.

---

### 3. Event 동기화 메커니즘의 역할은?

**문제:** Event 동기화 메커니즘의 역할은?

**상세 답변:**  
**쓰기 측이 완료된 후 읽도록** 보장하여, 반쯤 전송된 패킷 데이터를 읽는 것을 방지합니다. 여러 자식 프로세스가 있을 때 `event` 리스트에 대해 통일적으로 `set`하여, **한 번의 호출로 모든 워커를 깨우는** 것을 구현합니다.

**nano-vllm 소스 코드와 결합:**  
`write_shm` 끝에 `for event in self.event: event.set()`.

**면접 가산점 기법:**  
**조건 변수**에 비유하며, **다중 프로세스 무잠금 큐는 쌍을 이루는 동기화가 필요**함을 강조합니다.

---

### 4. 추론 처리량을 어떻게 계산하나요?

**문제:** 추론 처리량을 어떻게 계산하나요?

**상세 답변:**  
**Prefill 처리량**: 처리한 총 프롬프트 토큰 수 / 소요 시간(tokens/s). **Decode 처리량**: 생성 토큰 수 / 소요 시간; 여러 시퀀스일 경우 **총 생성 토큰**으로 계산합니다. 첫 토큰 지연(TTFT)은 보통 별도로 통계를 냅니다.  
nano-vllm은 `generate`에서 `num_tokens`의 부호로 prefill/decode를 구분하고 처리량을 추정합니다(`llm_engine.py`).

**nano-vllm 소스 코드와 결합:**  
`step`이 `num_tokens` 반환; `generate` 내 `perf_counter`(`llm_engine.py`).

**면접 가산점 기법:**  
**토크나이즈 전후**를 구분하여 포함 여부를 따집니다.

---

### 5. GPU 메모리 관리의 전체 전략은?

**문제:** GPU 메모리 관리의 전체 전략은?

**상세 답변:**  
가중치 점유 + KV 블록 풀(이용률과 피크에서 추정) + 런타임 활성화. 요청 수준 스왑은 없으며, **스케줄링 거부/선점**과 **블록 할당 실패**로 제어합니다. CUDA Graph는 별도로 **그래프 풀** GPU 메모리가 필요합니다.  
다중 프로세스 rank는 각각 `cuda` 디바이스.

**nano-vllm 소스 코드와 결합:**  
`allocate_kv_cache`; `Scheduler` 및 `BlockManager`.

**면접 가산점 기법:**  
vLLM의 **더 완전한 메모리 분석과 교환**과 대비시킵니다.
