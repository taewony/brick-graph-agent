# 강의 13: 연속 배치 처리(Continuous Batching)

본 강의는 대규모 모델 추론에서의 **연속 배치 처리** 기술을 깊이 있게 다룹니다. 이는 vLLM/nano-vllm이 높은 처리량 추론을 달성할 수 있는 핵심 스케줄링 전략입니다. 우리는 정적 배치 처리의 한계에서 출발하여 연속 배치 처리의 원리를 단계적으로 유도하고, nano-vllm 소스 코드와 결합하여 그 구체적인 구현을 분석하며, 업계 주류 솔루션과 비교할 것입니다.

## 1. 복습: 추론 엔진에 배치 처리가 필요한 이유

### 1.1 단일 요청 추론의 병목

Decode 단계에서, 각 단계는 **1개의 토큰**만 처리하지만, GPU 메모리에서 전체 모델 가중치를 로드해야 합니다. 7B 파라미터 모델(FP16)을 예로 들면:

- **모델 가중치 크기**: \( 7 \times 10^9 \times 2 \text{ bytes} = 14 \text{ GB} \)
- **단일 토큰 계산량**: 약 \( 2 \times 7 \times 10^9 = 14 \text{ GFLOPs} \)
- **산술 강도**: \( 14 \text{ GFLOPs} / 14 \text{ GB} = 1 \text{ FLOP/Byte} \)

A100 GPU의 피크 연산 능력은 312 TFLOPS, GPU 메모리 대역폭은 2 TB/s입니다. 산술 강도가 1인 작업의 경우:

- **대역폭 병목**: \( 2 \text{ TB/s} \times 1 \text{ FLOP/Byte} = 2 \text{ TFLOPS} \)
- **GPU 활용률**: \( 2 / 312 = 0.6\% \)

**GPU의 99.4% 연산 능력이 유휴 상태입니다!** 이것이 바로 배치 처리를 통해 활용률을 높여야 하는 이유입니다.

### 1.2 배치 처리의 본질

배치 처리의 핵심 아이디어: **여러 요청의 계산을 한 번의 GPU 연산에 병합하는 것**.

batch_size = B일 때:
- **데이터 전송량 불변**: 여전히 14 GB (모델 가중치는 한 번만 로드)
- **계산량은 B배**: \( B \times 14 \text{ GFLOPs} \)
- **산술 강도는 B**: \( B \text{ FLOP/Byte} \)

B = 156일 때, 산술 강도 = 156, GPU 활용률은 100%에 가까워집니다. 이것이 배치 처리가 처리량을 대폭 향상시킬 수 있는 수학적 원리입니다.

## 2. 정적 배치 처리(Static Batching)

### 2.1 작동 방식

정적 배치 처리는 가장 단순한 배치 처리 전략입니다:

1. 고정된 수의 요청을 모아 하나의 batch를 구성
2. 모든 요청이 동시에 Prefill 시작
3. 모든 요청이 동시에 Decode 진입
4. **반드시 batch에서 가장 느린 요청이 완료될 때까지 기다려야** 전체 batch 종료
5. 종료 후에야 다음 batch 처리 시작 가능

```
시간 →
요청A: [Prefill][D1][D2][D3][D4][D5][D6][~~~~대기~~~~]
요청B: [Prefill][D1][D2][D3][D4][D5][D6][D7][D8][D9][D10]
요청C: [Prefill][D1][D2][D3][D4][~~~~대기~~~~~~~~~~~~~~~~~~~~~]
                                    ↑ C는 완료되었지만 B가 끝날 때까지 대기
```

### 2.2 정적 배치 처리의 문제점

**문제 1: GPU 버블(Bubble)**

batch 내 요청의 생성 길이 차이가 클 때, 먼저 완료된 요청에 해당하는 GPU 계산 자원이 낭비됩니다:

```
Batch 내 4개 요청의 생성 길이: [10, 50, 200, 500]
- 10단계 후: 3개의 요청만 계산 중, 1개 위치 낭비
- 50단계 후: 2개의 요청만 계산 중, 2개 위치 낭비
- 200단계 후: 1개의 요청만 계산 중, 3개 위치 낭비
- 평균 GPU 활용률: (10×4 + 40×3 + 150×2 + 300×1) / (500×4) = 37%
```

**63%의 GPU 연산 능력이 낭비됩니다!**

**문제 2: TTFT 지연 증가**

모든 요청이 batch를 구성할 때까지 기다려야 처리를 시작합니다. 첫 번째 요청이 도착한 후, 다른 요청이 도착하여 batch를 구성할 때까지 기다려야 한다면, TTFT가 현저히 증가할 것입니다.

**문제 3: 처리량 제한**

이미 완료된 요청의 위치를 새 요청이 재사용할 수 없습니다. 전체 batch의 유효 처리량은 가장 느린 요청에 의해 결정됩니다.

**문제 4: GPU 메모리 낭비**

batch 내 각 요청에 대해 **최대 가능한 생성 길이**만큼 KV Cache 공간을 미리 할당해야 합니다. 실제 생성 길이는 보통 최대값보다 훨씬 작으므로, 대량의 GPU 메모리 낭비가 발생합니다.

### 2.3 정적 배치 처리의 적용 시나리오

여러 문제점에도 불구하고, 정적 배치 처리는 다음 시나리오에서 여전히 가치가 있습니다:

- **오프라인 배치 추론**: 모든 요청이 알려져 있고, 실시간 응답이 필요 없음
- **고정 길이 생성**: 요약 생성 등(출력 길이 제어 가능)
- **교육/프로토타입 검증**: 구현이 단순하고 이해하기 쉬움

## 3. 동적 배치 처리(Dynamic Batching)

### 3.1 개선 아이디어

동적 배치 처리는 정적 배치 처리의 기초 위에 하나의 핵심적인 개선을 했습니다: **batch 실행 도중에 새 요청을 추가할 수 있도록 허용**.

```
시간 →
요청A: [Prefill][D1][D2][D3][완료]
요청B: [Prefill][D1][D2][D3][D4][D5][D6][D7][완료]
요청C:      [대기.....][Prefill][D1][D2][D3][완료]
                        ↑ A 완료 후, C가 batch에 합류
```

### 3.2 동적 배치 처리의 한계

정적 배치 처리보다 낫지만, 동적 배치 처리에는 여전히 문제가 있습니다:

1. **여전히 요청 수준의 스케줄링**: 새 요청이 합류할 때, Prefill을 수행해야 하지만, 기존 요청은 여전히 Decode 중입니다. 두 연산의 계산 특징이 완전히 달라, 혼합 실행의 효율이 높지 않습니다.
2. **패딩 낭비**: 서로 다른 요청의 입력 길이가 달라, 동일한 길이로 채워야 합니다.
3. **자원 예약**: 여전히 각 요청에 대해 최대 가능한 KV Cache 공간을 예약해야 합니다.

## 4. 연속 배치 처리(Continuous Batching)

### 4.1 핵심 아이디어

연속 배치 처리(Continuous Batching)는 Orca 논문(Yu et al., 2022)에서 제안되었으며, vLLM과 nano-vllm 모두 이 전략을 구현했습니다. 그 핵심 아이디어는 세 가지로 요약할 수 있습니다:

1. **반복 수준 스케줄링(Iteration-level Scheduling)**: 매 순전파(iteration)마다 어떤 시퀀스가 계산에 참여할지 다시 결정
2. **즉시 합류 및 탈퇴**: 새 요청은 임의의 iteration에서 합류할 수 있고, 완료된 요청은 즉시 탈퇴
3. **Prefill과 Decode 분리**: 서로 다른 단계의 시퀀스는 분리하여 처리(또는 chunked-prefill에서 혼합 처리)

```
시간 단계1: [A-prefill, B-prefill]       ← 두 개의 새 요청 prefill 수행
시간 단계2: [A-decode,  B-decode]         ← 두 요청 decode 진입
시간 단계3: [C-prefill] 그 후 다음 단계 [A-decode, B-decode, C-decode] ← nano-vllm 단일 단계 schedule은 prefill/decode를 혼합하지 않음; 여기서는 두 단계로 "연속 반복" 상의 효과를 나타냄
시간 단계4: [A-완료,    B-decode, C-decode]  ← A 완료, 즉시 자원 해제
시간 단계5: [D-prefill]；시간 단계6: [B-decode, C-decode, D-decode]  ← D는 독립된 한 단계에서 prefill 수행 후, B/C와 동일 batch에서 decode
```

### 4.2 정적 배치 처리와의 본질적 차이

| 특성 | 정적 배치 처리 | 연속 배치 처리 |
|------|-----------|-----------|
| 스케줄링 세분성 | 요청 수준(Request-level) | 반복 수준(Iteration-level) |
| batch 생애주기 | 고정, 시작부터 모든 요청 완료까지 | 동적, 매 단계마다 변할 수 있음 |
| 새 요청 합류 | 반드시 현재 batch 종료까지 대기 | 임의의 iteration에서 합류 가능 |
| 요청 탈퇴 | 반드시 모든 요청 종료까지 대기 | 완료 즉시 탈퇴, 자원 즉시 해제 |
| GPU 활용률 | 낮음(버블 있음) | 높음(항상 가득 채움) |
| KV Cache 관리 | 사전 할당, 낭비 큼 | 필요 기반 할당(PagedAttention) |

### 4.3 토큰 수준 스케줄링 vs 요청 수준 스케줄링

**요청 수준 스케줄링(Request-level Scheduling)**:

"요청"을 단위로 스케줄링 결정을 내립니다. 한 요청이 처리를 시작하면, 완료될 때까지 지속적으로 처리합니다.

**토큰 수준 스케줄링(Token-level Scheduling)**:

"토큰"을 단위로 스케줄링 결정을 내립니다. 매 토큰 생성 후, 스케줄러는 모든 시퀀스를 재평가하여, 다음에 어떤 것을 처리할지 결정합니다.

nano-vllm의 연속 배치 처리는 실제로는 **반복 수준 스케줄링**입니다—`schedule()` 호출마다 이번 단계 계산에 참여할 시퀀스 집합을 다시 결정합니다. 이는 요청 수준 스케줄링보다 더 유연하지만, 엄격한 토큰 수준 스케줄링은 아닙니다(한 단계에서 모든 시퀀스가 동일한 순전파를 공유하기 때문).

```python
# nano-vllm의 메인 루프: 단계마다 schedule() 호출
def step(self):
    seqs, is_prefill = self.scheduler.schedule()   # ← 단계마다 재스케줄링
    token_ids = self.model_runner.call("run", seqs, is_prefill)
    self.scheduler.postprocess(seqs, token_ids)
```

### 4.4 연속 배치 처리가 정적 배치 처리의 문제를 어떻게 해결하는가

| 정적 배치 처리의 문제 | 연속 배치 처리의 솔루션 |
|----------------|-------------------|
| GPU 버블 | 요청 완료 후 즉시 탈퇴, 자리를 새 요청이 채움 |
| TTFT 지연 큼 | 새 요청은 다음 iteration에서 즉시 prefill 수행 가능 |
| 처리량 제한 | GPU가 항상 만재 상태 유지, 유효 계산 비율 높음 |
| GPU 메모리 낭비 | PagedAttention과 연계하여 필요 기반 KV Cache 할당 |

## 5. nano-vllm에서의 연속 배치 처리 구현

### 5.1 아키텍처 총람

nano-vllm의 연속 배치 처리는 다음 컴포넌트들의 협업으로 구현됩니다:

```
LLMEngine.step()          ← 구동 메인 루프
    ↓
Scheduler.schedule()      ← 반복 수준 스케줄링 결정
    ├── prefill 분기       ← waiting 큐의 새 요청 우선 처리
    └── decode 분기        ← waiting이 비어 있을 때 running 큐 처리
    ↓
ModelRunner.run()         ← 순전파 실행
    ↓
Scheduler.postprocess()   ← 토큰 추가, 종료 판단, 완료된 시퀀스 정리
```

### 5.1.1 `LLMEngine.generate` / `step`: 핵심 루프 (교육용 간소화 버전)

아래는 tqdm, 처리량 통계 등 세부 사항을 제거하고, **연속 배치 처리**와 가장 관련된 제어 흐름만 남긴 것입니다(`nano-vllm-main/nanovllm/engine/llm_engine.py` 논리와 일치하며, 읽기용 버전입니다):

```python
def generate(self, prompts, sampling_params, use_tqdm=True):
    for prompt, sp in zip(prompts, sampling_params):
        self.add_request(prompt, sp)
    outputs = {}
    while not self.is_finished():
        output, num_tokens = self.step()
        for seq_id, token_ids in output:
            outputs[seq_id] = token_ids
    outputs = [outputs[seq_id] for seq_id in sorted(outputs.keys())]
    outputs = [{"text": self.tokenizer.decode(token_ids), "token_ids": token_ids} for token_ids in outputs]
    return outputs

def step(self):
    seqs, is_prefill = self.scheduler.schedule()
    token_ids = self.model_runner.call("run", seqs, is_prefill)
    self.scheduler.postprocess(seqs, token_ids)
    outputs = [(seq.seq_id, seq.completion_token_ids) for seq in seqs if seq.is_finished]
    num_tokens = sum(len(seq) for seq in seqs) if is_prefill else -len(seqs)
    return outputs, num_tokens
```

**요점**:

- 외부 루프 `while not self.is_finished()`: 각 라운드는 하나의 **반복**입니다; prefill 여부, batch 내 어떤 시퀀스들이 있는지는 전적으로 `schedule()`이 결정합니다.
- `step()` 내에서 **먼저 스케줄링, 그 다음 추론, 마지막으로 후처리**하며, 순서를 바꿀 수 없습니다: 후처리에서야 `append_token`을 하고 `running`을 갱신합니다.
- 저장소에서 `num_tokens`는 prefill 단계에서 각 시퀀스 길이의 합, decode 단계에서는 `-len(seqs)`이며, 진행률 표시줄의 처리량 추정에만 사용됩니다; 면접에서 "연속 배치 처리"를 답변할 때는 `schedule()`을 중점적으로 설명하면 됩니다.

### 5.2 스케줄링 로직과 연속 배치 처리의 대응

#### Prefill 단계: 새 요청의 batch 합류

```python
# scheduler.py - schedule()의 prefill 분기 (num_seqs / num_batched_tokens 초기값 0)
while self.waiting and num_seqs < self.max_num_seqs:
    seq = self.waiting[0]
    if num_batched_tokens + len(seq) > self.max_num_batched_tokens \
       or not self.block_manager.can_allocate(seq):
        break
    num_seqs += 1
    self.block_manager.allocate(seq)
    num_batched_tokens += len(seq) - seq.num_cached_tokens
    seq.status = SequenceStatus.RUNNING
    self.waiting.popleft()
    self.running.append(seq)
    scheduled_seqs.append(seq)
if scheduled_seqs:
    return scheduled_seqs, True   # ← prefill 모드
```

이 코드는 연속 배치 처리의 **"즉시 합류"** 특성을 구현합니다:
- `schedule()` 호출마다, waiting이 비어 있지 않고 자원이 허용되면, 즉시 새 요청을 처리
- 새 요청은 현재 batch가 끝날 때까지 기다릴 필요가 없음
- 여러 개의 새 요청이 동일 단계에서 함께 prefill 수행 가능

#### Decode 단계: 기존 요청 계속 생성

```python
# scheduler.py - schedule()의 decode 분기 (저장소와 일치)
while self.running and num_seqs < self.max_num_seqs:
    seq = self.running.popleft()
    while not self.block_manager.can_append(seq):
        if self.running:
            self.preempt(self.running.pop())
        else:
            self.preempt(seq)
            break
    else:
        num_seqs += 1
        self.block_manager.may_append(seq)
        scheduled_seqs.append(seq)
assert scheduled_seqs
self.running.extendleft(reversed(scheduled_seqs))
return scheduled_seqs, False   # ← decode 모드
```

이 코드는 연속 배치 처리의 **"동적 batch 조합"** 특성을 구현합니다:
- 단계별 decode 시, running 큐에서 시퀀스를 선택하여 batch 구성
- 자원이 부족하면, 선점을 통해 블록 해제
- batch 구성은 매 단계마다 달라질 수 있음

#### 후처리: 완료된 요청 즉시 탈퇴

```python
# scheduler.py - postprocess()
def postprocess(self, seqs, token_ids):
    for seq, token_id in zip(seqs, token_ids):
        seq.append_token(token_id)
        if (not seq.ignore_eos and token_id == self.eos) or \
           seq.num_completion_tokens == seq.max_tokens:
            seq.status = SequenceStatus.FINISHED
            self.block_manager.deallocate(seq)   # ← 즉시 KV Cache 해제
            self.running.remove(seq)              # ← 즉시 batch에서 탈퇴
```

이 코드는 연속 배치 처리의 **"즉시 탈퇴"** 특성을 구현합니다:
- 시퀀스가 EOS를 생성하거나 max_tokens에 도달하면, **즉시** 자원 해제
- batch 내 다른 시퀀스가 완료될 때까지 기다릴 필요 없음
- 해제된 블록은 다음 단계에서 새 요청이 사용 가능

### 5.3 Prefill 우선 전략의 의미

nano-vllm은 **Prefill 우선** 전략을 채택합니다. 이는 다음을 의미합니다:

```
Step 1: waiting=[A,B,C], running=[]
        → prefill A,B （자원이 두 개 허용）
        → running=[A,B], waiting=[C]

Step 2: waiting=[C], running=[A,B]
        → prefill C （waiting이 비어 있지 않음, prefill 우선）
        → running=[A,B,C], waiting=[]

Step 3: waiting=[], running=[A,B,C]
        → decode A,B,C
        → A 완료 → running=[B,C]

Step 4: waiting=[D]（새 요청 도착）, running=[B,C]
        → prefill D （waiting이 비어 있지 않음, prefill 우선）
        → running=[B,C,D]

Step 5: waiting=[], running=[B,C,D]
        → decode B,C,D
```

Step 4에 주목하세요: B, C가 decode 중이더라도, 새 요청 D가 도착하면, 스케줄러는 D의 prefill을 우선 처리하며, B와 C는 이번 단계에서 decode하지 않습니다. 이것이 "Prefill 우선"의 의미입니다—**새 요청의 TTFT는 최소화되지만, 기존 요청의 TPOT는 증가할 수 있습니다**.

### 5.4 nano-vllm이 패딩을 피하는 방법

전통적인 배치 처리는 서로 다른 길이의 시퀀스를 동일한 길이로 채워야 하므로, 계산 낭비가 발생합니다. nano-vllm은 다음 기술을 통해 패딩을 피합니다:

**Prefill 단계**: `flash_attn_varlen_func` 사용

```python
# model_runner.py - prepare_prefill()
input_ids, positions, cu_seqlens_q, cu_seqlens_k = [], [], [0], [0]
for seq in seqs:
    input_ids.extend(seq[seq.num_cached_tokens:])
    positions.extend(list(range(seq.num_cached_tokens, len(seq))))
    cu_seqlens_q.append(cu_seqlens_q[-1] + seqlen_q)
    cu_seqlens_k.append(cu_seqlens_k[-1] + seqlen_k)
```

모든 시퀀스의 토큰을 하나의 1차원 텐서로 **이어붙이고**, `cu_seqlens`(cumulative sequence lengths)를 통해 각 시퀀스의 경계를 기록합니다. FlashAttention의 가변 길이 인터페이스는 이러한 형식을 처리할 수 있어, 패딩이 필요 없습니다.

**Decode 단계**: 각 시퀀스에 토큰이 1개뿐

```python
# model_runner.py - prepare_decode()
for seq in seqs:
    input_ids.append(seq.last_token)
    positions.append(len(seq) - 1)
```

모든 시퀀스가 각각 1개의 토큰을 가지므로, 자연스럽게 길이가 같아져 패딩이 필요 없습니다.

## 6. GPU 활용률 분석

### 6.1 정량 분석

100개의 요청이 있고, 입력 길이는 모두 100 토큰, 출력 길이는 [10, 200] 토큰 사이에 균등 분포한다고 가정합니다.

**정적 배치 처리(batch_size=10)**:

```
각 batch의 실행 단계 수 = max(batch 내 10개 요청의 출력 길이)
기대값 ≈ 190단계 (10개 균등 분포 표본의 최대값 기대)
10개 요청의 평균 출력 길이 = 105
GPU 활용률 ≈ (10 × 105) / (10 × 190) = 55%

총 완료 시간: 10개 batch × 190단계 = 1900단계
```

**연속 배치 처리(max_num_seqs=10)**:

```
GPU는 항상 10개의 시퀀스가 실행 중 유지 (하나 완료, 새것 즉시 합류)
GPU 활용률 ≈ 100% (prefill 오버헤드 무시)

총 완료 시간: 모든 100개 요청의 총 토큰 수 / 10
= (100 × 100 + 100 × 105) / 10
= 2050단계
```

잠깐, 총 단계 수를 보면 연속 배치 처리가 더 많은 것처럼 보입니다? 이는 연속 배치 처리의 장점이 주로 **처리량**에 반영되기 때문입니다:

- **정적 배치 처리 처리량**: \( \frac{100 \times 105}{1900} = 5.5 \text{ tokens/step} \)
- **연속 배치 처리 처리량**: \( \frac{100 \times 105}{2050} \approx 5.1 \text{ tokens/step} \)

하지만 연속 배치 처리의 **진정한 장점**은:
1. **각 요청의 TTFT가 더 낮음**(batch를 구성할 때까지 기다릴 필요 없음)
2. **GPU 버블 없음**(이미 완료된 요청을 위해 공회전할 필요 없음)
3. **PagedAttention과 함께 사용 시, GPU 메모리 효율이 더 높음**

### 6.2 실제 GPU 활용률에 영향을 미치는 요인

| 요인 | 영향 | nano-vllm에서의 파라미터 |
|------|------|-------------------|
| max_num_seqs | batch가 클수록, GPU 산술 강도가 높아짐 | `config.max_num_seqs` |
| max_num_batched_tokens | 단일 단계 prefill의 토큰 총량 제한 | `config.max_num_batched_tokens` |
| KV Cache block 총 수 | 동시에 서비스할 수 있는 시퀀스 수 결정 | `config.num_kvcache_blocks` |
| 요청 도착 속도 | waiting 큐 길이와 스케줄링 빈도에 영향 | 외부 입력 |
| 출력 길이 분포 | 시퀀스가 탈퇴/합류하는 빈도에 영향 | 요청이 결정 |

### 6.3 Prefill과 Decode의 자원 경쟁

nano-vllm의 Prefill 우선 전략 하에서, Prefill과 Decode는 동시에 실행되지 않습니다. 이는 두 연산의 자원 경쟁을 피할 수 있지만, 또 다른 문제를 도입합니다:

```
시간 →
[Prefill A,B,C (800 tokens, 시간이 오래 걸림)]
[Decode  D,E (2 tokens, 시간이 매우 짧음)]
[Prefill F (200 tokens)]
[Decode  A,B,C,D,E (5 tokens)]
```

Prefill이 긴 프롬프트를 처리할 때, Decode는 완전히 차단되고, 기존 시퀀스는 새 토큰을 생성할 수 없습니다. 사용자가 인지하는 현상은: **생성 중이던 응답이 갑자기 "멈추는"** 것입니다.

이것이 chunked prefill의 동기 중 하나입니다—긴 Prefill을 여러 개의 작은 chunk로 나누어, Decode와 교대로 실행하는 것입니다.

## 7. vLLM 및 Orca와의 비교

### 7.1 Orca(OSDI 2022)

Orca는 연속 배치 처리의 선구적인 작업이며, 그 핵심 기여는:

1. **반복 수준 스케줄링(Iteration-level Scheduling) 제안**: 매 순전파마다 참여할 시퀀스를 다시 선택
2. **선택적 배치 처리(Selective Batching)**: Attention 레이어에서는 각 시퀀스를 개별 처리하고, FFN 레이어에서만 배치 처리 수행
3. **Prefill과 Decode 혼합 지원**: 동일 batch 내에 prefill 시퀀스와 decode 시퀀스가 동시에 있을 수 있음

nano-vllm이 Orca에 비해 **간소화**된 점:
- 동일 단계에서 prefill과 decode를 혼합하지 않음
- 선택적 배치 처리를 하지 않음(FlashAttention을 사용하여 통일 처리)

### 7.2 vLLM(SOSP 2023)

vLLM은 Orca의 기초 위에 **PagedAttention**과 더 완전한 스케줄링 메커니즘을 도입했습니다:

| 특성 | vLLM | nano-vllm |
|------|------|-----------|
| 연속 배치 처리 | ✅ | ✅ |
| PagedAttention | ✅ | ✅ |
| Chunked Prefill | ✅ | ❌ |
| Swap(CPU↔GPU) | ✅ | ❌(recompute 사용) |
| 프리픽스 캐시 | ✅ | ✅ |
| Beam Search | ✅ | ❌ |
| SequenceGroup | ✅ | ❌ |
| Speculative Decoding | ✅ | ❌ |
| 다중 노드 추론 | ✅ | ❌ |

### 7.3 Chunked Prefill

Chunked Prefill은 vLLM 후속 버전에서 도입된 중요한 최적화로, nano-vllm의 한 핵심 문제를 해결합니다:

**문제**: 긴 프롬프트의 Prefill이 Decode를 차단합니다.

**솔루션**: 긴 Prefill을 여러 개의 chunk로 나누어, 각 chunk를 Decode batch와 혼합 실행합니다.

```
전통적(nano-vllm)：
Step 1: [Prefill A, 1000 tokens]  ← 시간이 오래 걸리며, Decode가 차단됨
Step 2: [Decode B, C, D, E]

Chunked Prefill(vLLM)：
Step 1: [Prefill A chunk1 (256 tokens), Decode B, C, D, E]
Step 2: [Prefill A chunk2 (256 tokens), Decode B, C, D, E]
Step 3: [Prefill A chunk3 (256 tokens), Decode B, C, D, E]
Step 4: [Prefill A chunk4 (232 tokens), Decode B, C, D, E]
```

Chunked Prefill의 장점:
- Decode가 Prefill에 의해 차단되지 않음
- 단계별 실행 시간이 더 균일함
- 더 나은 꼬리 지연(P99 latency)

Chunked Prefill의 대가:
- 구현 복잡도 증가
- 어텐션 커널이 혼합 모드를 지원해야 함
- Prefill의 총 소요 시간이 증가할 수 있음(여러 단계로 나누어 처리하므로)

### 7.4 세 가지 스케줄링 전략 비교

```
Orca:
  - prefill과 decode 혼합 허용
  - 선택적 배치 처리
  - 반복 수준 스케줄링

vLLM:
  - chunked prefill 지원(prefill + decode 혼합)
  - PagedAttention으로 KV Cache 관리
  - Swap 메커니즘으로 KV Cache 오버플로우 처리
  - 완전한 우선순위 및 공정성 보장

nano-vllm:
  - Prefill 우선, 혼합하지 않음
  - PagedAttention으로 KV Cache 관리
  - Recompute 전략(swap 하지 않음)
  - 간결한 구현, 교육에 적합
```

## 8. 심층 이해: 연속 배치 처리의 핵심 설계 결정

### 8.1 Prefill과 Decode를 혼합해야 하는가

**비혼합(nano-vllm 방안)**:

장점:
- 구현이 단순, `prepare_prefill`과 `prepare_decode`가 독립적
- 단일 단계 내 모든 시퀀스의 계산 모드가 일관되어, CUDA Graph 최적화에 유리
- 스케줄링 로직이 단순하고 명료함

단점:
- Prefill이 Decode를 차단하여, TPOT의 안정성에 영향
- 긴 프롬프트 시나리오에서 Decode 대기 시간이 제어 불가

**혼합(vLLM chunked-prefill 방안)**:

장점:
- Decode가 Prefill에 의해 차단되지 않음
- 더 안정적인 TPOT
- GPU 활용률이 더 높음

단점:
- 어텐션 커널이 혼합 길이 입력을 지원해야 함
- CUDA Graph 최적화가 어려움(단계별 batch shape이 다름)
- 스케줄링 로직이 복잡함

### 8.2 선점 전략의 선택

KV Cache 공간이 부족할 때, 어떤 시퀀스를 선점할지 결정해야 합니다:

| 전략 | 설명 | nano-vllm |
|------|------|-----------|
| LIFO | 가장 늦게 합류한 시퀀스 선점 | ✅ 이 전략 사용 |
| FIFO | 가장 일찍 합류한 시퀀스 선점 | ❌ |
| LRU | 가장 최근에 가장 적게 사용된 것 선점 | ❌ |
| 최단 잔여 시간 우선 | 잔여 생성 길이 추정, 가장 긴 것 선점 | ❌ |
| 무작위 | 무작위 선점 | ❌ |

nano-vllm이 LIFO를 선택한 이유: 가장 늦게 합류한 시퀀스가 보통 가장 적은 토큰을 생성했으므로, 선점 후 다시 prefill하는 대가가 가장 적습니다.

### 8.3 max_num_seqs와 max_num_batched_tokens의 관계

이 두 파라미터는 연속 배치 처리의 동작을 공동으로 제어합니다:

- `max_num_seqs`: batch 내에 최대 몇 개의 시퀀스가 포함될 수 있는지 제한. 주로 KV Cache 총량과 CUDA Graph의 batch size 제한에 의해 제약됩니다.
- `max_num_batched_tokens`: 단일 단계 prefill에서 최대 몇 개의 토큰을 처리할 수 있는지 제한. 주로 GPU 메모리(활성화 값 크기)와 계산 시간(TTFT에 영향)에 의해 제약됩니다.

양자의 시너지 효과:

```
시나리오1: max_num_seqs=256, max_num_batched_tokens=2048
  → Prefill 시, 최대 한 번에 2048개 토큰 처리 (1개의 긴 프롬프트 또는 여러 개의 짧은 프롬프트일 수 있음)
  → Decode 시, 최대 256개 시퀀스가 동시에 decode

시나리오2: max_num_seqs=32, max_num_batched_tokens=8192
  → Prefill 시, 매우 긴 프롬프트 처리 가능 (하지만 batch 내 시퀀스 수는 많지 않음)
  → Decode 시, 최대 32개 시퀀스
```

nano-vllm에서, 이 두 파라미터는 `Config`에서 설정되고, `Scheduler`에 전달됩니다:

```python
class Scheduler:
    def __init__(self, config):
        self.max_num_seqs = config.max_num_seqs
        self.max_num_batched_tokens = config.max_num_batched_tokens
```

## 9. 연속 배치 처리의 성능 최적화 방향

### 9.1 CUDA Graph와 연속 배치 처리

CUDA Graph는 GPU 커널 런칭 오버헤드를 대폭 줄일 수 있지만, 입력 shape이 고정되어야 합니다. 연속 배치 처리에서는 단계별 batch size가 다를 수 있어, CUDA Graph의 요구 사항과 모순됩니다.

nano-vllm의 솔루션: **미리 다양한 batch size에 대해 CUDA Graph를 캡처**하고, 런타임에 가장 가까운 것을 선택.

```python
# model_runner.py
def capture_cudagraph(self):
    for bs in capture_batch_sizes():   # 가능한 batch size 열거
        self.graph_runners[bs] = CUDAGraphRunner(self.model, bs)
```

Decode 단계의 batch size는 보통 1~max_num_seqs 사이에서 변화합니다. 사전 캡처를 통해 대부분의 상황을 커버할 수 있습니다.

### 9.2 프리픽스 캐시와 연속 배치 처리

프리픽스 캐시(Prefix Caching)는 연속 배치 처리에서 그 역할이 더욱 중요합니다:

- 여러 요청이 동일한 system prompt를 공유 → 프리픽스의 KV Cache 재사용 가능
- 선점된 시퀀스가 재스케줄링될 때 → 부분적으로 프리픽스 캐시에 적중할 수 있어, 다시 prefill하는 계산량 감소
- Prefill 단계의 소요 시간 감소 → Decode가 차단되는 시간이 더 짧아짐

### 9.3 투기적 디코딩(Speculative Decoding)

투기적 디코딩은 연속 배치 처리의 효율을 향상시키는 또 다른 기술입니다:

- 작은 모델을 사용하여 여러 후보 토큰을 빠르게 생성
- 대형 모델이 모든 후보를 한 번에 검증
- 올바른 후보는 바로 채택되어, 대형 모델의 Decode 단계 수 감소

nano-vllm은 이 기술을 구현하지 않았지만, vLLM에서는 이미 지원하고 있습니다.

## 10. 면접 빈출 주제

### Q1: 연속 배치 처리(Continuous Batching)의 원리와 정적 배치 처리 대비 장점을 설명하세요.

**참고 답안**:

연속 배치 처리는 반복 수준 스케줄링 전략으로, 매 순전파마다 어떤 시퀀스가 계산에 참여할지 다시 결정합니다. 정적 배치 처리와 비교하여:

1. **즉시 합류**: 새 요청은 현재 batch가 끝날 때까지 기다리지 않고 합류 가능, TTFT 감소
2. **즉시 탈퇴**: 완료된 요청은 즉시 자원 해제, GPU 버블 없음
3. **동적 batch**: batch 구성은 매 단계마다 변할 수 있어, GPU가 항상 만재 상태 유지
4. **PagedAttention과 연계**: 필요 기반 KV Cache 할당, GPU 메모리 낭비 방지

### Q2: nano-vllm의 연속 배치 처리 구현의 특징과 한계는 무엇인가요?

**참고 답안**:

특징:
- **Prefill 우선 전략**: waiting 요청이 있으면 prefill을 우선하여, TTFT 최소화
- **prefill과 decode 비혼합**: 한 단계에 한 가지 연산만 수행, 구현 단순화
- **Recompute 전략**: 선점된 시퀀스는 CPU로 swap하는 대신 prefill 재수행
- **프리픽스 캐시**: prefill 재수행의 계산량 감소

한계:
- chunked prefill 미지원, 긴 프롬프트가 decode를 차단
- swap 미지원, 선점 대가가 비교적 높음
- Prefill 우선으로 인해 decode가 굶주릴 수 있음

### Q3: Prefill 우선과 Decode 우선은 각각 어떤 장단점이 있나요? 실제 시스템에서는 어떻게 선택하나요?

**참고 답안**:

| | Prefill 우선 | Decode 우선 |
|--|-------------|------------|
| TTFT | 낮음 | 높음 |
| TPOT 안정성 | 나쁨(prefill에 의해 중단됨) | 좋음 |
| 처리량 | 요청 도착 패턴에 따라 다름 | 요청 도착 패턴에 따라 다름 |
| 적용 시나리오 | 대화형 상호작용(사용자가 첫 글자를 기다림) | 배치 생성(처리량 추구) |

실제 시스템에서는 보통 chunked prefill을 절충안으로 사용합니다: Prefill을 작은 조각으로 나누어 Decode와 혼합 실행하여, TTFT와 TPOT 안정성을 모두 고려합니다.

### Q4: 연속 배치 처리는 어떻게 패딩 낭비를 피하나요?

**참고 답안**:

두 가지 기술:
1. **Prefill 단계**: FlashAttention의 가변 길이 인터페이스(`flash_attn_varlen_func`)를 사용하여, 모든 시퀀스의 토큰을 1차원 텐서로 이어붙이고, `cu_seqlens`로 경계를 기록. 짧은 시퀀스를 가장 긴 시퀀스의 길이로 채울 필요가 없음.
2. **Decode 단계**: 각 시퀀스에 토큰이 1개뿐이므로 자연스럽게 길이가 같으며, `flash_attn_with_kvcache`와 block_table을 함께 사용하여 페이징 어텐션 수행.

### Q5: Orca, vLLM, nano-vllm의 연속 배치 처리 구현을 비교하세요.

**참고 답안**:

- **Orca**(창시자): 반복 수준 스케줄링과 선택적 배치 처리 제안. 동일 단계에서 prefill과 decode 시퀀스 혼합 허용, 하지만 Attention 레이어에서 분리 처리 필요.
- **vLLM**: Orca 기초 위에 PagedAttention으로 KV Cache 관리 도입, chunked prefill로 긴 prefill 분할 지원, swap 메커니즘으로 KV Cache 오버플로우 처리, 프리픽스 캐시 등 고급 기능.
- **nano-vllm**: 간소화된 구현, 연속 배치 처리와 PagedAttention의 핵심 사상 유지. prefill 우선 비혼합 전략 채택, swap 대신 recompute 사용, 코드가 간결하여 교육에 적합.

### Q6: Chunked Prefill이란 무엇인가요? 어떤 문제를 해결하나요?

**참고 답안**:

Chunked Prefill은 긴 프롬프트의 Prefill을 여러 개의 chunk로 나누어(예: chunk당 256 토큰), 각 chunk를 Decode batch와 혼합 실행하는 것입니다.

해결하는 문제:
1. **Decode 차단**: 전통적인 Prefill 우선 전략에서, 긴 프롬프트가 오랫동안 Decode를 차단하여, 기존 시퀀스가 새 토큰을 생성할 수 없음
2. **TPOT 불안정**: Decode가 간헐적으로 중단되어, 사용자가 생성 속도가 빨라졌다 느려졌다 하는 것을 인지함
3. **꼬리 지연 높음**: 긴 Prefill로 인해 P99 지연이 크게 증가

대가는 구현 복잡도 증가, 어텐션 커널이 혼합 길이 입력을 지원해야 함.

### Q7: 연속 배치 처리에서, max_num_seqs의 최적값을 어떻게 결정하나요?

**참고 답안**:

`max_num_seqs`의 최적값은 여러 요인에 따라 달라집니다:

1. **KV Cache 총량**: `num_kvcache_blocks`를 각 시퀀스가 평균적으로 필요로 하는 block 수로 나누어 상한 획득
2. **GPU 연산 능력**: batch가 너무 크면 Decode가 memory-bound에서 compute-bound로 변하여, TPOT 증가
3. **CUDA Graph 제한**: 모든 가능한 batch size에 대해 그래프를 사전 캡처해야 함
4. **지연 SLA**: TPOT가 서비스 수준 협약을 반드시 충족해야 함

일반적인 방법은 프로파일링을 통해 결정하는 것입니다: 작은 값에서 큰 값으로 max_num_seqs를 증가시키며, 처리량과 TPOT를 관찰하여, 처리량이 포화되고 TPOT가 SLA를 충족하는 지점을 선택합니다.

## 11. 요약

| 요점 | 내용 |
|------|------|
| **정적 배치 처리** | 고정 batch, 가장 느린 요청이 완료되어야 새 batch 시작 가능. GPU 버블과 TTFT 문제 있음 |
| **연속 배치 처리** | 반복 수준 스케줄링, 요청 즉시 합류/탈퇴 가능, GPU 항상 만재 |
| **nano-vllm 전략** | Prefill 우선 + 비혼합 + Recompute 선점 + 프리픽스 캐시 |
| **패딩 회피** | Prefill은 `cu_seqlens` 가변 길이 어텐션 사용, Decode는 자연스럽게 동일 길이 |
| **핵심 비교** | Orca(창시)→vLLM(PagedAttention + Chunked Prefill)→nano-vllm(교육용 간소화) |
| **성능 핵심** | `max_num_seqs`와 `max_num_batched_tokens`가 처리량과 지연을 공동 제어 |

**핵심 기억 구호**:

> 정적 배치 처리는 **가장 느린 것을 기다리고**, 연속 배치 처리는 **멈추지 않고 돌아간다**;
> Prefill 우선은 **첫 글자가 빠르고**, Decode 라운드 로빈은 **끊기지 않는다**;
> CUDA Graph는 **형상을 고정하고**, 프리픽스 캐시는 **재계산을 절약한다**.

**다음 강의 예고**: 연속 배치 처리의 스케줄링 전략을 숙달했으니, 이제 **ModelRunner 모델 실행기**로 들어가—스케줄러가 선택한 시퀀스를 어떻게 실제 GPU 계산으로 변환하는지, 입력 준비, 모델 실행 및 샘플링의 완전한 흐름을 이해할 것입니다.
